## The uncomfortable pattern: most findings are in the drills, not the system

Seven of this run's ten findings are defects in the **runbooks themselves**, and five of those would
have produced a *false result* — three false PASSes and two false FAILs. That matters more than it
sounds: a drill's only output is a written judgement, so a runbook that reliably mis-measures is
worse than no drill at all.

**False FAILs — a healthy system reported as broken:**

- **03/2** — `php artisan serve` serialises backgrounded probes unless started with `--no-reload`
  **and** `PHP_CLI_SERVER_WORKERS ≥ 2` (Laravel silently downgrades to one worker, warning only into
  the serve log). Produces `3 / 6 / 9 / 12 / 15 s` — the textbook signature of N × `read_timeout`
  stacking, which is *the* headline finding this drill hunts for — against a system bounding every
  request at exactly one `read_timeout`. Caught only by the solo control.
- **01/1** — unconfigured-KV mode is incompatible with `APP_ENV=staging`, which drill 03 mandates.
  `guardUnconfigured()` throws by design outside `local`, so every `SyncSubdomainToKvJob` fails and
  writes a `failed_jobs` row — listed in the runbook as a FAIL signal. Running 03 then 01 in one
  session walks straight into it.
- **01/3** — reading `ready` and `reserved` as two separate `redis-cli` calls can straddle an
  in-flight job and read as "the job vanished from both", the runbook's most serious FAIL signal.

**False PASSes — nothing actually tested:**

- **02/1** — the `fresha` seed recipe (`payload => ['url' => …]`) makes `FreshaFetch` 304 on its
  first guard. No HTTP request, no exception, `status='ok'`. An operator reading the attempt count
  records "Variant 2: bounded at 1 attempt" having never executed the raw-exception path at all.
- **03/4** — `ps aux | grep -c '[h]orizon:work'` reads a healthy Horizon as dead mid-outage, because
  worker *children* legitimately exit and respawn while the master and five supervisors keep running.
- **01/2** — a one-shot batch cannot enter Scenario A's race (pickup latency ~3 s against a ~5 ms
  job), so "all jobs remained queued" gets recorded as Pass A without the interesting half ever
  happening.

All six are **fixed in this branch**. The drills are now measurably harder to fool than they were
this morning.

### Update — 03/3 closed, 2026-08-06 (same day)

**The decision this table asked for was taken, and it was NOT the option sketched above.**
Adding `leads` to `FAIL_OPEN_LIMITERS` was rejected for exactly the reason the finding names — it
would leave a public write endpoint unmetered during the window an attacker would pick. Instead the
limiter gained a **third failure mode**: on a store fault `leads` answers from a Postgres counter
over `analytics.lead_submissions` (a table both controllers behind that limiter already write on
every outcome), degrading to closed/503 if Postgres is also gone. It never opens.

Design: `docs/superpowers/specs/2026-08-06-enquiry-path-redis-resilience-design.md`.
Merged to `development` as `759fb7c52` (CI 9/9 green).

**The filed P2 understated the problem.** `throttle:leads` was the first of **five** Redis gates on
`POST /public/enquiry`, not one — repairing only it would have moved the failure downstream and made
it dirtier (a 500 on an already-committed lead rather than a clean 503). All five are now repaired;
the fifth (`CustomerObserver` → `UserCacheService::invalidateCustomerCount()` → unguarded
`Cache::deleteMultiple()`, sitting *before* `$enquiry->save()`) was found only by the final
whole-branch review, after all eight per-task reviews had passed.

**Verified against a real outage, not a test double** — `logs/2026-08-06-redis-down-rerun.md`:
enquiry `200 · 0.023s` where the pre-fix run recorded 503 with the lead discarded; row persisted with
`notifications_pending_since`; reconciler drained 4 → 0 with all 8 jobs delivered and zero failed; an
over-limit burst from one IP still returned **429**, so the gate degrades without opening. Scenario C
(hung Redis) re-run too — `200` in both the solo control and a 40s-hang parallel round.

Drill 03's pass criterion "no non-analytics data loss" is now **PASS** (was PARTIAL) in
`03-redis-down.md`.

  outage stops job delivery before any job can consult `FeatureAvailability`. Verified by direct
  call instead.

  container is stopped. Needs a real scratch project.
