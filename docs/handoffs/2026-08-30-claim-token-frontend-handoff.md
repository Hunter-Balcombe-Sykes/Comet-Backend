## TL;DR

Today, **any logged-in stranger who guesses a demo site's subdomain can claim it** — the site, its scraped content, and all future dashboard access. That has been true since August and is still true right now.

The backend fix is merged but switched off, because turning it on before the claim page sends a token would make *every* self-serve claim fail with a 404. **Frontend work is the only thing between the fix and it being effective.**

What you need to do:

1. 🔴 **Capture, keep and send `claim_token`** — read it from the build response, hold it against that subdomain, send it in the `POST /api/claim` body. **Ship this now**: while the flag is off the backend ignores it, so there is no coordination needed and no risk in landing early.
2. 🟡 **Handle the DM'd `?t=` link** (`/claim/{subdomain}?t=<token>`) — nothing reads that param today. Same mechanism, worth doing in the same pass.
3. 🟢 **Fix the 404 copy** — see §5. It becomes actively misleading once enforcement is on.

## 1. What the backend does now

Two changes, both live on dev.

**Every new demo site mints a secret token.** `POST /api/public/signup/build` now returns a one-time `claim_token`, generated by `ClaimTokenIssuer` (32 random bytes, base64url, 43 chars). It is returned **exactly once**, in that response, and never again — only a SHA-256 hash is stored. Verified working on dev: build `thai-on-wok` (2026-08-29) minted automatically at creation.

**The claim endpoint can require proof — but doesn't yet.** `ClaimSiteService::claim()` gained a lane-agnostic gate behind `config('partna.pre_account.require_claim_proof')` / `PARTNA_PRE_ACCOUNT_REQUIRE_CLAIM_PROOF`, which **ships `false`**. Claims behave exactly as they always have.

Previously the gate only fired for *outreach* builds (`built_via` of `staff` / `early_access`). A self-serve `signup` build with no `contact_email` had **no ownership check at all**.

## 2. Order of operations

Order matters — flipping the flag before step 1 ships breaks claiming for every real user.

| # | Owner | Step | State |
|---|-------|------|-------|
| 1 | **Frontend** | Capture + forward `claim_token` | ⬜ **This handoff** |
| 2 | Backend | Backfill tokens on pre-existing untokened builds | ✅ Done 2026-08-30 (13 on dev; new ones auto-mint) |
| 3 | Backend | Flip `PARTNA_PRE_ACCOUNT_REQUIRE_CLAIM_PROOF=true`, dev first | ⬜ Blocked on step 1 |

Only step 3 closes the hole. It also rewrites ~50 backend tests (including `tests/Postgres/ClaimConcurrencyTest.php`, whose hand-rolled DDL lacks `built_via` and `claim_token_*`), so it is its own piece of work.

## 3. The wire

**All responses are flat JSON — there is no `data` envelope on any of these endpoints.** (`ApiController::success()` returns `response()->json($data)` directly.)

### `POST /api/public/signup/build`

Unauthenticated. Rate limited 3/min + 10/hour per IP, and still requires the bot-token header you already send.

**The status code tells you whether a token was minted:**

- `202` — a **new** build. `claim_token` is present.
- `200` — an **existing** build was re-served (dedupe on `source_type` + `source_ref`). **No token.**

```jsonc
// 202 — new build
{
  "build_id":     "01a04b84-e729-7242-b892-0635275c1bb6",
  "build_state":  "pending",
  "account_type": "partna",
  "subdomain":    "thai-on-wok",
  "claim_token":  "UTjf97s-Kq2…"   // 43 chars, this response only
}

// 200 — re-served build: the key is ABSENT, not null
{ "build_id": "…", "build_state": "ready", "subdomain": "thai-on-wok" }
```

> **Why no token on the `200`:** minting on the dedupe path would let anyone who guesses a live `source_ref` fetch a working takeover capability for someone else's build. This is spec §5.4 and is deliberate — do not ask for it to be changed.

### `POST /api/claim`

Requires the Supabase JWT in `Authorization`. The email is read from the **verified token claim**, never from the body. Add `claim_token` to what you already send:

```jsonc
{
  "subdomain":        "thai-on-wok",
  "marketing_opt_in": false,
  "claim_token":      "UTjf97s-Kq2…"   // omit if you don't have one
}
```

Validation: `subdomain` required (max 63), `marketing_opt_in` boolean, `claim_token` nullable string (max 128).

Success is `200` with `professional` and `site` — byte-compatible with `/api/bootstrap`, so the dashboard redirect is unchanged.

### `GET /api/public/signup/builds/{build_id}`

The poll endpoint, unchanged. It **will never return `claim_token`**, permanently — it is a public opaque-UUID GET, so the plaintext must exist in exactly one response. If you lose the token from the create response, polling will not recover it.

## 4. Errors from `/api/claim`

All arrive as flat `{ "code": …, "message": … }`.

| Status | Code | Meaning |
|--------|------|---------|
| 404 | `CLAIM_NOT_FOUND` | No such site — **or** they can't prove it's theirs. Deliberately indistinguishable (see §5). |
| 409 | `ALREADY_CLAIMED` | Someone got there first. |
| 409 | `CLAIM_EMAIL_MISMATCH` | Reserved for a different email. **A token does not override this** (spec §6.2 — the token proves *invitation*, not *identity*). |
| 409 | `ACCOUNT_EXISTS` | They already own a site. |
| 409 | `EMAIL_ALREADY_REGISTERED` | That email is on another account. |
| 409 | `BUILD_FAILED` | The site never finished building. |
| 422 | `EMAIL_VERIFICATION_REQUIRED` | Session has no verified email — send them back through the OTP. |

## 5. Gotchas

**Check for the key, not for null.** When no token is minted, `claim_token` is **absent from the response**, not `null` (the resource runs `array_filter`). Use `'claim_token' in res`, not `res.claim_token !== null`.

**Your 404 copy becomes misleading.** Once enforcement is on, a legitimate owner who lost their token receives the same `404 CLAIM_NOT_FOUND` as a genuinely missing site. The collapse is deliberate — it stops a stranger sweeping handles to build a target list of claimable sites — but "Site not found" would dead-end a real customer. Use something closer to *"We couldn't verify this site is yours"* plus a support route.

**A failed claim does not burn the token.** It is consumed only on a **successful** claim (the burn is folded into the final `claimed_at` write, so every throw lands structurally before it). Wrong email, already-claimed, network error — the token stays valid. Safe to retry with the same one.

**One tab is usually enough, but not always.** The signup OTP is a **6-digit code typed into the same tab**, not a magic link, so the token normally survives the whole flow in `sessionStorage` keyed by subdomain. It will **not** survive closing the tab or switching device. Known gap; staff can re-issue via `POST /api/staff/builds/{build}/claim-token` (no UI for this yet).

**Never put the token in a URL.** Body only. A token in a query string lands in access logs, browser history, and the `Referer` of every asset the page loads.

**Never show it to the user.** It is a bearer secret, not a reference number. Don't render it, don't put it in a "save this" message, don't log it.

## 6. The related job — ManyChat `?t=` links

Separate from the above and also never done (outstanding since 2026-08-25).

Sites we build for leads over DM produce `…/claim/{subdomain}?t=<token>`. **Nothing currently reads that `t` parameter.** It needs the same treatment: pull it out, forward it in the claim body, and strip it from the address bar immediately so it doesn't persist in history:

```js
history.replaceState(null, '', location.pathname);
```

Same token mechanism, same endpoint, same rules. Spec: `docs/superpowers/specs/2026-08-25-manychat-claim-link-design.md` §6.3.

## 7. How to verify

**Happy path (flag off, today):** build a site on dev, confirm you captured a `claim_token`, claim it, confirm you land in the dashboard.

**Enforced behaviour (before the global flip):** ask Josh to enable the flag on dev. With your change in place a normal claim should still succeed; a claim with the token deliberately withheld should return `404 CLAIM_NOT_FOUND`.

---

## 8. Do not

- **Do not reintroduce a read-side "Dark Until Claimed" gate.** It shipped as `ee1c22784` (2026-08-24) and was reverted 2026-08-25 on owner decision because it defeats the pre-claim demo, which is the product pitch. A pre-account site is publicly routable pre-claim **by design**. Ownership proof belongs at the claim step only.
- **Do not** send the token in a URL, query string, or `Referer`.
- **Do not** wait for the backend flag before shipping — forwarding the token is inert while the flag is off, which is exactly what makes this safe to land independently.
