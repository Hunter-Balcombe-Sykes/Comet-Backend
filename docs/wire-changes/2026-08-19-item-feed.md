# Wire change — item feed (2026-08-19)

Backend-only execution; the frontends are told, not designed around
(spec `docs/superpowers/specs/2026-08-19-item-feed-design.md`, owner decisions
2026-08-19). Branch `feature/item-feed-2026-08-19`, not yet merged to
`development`.

## `GET /api/public/profiles/{handle}` and `GET /api/site/actions`

**Consuming repos:**
- `/api/public/profiles/{handle}` — partna-monorepo (`@partnaau/design-system`), public render
- `/api/site/actions` — Partna-App, authenticated dashboard (design page)

### Added: top-level `feed` key, both endpoints

Additive on both wire contracts. No existing key changed or removed; no
lockstep obligation — a frontend that ignores `feed` sees no other behaviour
change.

**Public payload** — `profile.feed`, beside `rankedActions`:

```jsonc
"feed": {
  "mode": "score",            // "manual" | "newest" | "score"
  "entries": [
    { "kind": "item",     "pool": "watch",  "itemId": "<content item id>", "score": 0.41 },
    { "kind": "category", "pool": "menus",  "collectionId": "<id>",
      "itemIds": ["<id>", "<id>"],          "score": 0.29 },
    { "kind": "item",     "pool": "shop",   "itemId": "<id>",              "score": null }
  ]
}
```

**Dashboard** — `GET /api/site/actions` gains the same shape plus the raw
stored list:

```jsonc
{ "pool": [...], "rankedActions": [...], "ordering": {...},
  "feed": { "mode": "newest", "entries": [...], "manual": [...] } }
```

- `entries` on the dashboard route is resolved through the **same**
  `publicPools()` call the public payload uses (`IndividualProfilePayloadBuilder::publicPools()`)
  — the preview and the lander cannot drift.
- `manual` is the stored raw `settings.manual_feed` list, unresolved, for the
  editor (`[]` when unset).

### Entry shape — references only, never item bodies

- `kind` is a discriminator: `item` ⇒ `itemId` (no `itemIds`/`collectionId`);
  `category` ⇒ `collectionId` + `itemIds`. Illegal combinations are
  unrepresentable.
- Join `itemId` against `pools.<pool>.items[].id`; `collectionId` against the
  pool's `collections` map. Both keys already exist on the wire — the feed adds
  no new resolvable ids.
- **Category entries come from `menus` and `services` only.** Shop also has
  `collections`, but shop products float individually as plain `item` entries
  (owner decision 2026-08-19). A menu/service item with no `collectionIds`
  floats too, rather than vanishing.
- Sources: every content pool except `reviews` (`watch`, `listen`, `media`,
  `events`, `services`, `shop`, `custom_links`, `menus`) — a review has no
  destination and the pool is exclusion-only by contract.
- `score` carries the blended popularity score in score mode, `null` in
  `manual`/`newest`.
- **The key is always present.** Empty `entries: []` when nothing resolves —
  never a missing key, never a 500.
- **Forward-compat / no dangling refs.** An entry only ever references an item
  present in the served `pools` payload on the same response. If pools ever
  truncate or paginate, the feed resolver filters to what actually shipped.
  Pinned by test (`tests/Unit/PublicSite/ItemFeedServiceTest.php` for
  resolution, `tests/Feature/Api/PublicSite/IndividualProfileControllerTest.php`
  for the public wire pin, `tests/Feature/Api/User/SiteManagement/UserSiteActionsEndpointTest.php`
  for dashboard-vs-public parity), not just documented.

### Write path — `PATCH /api/site`

Two new keys inside `settings` (JSON — no migration):

- `settings.feed_mode` — `manual|newest|score`, default `newest` when absent.
- `settings.manual_feed` — consulted only when `feed_mode = manual`; strict
  discriminated-union entries mirroring `manual_actions`: `item` requires
  `pool` + `ref` and rejects `items`; `category` requires `pool` + `ref` +
  `items` and its `pool` must be `menus` or `services`; `pool` must be one of
  the eight feed pools. Duplicate `(kind, pool, ref)` pairs 422. Cap
  `config('partna.feed.manual_max')`, default 100. The list REPLACES
  atomically on write — send the whole list every time.
- **Refs are not existence-checked at write time**, same stance as
  `manual_actions`: pool membership changes out from under the settings blob,
  so a write-time check would be a false guarantee. The resolver's
  drop-unknown-ref rule at read time is the sole enforcement point.

### Degradation

- No pools resolve (partial test env, DB blip): `feed: {mode, entries: []}`.
  Never a 500.
- Score lookup fails in score mode: falls open to newest ordering for that
  build, matching the analytics fail-open posture platform-wide.
- Stale manual refs drop silently at resolve time; a fully stale manual list
  yields an empty feed — strict curation working as specified.
- No new href surface: every entry is a reference, so every URL a rendered
  entry uses still comes off the pool item, which the pool wire already gates.
  No new SSRF/scheme concerns.
- Unclaimed (pre-account) sites serve the feed normally, same as every other
  payload engine.

## Cache lanes

Resolution happens inside `IndividualProfilePayloadBuilder`, next to
`resolveRankedActions()` — behind the existing 60s in-process payload cache
(keyed on `site.sites.updated_at`) and the edge cache. It inherits all three
cache invalidation lanes already wired through `PATCH /api/site` writes; no new
lane was needed.

## Frontend action

Render when ready. This is additive on both contracts with no removal and no
lockstep requirement — existing clients that don't read `feed` see identical
behaviour on every other key.
