## Q3 — These may be data-validation errors, not authorization errors

All 8 `abort(403)` calls follow the same pattern:

```php
// 1. Fetch all items owned by this professional (filtered by professional_id / site_id)
$allIds = Block::query()->where('professional_id', $pro->id)->where('site_id', $site->id)->pluck('id')->all();

// 2. Check submitted IDs are all in the owned set
foreach ($ids as $id) {
    if (! isset($allSet[$id])) {
        abort(403, 'One or more blocks do not belong to you');
    }
}
```

The check fires when a user submits an ID that their own query doesn't return — i.e., stale frontend state or a bug. This is not "user lacks permission to perform the action" (403) but "user submitted invalid data" (422). Using `authorizeForUser` for bulk input validation would require N+1 policy checks or an unusual policy shape.

**Question:** Should these be converted to 422 validation errors (removing the auth concern entirely) rather than routed through policies? Or is the intent to keep them as 403s via policy?
