### ⚠️ Finding — origin TTFB degrades badly under 50 concurrent (no threshold covers this)

This phase is the mirror image of 2a: `waiting` is essentially the whole of `duration`.

| metric | p50 | p95 |
|---|---|---|
| `http_req_duration` | 2911.4 | 4802.3 |
| **`http_req_waiting` (TTFB)** | **2907.9** | **4675.7** |
| `http_req_receiving` | 0.1 | 22.6 |

By status: **200s p50 4,342 ms / p95 5,774 ms**; **429s p50 2,897 ms / p95 3,483 ms**.

So the origin takes ~2.9 s merely to *reject* a request it has already decided to throttle, and
~4.3 s to serve one. Throughput collapsed to 15.6 req/s at 50 VUs.

This is well-controlled evidence, not a client artefact: **the same machine at the same 50 VUs
measured 239 ms p95 TTFB against the edge minutes earlier**, and `blocked`/`connecting` are ~0
here. It is not Postgres either — DB connections were flat and idle throughout.

### Follow-up investigation (same day): the container saturates at ~17 req/s

A concurrency ladder on `spike-origin.js` (20 s per rung) shows a classic saturation knee —
throughput flatlines while latency grows in direct proportion to the queue:

| VUs | throughput | p50 |
|---|---|---|
| 5 | 7.1 req/s | 359 ms |
| 10 | **17.4 req/s** | 551 ms |
| 20 | **17.4 req/s** | 1,150 ms |
| 50 | 14.8 req/s | 2,920 ms |

Past 10 VUs, extra concurrency buys **zero** throughput and converts entirely into wait. Little's
Law holds at every rung (17.4 × 0.551 ≈ 10; 17.4 × 1.15 ≈ 20; 14.8 × 2.92 ≈ 43), i.e. every VU is
in flight and the server drains at a fixed ~17/s.

**The origin's own access log confirms it is not merely queuing out of sight.** Captured *during* a
50-VU flood via `cloud env:logs partna development` (95 arrivals, all 429):

> server-reported `duration_ms`: **min 2,313 · p50 2,900 · p95 3,211 · max 3,318**

That matches the client's 2,920 ms p50 almost exactly, so the origin attributes the full ~2.9 s to
requests it ultimately **rejects**.

**It is container-wide, not specific to the throttled route.** `/api/health` — different route, no
rate limiter, no DB work — was probed during the same flood:

| `/api/health` | TTFB |
|---|---|
| idle control | **0.20 / 0.21 / 0.29 s** |
| during 50-VU flood | **2.33 / 2.42 / 2.38 / 2.38 / 2.51 s** (first 4.87 s) |

A ~12× dilation on an unrelated endpoint. So a single-IP flood of *rejected* requests degrades
**every** route on that container. Implication: the 429 is not cheap — it is returned by
`throttle:public-profile`, which is **route** middleware (`routes/api.php:178`) and therefore runs
only after PHP-FPM handoff, full Laravel bootstrap, and the global stack
(`ArmRedisRequestBreaker` → Redis, `SecureHeaders`, `AddPublicCacheHeaders`). Working back from the
~17 req/s ceiling, each rejected request costs roughly **60 ms of CPU** on this container.

Cheapest real fix is to reject *before* the origin — a Cloudflare-side rate limit — so hostile
volume never buys origin CPU at all. In-app reordering can only ever shave the tail of the cost,
not the bootstrap.

It passes the phase as written (`5xx==0`, `429>0`) because no threshold covers latency-under-flood.
Worth noting it is a **dev-sized** container with `usesHibernation: true`; prod sizing differs and
this number should not be projected onto prod. Suggested follow-up: decide whether rejection should
happen cheaper/earlier (edge or middleware ordering) so throttled traffic cannot occupy request
workers, and re-measure with prod-like sizing under `OPS-S4-3`.

## Phase 3b — queue saturation (Option A: direct dispatch, bypassing the HTTP limiter) ✅⚠️

The HTTP limiter caps intake at 120/min, so the queue can never be made deep through the front
door. Jobs were dispatched straight onto the queue via `cloud tinker development` instead — no
config change, and the limiter is irrelevant to the questions being asked (they are all about the
**worker**, not the request path).

**20,000 `RecordAnalyticsEventJob`s**, plus 3 canaries on `images` and 3 on `default`.

### Does the queue drain? Yes — linearly, at ~58–65 jobs/s

| time | `analytics` depth | `images` | `default` |
|---|---|---|---|
| 13:04:08 | 15,774 | **3** | 0 |
| 13:05:08 | 12,156 | **3** | 0 |
| 13:06:23 | 7,445 | **3** | 0 |
| 13:07:31 | 3,159 | **3** | 0 |
| 13:08:18 | 246 | **3** | 0 |
| 13:08:40 | **0** | **0** | 0 |

Dispatch ran at 291 jobs/s; drain held a steady ~58–65/s with no degradation as depth fell. 20,006
jobs cleared in ≈5.7 minutes. Depth never ran away.

### Zero loss, zero failures

`analytics.site_visits` went 3,503 → **23,509** = exactly +20,000 +6 canaries. `failed_jobs` stayed
at **2 for the whole run**, and both were *this session's own* test artefacts (queued closures
dispatched from tinker at 13:01:13, which fail because `laravel/serializable-closure` cannot reflect
eval'd source). **No `RecordAnalyticsEventJob` failed.** Both records were deleted afterwards.

### ⚠️ Cross-queue starvation is REAL and reproducible

`supervisor-1` is `balance => false`, `maxProcesses => 2` on dev (confirmed at runtime, not just in
the file), draining ten queues in **strict priority order**:

```
moderation_high, default, cloudflare, cache-warm, analytics, images, streaming,
platform_refresh, platform_connect, cloudflare_bulk
   ↑ position 2                        ↑ position 5   ↑ position 6
```

With `balance => false`, one `queue:work` drains that list top-down, so anything **below** a busy
queue waits for it to empty. Measured exactly that:

- **`default` (priority 2, above analytics)** — drained **immediately**, unaffected by the backlog.
- **`images` (priority 6, below analytics)** — **stuck at 3 for the entire ~4.5-minute drain**, and
  cleared only in the same sample where `analytics` reached 0.

So a burst of analytics traffic **stalls `images`, `streaming`, `platform_refresh`,
`platform_connect` and `cloudflare_bulk` for as long as the burst takes to clear**. At the measured
58/s, a 1-hour visitor spike of ~200k beacons would stall image processing for roughly an hour.
This is by design (the config comments spell the ordering out) but its blast radius had never been
measured. It is a **latency** problem, not a correctness one — nothing is lost, only delayed.

### The web tier is NOT affected

Probed during the backlog: `/api/health` **142–366 ms** (normal). Workers run on a physically
separate instance (`Worker cluster`, `flex-2gb`) from the app (`App`, `flex.g-1vcpu-512mb`), so
queue depth costs the public site nothing.

### Not measured

**Worker memory could not be read directly.** The Cloud CLI exposes no metrics command, and a probe
job cannot be injected without deploying code. Indirect evidence only: `supervisor-1` held steady at
**2 processes across every sample** during the drain with no churn, no failures, and no throughput
decay — none of which is what a leaking worker approaching the 256 MB restart ceiling looks like.
"Worker memory recovers" is therefore **still not directly verified**.

## ⚠️ Correction to the Phase 2b caveat: production is sized IDENTICALLY

The 2b finding above was hedged with "dev-sized container; do not project onto prod". That hedge was
wrong, and `cloud instance:list` settles it:

| environment | app instance | scaling | replicas |
|---|---|---|---|
| development | `flex.g-1vcpu-512mb` | **none** | min 1 / max 1 |
| **production** | **`flex.g-1vcpu-512mb`** | **none** | **min 1 / max 1** |

Production runs the **same single 1-vCPU / 512 MB replica with autoscaling off**. That also explains
the ~17 req/s ceiling exactly: one core ÷ ~60 ms CPU per request ≈ 17/s — the arithmetic and the
measured knee agree.

The implication is that **the 2b behaviour should be expected to reproduce on production**: one IP
can drive origin TTFB to seconds for every visitor, and there is no autoscaling to absorb it. This
was *not* tested against prod — load-testing prod is explicitly out of scope here (`OPS-S4-3`) — so
this is an inference from identical sizing, not a measurement. It raises the priority of a
Cloudflare-side rate limit, which rejects at the edge and never buys origin CPU.
