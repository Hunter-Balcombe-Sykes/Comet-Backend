## P1 — Fix before pilot launch

- [ ] **#RANK-1** · P1 — The anti-thrash `rank` is written for every action row but never read; page order and smart action fill both re-derive order from raw score
    - **Where:** app/Services/Analytics/ContentPopularityReader.php:75-89 (`pageRanksFromActions`), app/Site/Actions/ActionSlots.php:70-72 (`order`, smart branch)
    - **Affects:** Every site using `smart`/`newest` page order or `smart` action-slot fill — i.e. the primary lander nav and the action rail on any site that hasn't opted into fully manual ordering.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Have `actionScoresForSite()` (or a new sibling reader) select and return `rank` alongside `score`, keyed by content_key.
        - Change `pageRanksFromActions()` to sort by the stored `rank` ascending instead of `arsort()`ing raw `score`.
        - Change `ActionSlots::order()`'s smart branch to compare by the stored rank (scored-before-unscored, then rank asc) instead of `$sb <=> $sa` on raw score.
        - Add a regression test: two action rows whose blended scores differ by <10% (the `RANK_SWAP_THRESHOLD` in `ActionScorer::rankWithHysteresis`) must keep the previous-run rank order when read back through `pageRanksFromActions()`/`ActionSlots::order()`.
    - **Technical:** `ActionScorer::computeForSite()` (and the mirrored logic in `ComputeContentPopularityScores::computeActions()`) writes both `score` and `rank` to `analytics.content_popularity_scores` for `content_type='action'`, where `rank` is produced by `rankWithHysteresis()` — a previous-rank-seeded bubble sort that only lets a candidate overtake the incumbent above it when its blended score beats it by >10%. This is the class's entire stated purpose ("anti-thrash"). But `ContentPopularityReader::forSite()` — the only other action-row reader — explicitly excludes `content_type='action'` (`where('content_type', '!=', ActionScorer::CONTENT_TYPE)`), and `actionScoresForSite()` selects only `content_key, score`, never `rank`. Both downstream consumers — `pageRanksFromActions()` (`arsort($pages)` over raw score) and `ActionSlots::order()`'s smart branch (`$sb <=> $sa` over raw score) — therefore recompute a fresh, ungated ordering on every read. The stored `rank` column for action rows is written on a ~15-minute cron cadence (`analytics:compute-popularity`) and then never consulted by anything. This isn't a rare edge case: any site with ordinary traffic will produce blended-score deltas under 10% between consecutive scoring runs routinely, so page nav and the action rail will reorder on cadence even though the scoring layer was specifically built to prevent exactly that.
    - **Plain English:** We built a "steadiness" rule so the buttons and page links on someone's site don't shuffle around every time a tiny bit of new traffic comes in — a page only jumps ahead of another if it's clearly, meaningfully more popular. That rule computes and saves a stable order, but the code that actually decides what order to *show* on the site ignores the stable order and just re-sorts by the raw, jittery number instead. So the steadiness feature exists, runs, and gets thrown away — visitors can still see the nav bar or action buttons reshuffle for no real reason, on basically every scoring refresh.
    - **Evidence:**
        ```php
        $scores = $this->actionScoresForSite($siteId);
        $pages = [];
        foreach ($scores as $id => $score) {
            if (str_starts_with($id, 'page:')) {
                $pages[substr($id, 5)] = $score;
            }
        }
        arsort($pages);
        $out = [];
        $rank = 1;
        foreach (array_keys($pages) as $pageId) {
            $out[$pageId] = $rank++;
        }
        ```
        ```php
        usort($candidates, static function (array $a, array $b) use ($scores): int {
            $sa = $scores[$a['id']] ?? null;
            $sb = $scores[$b['id']] ?? null;
            if ($sa !== $sb) {
                if ($sa === null) {
                    return 1;
                }
                if ($sb === null) {
                    return -1;
                }

                return $sb <=> $sa;
            }
        ```

## P2 — Should fix

- [ ] **#RANK-2** · P2 — Duplicate within-category pool lock positions pass validation and one lock is silently dropped
    - **Where:** app/Http/Requests/Concerns/SiteOrderingValidationRules.php:120-136 (`poolLockPositionsRule`); app/Site/Pools/PoolOrdering.php:56-68 (`applyLocks`)
    - **Affects:** Owners using per-category "Lock in position" on menus or services. A settings write containing two locks at the same position inside the same category is accepted, and one silently loses its lock.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - For category pools, validate distinct `(category, position)` pairs — this requires resolving each locked item's home category (as `ActionCandidates`/`PoolOrdering::homeCollection` already do) at validation time, not just skipping the distinct-position check outright.
        - Alternatively, accept the current permissive validation but make `PoolOrdering::applyLocksPerCollection()` reject (not silently drop) a duplicate-position lock within one bucket, and thread that back to the response so the dashboard can tell the owner which lock didn't apply.
        - Add a unit test for `PoolOrdering::applyLocksPerCollection()` covering two locks in the same bucket at the same position.
    - **Technical:** `poolLockPositionsRule()` intentionally returns early for category pools (`menus`/`services`) because positions there are per-category, not global — two different categories may legitimately each hold a `#0`. But the early return also skips checking whether two locks target the *same* category at the same position, which the method's own docblock treats as invalid ("a position is the index within the item's category"). Downstream, `PoolOrdering::applyLocks()` (invoked per-bucket by `applyLocksPerCollection()`) resolves a position collision with `! isset($placed[$lock['position']])`, so the second lock for that position is simply skipped. Unlike `ActionSlots::resolve()`, which returns an explicit `unavailable` list for slots it couldn't place, `PoolOrdering::applyLocks()`/`applyLocksPerCollection()` return only the reordered item list — there is no signal anywhere in this path that a submitted lock failed to apply, for this or any other reason.
    - **Plain English:** For menus and services, an owner can "pin" a dish or a service to a specific spot inside its category. The form correctly allows position 1 in two *different* categories, but it also currently allows position 1 twice inside the *same* category — that should be rejected, but isn't. The system then quietly keeps one pin and throws the other away, with no message telling the owner that happened.
    - **Evidence:**
        ```php
        if (isset(ItemFamily::CATEGORY_FAMILIES[$pool])) {
            return;
        }
        ```
        ```php
        if (isset($byId[$lock['id']]) && ! isset($placed[$lock['position']])) {
            $placed[$lock['position']] = $lock['id'];
        }
        ```

## P3 — Nice to have

- [ ] **#RANK-3** · P3 — Pool locks have no `unavailable` reporting at all, unlike action slots
    - **Where:** app/Site/Pools/PoolOrdering.php:56-68 (`applyLocks`), :95-146 (`applyLocksPerCollection`); app/Site/Pools/PoolResolver.php (`assemble`, call site)
    - **Affects:** Owners whose pool locks reference an item that's later removed, excluded, or disconnected — the dashboard has no way to surface "this lock stopped applying."
    - **Effort:** M (~2–3h)
    - **What to do:**
        - Change `applyLocks()`/`applyLocksPerCollection()` to return `{items, unavailable}` (mirroring `ActionSlots::resolve()`'s contract) instead of a bare item list.
        - Thread the `unavailable` list through `PoolResolver::assemble()`'s return shape and, where useful, into the dashboard-facing pool payload.
    - **Technical:** `ActionSlots::resolve()` explicitly tracks and returns `unavailable` slot ids (spec §5.3) so the dashboard can tell an owner "this lock's item is gone." `PoolOrdering::applyLocks()` and `applyLocksPerCollection()` have no equivalent — a lock skipped because its id isn't in `$byId`/the bucket, or because it collided with another lock's position (#RANK-2), is dropped with no trace anywhere in the return value. `PoolResolver::assemble()` calls these functions and only consumes the reordered `$selection`, so this information is unrecoverable by the time it reaches any caller.
    - **Plain English:** When someone pins an item on their site's nav, we already have a way to tell them "that pin stopped working." Pool locks — the equivalent feature for menu and shop categories — don't have that at all, so if a pinned dish gets removed, the owner's layout quietly changes shape with no warning that their pin fell off.
    - **Evidence:**
        ```php
        public static function applyLocks(array $items, array $locks): array
        {
            if ($locks === [] || $items === []) {
                return $items;
            }
        ```
