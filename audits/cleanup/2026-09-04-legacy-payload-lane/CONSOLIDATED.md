## P2 — Should fix

- [x] **#LEGACY-1** · P2 — Superseded public-site payload lane still wired alongside the canonical profile endpoint
    - **Where:** app/Http/Controllers/Api/PublicSite/PublicSiteController.php:1-118; app/Services/Cache/SiteCacheService.php:47-63 (`buildPayloadFromDb`); app/Models/Views/PublicSitePayload.php; routes/api.php:113; routes/api/publicSite.php:25
    - **Affects:** Backend API-surface clarity and maintenance load; any real external consumer still on this lane gets an older, pre-pools payload shape (no `profile.pools.*`, no unified actions) that has visibly drifted from the canonical lane.
    - **Category:** (1) Duplicate public surface / (2) Superseded reader/writer still wired
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Confirm with the Astro Worker / partna-pages front-end (and any mobile client) that `GET /api/public/site` and `GET /api/public/site-by-slug` are no longer called.
        - Delete `PublicSiteController`, its two route registrations, `SiteCacheService::buildPayloadFromDb()` / `getPublicSitePayload()` / `warmSiteCache()`, the `PublicSitePayload` Eloquent view model, and the `site:public:*` / `site:payload:*` cache-key generators.
        - Remove the individual-site half of `WarmPublicSiteCacheJob`'s dual-warm (`$siteCache->warmSiteCache($subdomain)` call) once the lane is gone — its own docblock already says that warm is dead weight for individuals.
    - **Technical:** The canonical lane is `GET /api/public/profiles/{handle}` → `IndividualProfileController::show()` → `IndividualProfilePayloadBuilder`. The superseded lane still reads the `site.public_site_payload` DB view through the `PublicSitePayload` Eloquent view model and hand-assembles a raw array in `SiteCacheService::buildPayloadFromDb()`, bypassing the Resource/Builder layer the canonical path enforces. `SiteCacheService` itself documents this as legacy: *"LEGACY PATH NOTE (audit finding API-2, safe subset): This method hand-assembles a raw array for GET /api/public/site and GET /api/public/site-by-slug (served by PublicSiteController). Those routes bypass the Resource layer enforced by the newer IndividualProfileController → IndividualProfileResource path... Decommissioning requires confirming with the Astro Worker / front-end."* Stronger corroboration than DeepSeek cited: `app/Jobs/Cache/WarmPublicSiteCacheJob.php` carries its own dated note — *"Audit #12: for individuals, the legacy SiteCacheService::warmSiteCache populates a cache key that visitors of `<handle>.partna.au` never read — they hit the §28.8 endpoint (IndividualProfileController)"* — and the job now warms BOTH keys defensively rather than removing the dead one. `PublicSiteController::showByHeader()`'s own comment additionally ties it to a "Next.js proxy" for path-based routing, an architecture CLAUDE.md no longer describes (current architecture is Cloudflare Worker + Astro `@partnaau/design-system`), reinforcing that this is a residual lane from an earlier frontend generation, not the live one. Canonical-lane grep: `grep -rn "IndividualProfilePayloadBuilder" app/Http/Controllers/Api/PublicSite/IndividualProfileController.php` → wired at the `/public/profiles/{handle}` route. Superseded-lane grep: `grep -rn "PublicSiteController::class\|buildPayloadFromDb\|public_site_payload" app routes` → still bound at `routes/api.php:113` and `routes/api/publicSite.php:25`, with no confirmed external consumer beyond the unverifiable Astro/mobile claim in the code comment itself. Removal is **blocked on frontend confirmation** (the code's own docblock states this precondition; do not delete without it).
    - **Plain English:** There are two different machines answering "what does this person's page look like?" The official front door is the newer one; the old machine is still plugged in "just in case" and even its own maintenance notes say real visitors never walk through it — but nobody has confirmed that for the phone app or any outside partner that might still be calling it. Turn the old machine off only after that confirmation comes back.
    - **Evidence:**
        ```php

         * Returns null (with a short-lived sentinel cached) when the subdomain has no
         * published site in the view.
        ```

- [x] **#LEGACY-2** · P2 — Dead domain-scoped public route group duplicates flat customer-lead, enquiry, and subscribe endpoints
    - **Where:** routes/api/publicSite.php:20-32 (domain group); routes/api.php:165, 232, 235 (flat siblings)
    - **Affects:** Route-list clarity and maintainer time only — the domain group is documented as unreachable in production, so no live traffic differentiates behavior.
    - **Category:** (1) Duplicate public surface
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Delete the `{subdomain}.partna.au/public/customers`, `/public/enquiry`, and `/public/subscribe` route registrations from `routes/api/publicSite.php`'s domain group.
        - Keep the flat siblings (`routes/api.php:232`, `:235`, `:165`) and their existing test coverage untouched.
        - Leave the domain group's `/site` route alone — it is a separate finding (#LEGACY-1) with its own confirmation gate.
    - **Technical:** `routes/api/publicSite.php` registers `POST /customers`, `/enquiry`, and `/subscribe` under a `{subdomain}.{public_domain}` domain group. The file's own comment states the group is provably unreachable in production: *"this domain group is unreachable in production anyway — the Worker forwards every *.partna.au request to the pages app (measured 2026-08-05, SIGNUP-7)."* Canonical-lane grep: `grep -n "public/customers\|public/enquiry\|public/subscribe" routes/api.php` → flat siblings at lines 232, 235, 165, with **identical middleware stacks** to the domain-group versions (`['lead.log','throttle:leads','bot.token:lead']`, `['lead.log','throttle:leads','bot.token:enquiry']`, `['throttle:public-subscribe','bot.token:subscribe']` respectively — verified byte-for-byte against `routes/api/publicSite.php:26,30,33`), so there is no middleware-bypass concern, only route-list duplication. Superseded-lane grep: `grep -n "domain.*partna\|unreachable in production" routes/api/publicSite.php` → the domain group and its own retirement note. Removal is **safe now** — the file's comment already measured unreachability, and the flat routes it points to already carry test coverage.
    - **Plain English:** We have a second, unused set of doors for customer messages, enquiries, and newsletter sign-ups bolted onto an old subdomain entrance. The building's own floor plan already notes that entrance is dead in production. Removing the extra doors from the map stops someone from wasting time maintaining or "fixing" a door nobody can walk through.
