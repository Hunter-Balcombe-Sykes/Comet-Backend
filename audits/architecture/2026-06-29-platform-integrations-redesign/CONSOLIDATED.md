- [x] **#SEC-1** · P1 — Dropped `platform` CHECK has no explicit app-level replacement; `PlatformInRegistry` is dead code
    - **Where:** `supabase/migrations/20260629120000_drop_platform_connections_check.sql`; `app/Rules/PlatformInRegistry.php` (referenced only by `tests/Feature/Platforms/Registry/PlatformInRegistryRuleTest.php`)
    - **Affects:** Data integrity of `site.platform_connections.platform`; compounds with SEC-2 to become a public data-exposure path.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Enforce the registry as the write-time gate explicitly. Preferred: a `saving` guard on the `IntegrationConnection` model — `abort_unless(app(\App\Services\Platforms\Registry\PlatformRegistry::class)->has($this->platform), 422)` (or throw) in a `booted()` saving hook — so any write of an unregistered `platform` is rejected the way the DB CHECK used to reject it.
        - Add a feature test that asserts persisting an unregistered platform value is rejected (the test the dropped CHECK never had).
        - Decide whether `PlatformInRegistry` stays as the FormRequest rule (wire it where a `platform` value is user-influenced — today only `RefreshController`'s route param, already gated) or is folded into the model guard. Don't leave it dead.
    - **Technical:** The CHECK was dropped (commit `c3ead5f1`) on the premise "the registry is now the gate." Verified true for *reads/refresh/connect-routing* (`GenericPlatformController::descriptor()` 404s on unknown slugs; `RefreshController` gates on `registry->isRefreshable()`), but **no write path validates `platform` against the registry**. `grep -rn "PlatformInRegistry" app/` returns only the class definition. Every current write happens to source `platform` from a hardcoded constant / route default / detected value, so it is safe *today* — but the protection is emergent, not enforced, and the migration comment over-claims that `RegistryCoverageTest` does the CHECK's job (it asserts registry *contents*, not write constraint).
    - **Plain English:** The database used to have a built-in bouncer that rejected any connection tagged with a platform name it didn't recognise. That bouncer was removed on the promise that the app's own list would do the same job — but the app never actually checks the list when *saving* a connection. Right now nothing bad gets through because every save hard-codes a known name. But the safety net is gone and the replacement was never switched on, so one future code path that lets a user influence the platform name would slip an unknown value straight into storage. Add the check back in code so the guarantee is real, not lucky.
    - **Evidence:**
        ```sql
        -- supabase/migrations/20260629120000_drop_platform_connections_check.sql
        --   * tests/Feature/Platforms/Registry/RegistryCoverageTest.php asserts the registry
        --     key set == the platforms the app stores — the job the CHECK used to do.
        ALTER TABLE site.platform_connections
            DROP CONSTRAINT IF EXISTS platform_connections_platform_check;
        ```
        ```php
        // app/Rules/PlatformInRegistry.php — defined, never referenced in app/ (grep: class def only)

            $fail('The selected :attribute is not a supported platform.');
        ```

- [x] **#SEC-2** · P1 — `PublicIntegrationConnectionResource::filterPayload` fails OPEN for an unknown platform
    - **Where:** `app/Http/Resources/Platforms/PublicIntegrationConnectionResource.php:121-130`
    - **Affects:** Public, CDN-cached sitepage payload (`<handle>.partna.au`) — the unauthenticated render surface.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Fail **closed**: when a platform has no allowlist entry, log the warning and return `[]` (an empty object on the wire), never the raw payload.
        - Add a test asserting an unrecognised platform yields no payload keys publicly.
    - **Technical:** `filterPayload()` allowlists per platform via `array_intersect_key`, but the `$allowed === null` branch returns the entire stored `$payload` verbatim. Benign for the 36 registered platforms (all have allowlist entries), but it is the amplifier on SEC-1: any payload stored under an unrecognised platform string leaks in full to the public wire, including internal keys (`_folder`, `source`, `sourceUrl`). The correct default for a public serializer is fail-closed.
    - **Plain English:** When the public website builds a visitor-facing page, it has a list of exactly which fields each connection is allowed to show. If it ever meets a connection type that isn't on that list, instead of showing nothing it currently shows *everything* stored for it — including private internal bookkeeping. No real connection triggers this today, but "show everything when unsure" is the wrong instinct for a public page. Flip it to "show nothing when unsure."
    - **Evidence:**
        ```php
        // app/Http/Resources/Platforms/PublicIntegrationConnectionResource.php:121
        $allowed = self::ALLOWLIST[$platform] ?? null;
        if ($allowed === null) {
            // A new platform shipped without an allowlist entry — fail OPEN (never
            // break public rendering) but surface the gap so it gets filled.
            Log::warning('PublicIntegrationConnectionResource: no allowlist for platform', [
                'platform' => $platform,
            ]);

            return $payload;
        }
        ```

- [x] **#CAP-1** · P2 — Capability gate `availableFor()` is consulted at exactly one site; spec's "every dispatcher/route/render checks this" unmet
    - **Where:** `app/Services/Platforms/Registry/PlatformDescriptor.php:203-206` (definition, returns `true`); sole call site `app/Http/Controllers/Api/Platforms/GenericPlatformController.php:54`
    - **Affects:** Future paid-tier / account-type gating; the public render path and ~20 bespoke connect flows would silently bypass it.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Either (a) route the bespoke `connect()` flows (Instagram/Fresha/Shop/GoogleBusiness/Events/CustomLinks/Square/Spotify/…) and `PublicIntegrationController::show` through a shared capability checkpoint now (cheap, behaviour-neutral while it returns `true`), OR
        - (b) explicitly accept it as a not-yet-wired seam and add a test/comment documenting that the single call site is intentional — so a future predicate isn't shipped into a half-wired gate.
        - Preferred long-term: move the gate into `ManagesIntegrationConnection::writeConnection()` so every connect path inherits it.
    - **Technical:** `grep -rn "availableFor" app/` returns one production call. `availableFor()` returns `true` for everyone, so there is no live bug — but the spec (§9) wants central checkpoints at connect / dashboard list / public render. As written, the first real predicate (paid tier) would be bypassed by every bespoke connect and the public endpoint.
    - **Plain English:** There's a single switch meant to decide "is this integration available to this user?", and the plan was for every entry point to consult it. Right now only one of roughly twenty entry points actually does, and the switch is currently set to "yes" for everyone so nothing's broken. The danger is the day someone wires real logic into that switch (e.g. "paid plans only") — most of the app won't be looking at it, and the rule will quietly do nothing. Decide now: wire it everywhere, or clearly mark it as not-yet-active.
    - **Evidence:**
        ```php
        // app/Services/Platforms/Registry/PlatformDescriptor.php:203
        public function availableFor(User $user): bool
        {
            return true;
        }
        ```
        ```php
        // app/Http/Controllers/Api/Platforms/GenericPlatformController.php:54 (the only caller)
        abort_unless($descriptor->availableFor($user), 403);
        ```

- [x] **#ARCH-1** · P3 — `refreshable` is expressed in two places that could drift
    - **Where:** `app/Services/Platforms/Registry/PlatformDescriptor.php:193-198` (`refreshStrategy()`); `app/Services/Platforms/Registry/PlatformRegistry.php:44-47` (`refreshable()`)
    - **Affects:** Robustness of the cron refresh selection (no current bug).
    - **Effort:** S (~0.5–1h)
