## P1 — Fix before pilot launch

- [ ] **PRIV-1** · P1 — GDPR deletion-audit export discloses staff members' IP address and browser fingerprint to the data subject
    - **Where:** app/Services/User/DataExport/DataExportPayloadBuilder.php:792-812 (`streamDeletionAudit()`); app/Services/User/AccountDeletionService.php (`logAuditEvent()`, `adminInitiate()`)
    - **Affects:** Partna staff members who process admin-initiated account-deletion requests (the GDPR support flow `adminInitiate()` exists specifically for) — their IP address and User-Agent string become part of the professional's own permanent audit trail and are later handed to that professional in their own Article-15 data export.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - In `streamDeletionAudit()`, redact `ip_address`/`user_agent` for any row whose `actor_type` is not `UserDeletionAuditEntry::ACTOR_TYPE_PROFESSIONAL` — i.e. keep them only for self-service `requested`/`confirmed`/`cancelled` events, where the IP/UA genuinely belong to the exporting user.
        - Mirror the pattern `streamHandleChangeLog()` already uses one method above it in the same file: drop the raw fields and emit a coarse `actor_kind` (`self` / `staff` / `system`) instead of the identifying values.
    - **Technical:** `AccountDeletionService::adminInitiate(User $professional, string $staffActorId, string $staffActorHandle, string $reason, bool $overrideObligations, Request $request)` forwards the **staff member's own** `$request` into `executeConfirmation()`, which calls `logAuditEvent($professional, $event, $request, ...)`. `logAuditEvent()` unconditionally captures `'ip_address' => $request?->ip()` and `'user_agent' => $request?->userAgent()` — for an admin-initiated row, that is the staff member's IP/UA, not the professional's. `streamDeletionAudit()` then exports `ip_address` and `user_agent` for every row matching the professional's `user_id`, with no actor-type branch. The FK on `audit.user_deletion_audit` is `ON DELETE SET NULL` (not CASCADE), so these rows are the intended long-term Article-15 disclosure surface — meaning this is not a transient bug, it fires every time support closes out an admin-initiated deletion. Compare with `streamHandleChangeLog()` two methods below, in the same file, which already solves exactly this problem for a structurally identical actor-provenance column (`actor_id`) by mapping it to a coarse `actor_kind` before export.
    - **Plain English:** When a Partna support staff member helps someone delete their account — say, in response to a formal privacy request — the system quietly records that staff member's own internet address and browser details in the account's permanent history. Months later, when that same person downloads "everything Partna knows about me," our own employee's technical fingerprint is bundled into the file we hand them — a person who never agreed to have their information shared with a stranger. This is a real disclosure of one person's data to another, every single time staff processes this kind of request. The fix is small: only include that technical detail when it's the account owner's own information, exactly like we already do for username-change history.
    - **Evidence:**
        ```php
        public function adminInitiate(
            User $professional,
            string $staffActorId,
            string $staffActorHandle,
            string $reason,
            bool $overrideObligations,
            Request $request,
        ): array {
            ...
            $deletesAt = $this->executeConfirmation(
                $professional,
                UserDeletionAuditEntry::EVENT_ADMIN_INITIATED,
                $request,

            );
        ```

        ```php
                ...
        ```

## P2 — Should fix

- [ ] **PRIV-2** · P2 — Nine GDPR export sections stream unfiltered table columns with no explicit allowlist
    - **Where:** app/Services/User/DataExport/DataExportPayloadBuilder.php — `streamCustomers()`, `streamServices()`, `streamServiceCategories()`, `streamNotifications()`, `streamNotificationReceipts()`, `streamConfirmationPreferences()`, `streamNotificationPreferences()`, `streamNotificationPolicies()`, `streamDesignKit()`
    - **Affects:** Users receiving GDPR exports — a future migration adding an internal token, staff-only note, or operational hash to any of these nine tables would silently appear in every subsequent export with no code-review gate to catch it.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Add explicit `->select([...])` allowlists to all nine methods, mirroring the pattern already used by `streamFeedback()`, `streamEnquiries()`, `streamMedia()`, `streamAudit()`, and `streamHandleChangeLog()` in the same file — each with a short comment naming any deliberately excluded column and why.
        - Extend `tests/Feature/Security/DataExportCoverageTest.php` (already the house guard for this builder) with a check that every `DB::table(...)` call inside `DataExportPayloadBuilder` chains an explicit `->select()` — that test currently checks table *presence* and *erasure-path* coverage but has no assertion against bare `SELECT *` usage.
    - **Technical:** The disciplined export methods in this file (`streamFeedback`, `streamEnquiries`, `streamMedia`, `streamIntegrations`, `streamAudit`, `streamHandleChangeLog`, `streamEmailSubscriptions`, `streamEarlyAccessSignups`) all enumerate columns explicitly, several with inline comments explaining exclusions (technical fingerprints dropped, credentials withheld). The nine methods listed here instead call `$this->lazyRows()` on a bare `->where('user_id'/'site_id', ...)` builder, which Laravel compiles to `SELECT *`. Verified directly against the provided source: none of the nine has a `->select()` call. `tests/Feature/Security/DataExportCoverageTest.php` guards table-level presence (`COVERED_PII_TABLES`) and erasure-path completeness, but its `PII_MARKERS` list only flags email-shaped columns — it would not catch a new non-email column silently entering one of these nine `SELECT *` queries.
    - **Plain English:** Think of a filing cabinet where most drawers have a label listing exactly what's inside, but nine drawers just say "everything in here." The team has been careful about labeling the sensitive drawers — customer enquiries, feedback, audit history all explicitly list which fields go out and which are held back. But customer records, services, notifications, and site design settings are still wide open: whatever columns exist in the database get copied into every export, no review required. If someone adds an internal note field to the customer table next year, it will automatically show up in every customer's downloadable data file without anyone deciding that should happen. The fix is to label those nine drawers the same careful way the rest already are.
    - **Evidence:**
        ```php
        // Disciplined pattern — explicit allowlist, comments explain exclusions:
        private function streamFeedback(string $userId): Generator
        {
            return $this->lazyRows(
                DB::connection('pgsql')
                    ->table('core.feedback')
                    ->select(['id', 'user_id', 'reply_email', 'kind', 'severity',
                              'message', 'page_url', 'viewport', 'app_version',
                              'request_id', 'status', 'source', 'tags',
                              'internal_notes', 'created_at', 'updated_at'])
                    ->where('user_id', $userId)
            );
        }

        // Undisciplined — SELECT *, no guard against future column leakage:
        private function streamCustomers(string $userId): Generator
        {
            return $this->lazyRows(
                DB::connection('pgsql')
                    ->table('site.customers')
                    ->where('user_id', $userId)
            );
        }
        ```

- [ ] **PRIV-3** · P2 — `analytics.item_views` has no FK to `core.users`, so visitor IP/UA rows outlive an account by up to 90 days with a dangling reference to the deleted user
    - **Where:** supabase/migrations/20260709042911_create_item_views.sql:9-26 (table definition, no FK constraint); app/Services/User/AccountDeletionService.php:452-486 (`purge()` — no `item_views` step); app/Console/Commands/PurgeRawAnalyticsEvents.php (the retention job that eventually catches it)
    - **Affects:** Visitors to a professional's site whose IP hash and user agent sit in `item_views` rows still pointing at a hard-deleted `user_id` for up to 90 days after that professional's account is erased.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add a `purgeItemViewsPii(User $professional)` step to `AccountDeletionService::purge()`, alongside the existing explicit purge calls for other non-cascaded tables (`purgeFeedbackRows()`, `purgeCaseSignalPii()`), deleting `analytics.item_views` rows where `user_id = $professional->id`.
        - Add `'analytics.item_views'` to `AccountDeletionService::PURGED_PII_TABLES`.
    - **Technical:** The three older analytics tables (`site_visits`, `link_clicks`, `section_views`) carry `user_id uuid NOT NULL REFERENCES core.users(id) ON DELETE CASCADE` (confirmed in `supabase/migrations/20260526000000_baseline_standalone_user.sql`, column renamed `professional_id → user_id` by `20260527030000_rename_professional_to_user.sql`) — `forceDelete()` already erases these correctly with zero code changes needed. `analytics.lead_submissions` uses `ON DELETE SET NULL`, so Postgres itself severs the link to the deleted account at delete time, the same erasure shape the codebase already accepts for `moderation.case_signals` (`reporter_user_id = null`). `analytics.item_views` (added later, `20260709042911_create_item_views.sql`) is different: `user_id uuid` carries **no FK constraint at all** — the migration's own comment calls it "denormalized... nullable = fail-open." `forceDelete()` never touches it, and it is absent from `AccountDeletionService::PURGED_PII_TABLES`, so a deleted professional's `item_views` rows keep a literal, unerased reference to their UUID plus the visiting third party's `ip_hash`/`user_agent`. The gap is bounded, not indefinite: `app/Console/Commands/PurgeRawAnalyticsEvents.php` runs daily (`routes/console.php:66-71`) and deletes rows in `analytics.item_views` (and the other four analytics tables) older than `config('partna.analytics_raw_event_retention_days')` (default 90) regardless of owner status — so this is a "narrows an up-to-90-day exposure window to immediate" hardening fix, not an indefinite-retention gap, which is why it lands at P2 rather than P1.
    - **Plain English:** When someone deletes their Partna account, most of the visitor-traffic records tied to their old site are cleaned up automatically because the database is wired to do that. One table — the one tracking which products/menu items/gallery photos visitors looked at — was built without that automatic wiring, so it keeps a live pointer to the now-deleted account, plus the visiting stranger's IP address and browser info, for up to 90 days until a separate nightly cleanup catches it. It's not a permanent leak (the 90-day cleanup does eventually clear it), but it means a deleted account still has orphaned visitor data sitting around longer than it should. The fix is a few lines: explicitly clear this one table the moment the account is deleted, the same way we already do for a couple of other tables that needed the same manual handling.
    - **Evidence:**

        ```sql
            id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
            user_id      uuid,             -- site owner (denormalized; populated by controller, nullable = fail-open)

            item_type    text NOT NULL,
            item_id      text NOT NULL,
            ...
            ip_hash      text,
            user_agent   text,
            ...
        );
        ```
