Both DeepSeek drafts were checked against the real migration DDL and disproven — neither survives adjudication.

**#PARITY-1 (dropped) — "`DataExportAudit` transition methods call `update()` on an audit-schema table Postgres triggers may reject."** False premise. `supabase/migrations/20260526000000_baseline_standalone_user.sql:2333` grants `audit.data_export_audit` (then `core.data_export_audit`) full `SELECT, INSERT, UPDATE, DELETE` at baseline — it was never one of the three trigger-hardened append-only tables. Those three (`core.handle_change_log`, `core.staff_audit_log`, `core.auth_factor_events`) get an explicit `RAISE EXCEPTION ... 'is append-only'` trigger (baseline lines 286, 296) — `data_export_audit` gets none. `20260527010000_reorganize_schemas.sql` moved the table into the `audit` schema and a blanket schema-wide REVOKE briefly broke `markProcessing`/`markCompleted`/`markFailed`; that regression was already caught and fixed by `20260624000000_grant_update_data_export_audit.sql`, whose own commit message states the exact failure DeepSeek describes and re-grants `UPDATE` specifically because "reorganize_schemas... blanket-revoked UPDATE/DELETE on the entire audit schema, which (a) breaks DataExportAudit::markProcessing/markCompleted/markFailed." The current `->update()` calls in `DataExportAudit.php` are correct, intentional, and already covered by a targeted grant — citing commit-equivalent migration `20260624000000`.

**#PARITY-2 (dropped) — "Analytics models' `$timestamps = false` + missing `created_at` in `$fillable` relies on an unverifiable DB default."** DeepSeek explicitly hedged this at confidence 0.50 pending migration access. With migrations now in scope: `analytics.site_visits`, `analytics.link_clicks`, `analytics.section_views` (baseline, lines 1142/1173/1232) and `analytics.item_views` (`20260709042911_create_item_views.sql:25`) all declare `created_at timestamptz [NOT NULL] DEFAULT now()`. `analytics.lead_submissions` has no `created_at` column at all in the DDL — and correspondingly `LeadSubmission::$casts` never references `created_at`, so the model matches the schema exactly. Every write path in this class is safe; the DB defaults DeepSeek couldn't confirm do exist.

No other NOT NULL / CHECK / ENUM / FK issues were found in this file set. Notably checked and confirmed **clean**:
- `site.enquiries.status` is a native Postgres ENUM `site.enquiry_status ('new','read','replied','archived','spam')` (`20260527160000_enquiry_inbox.sql:23`) — `App\Enums\EnquiryStatus` carries exactly those five cases, and every `Enquiry` transition method (`markRead`/`markReplied`/`archive`/`markSpam`/`restoreToNew`) writes only allowed values.
- `site.blocks` pair-CHECK `blocks_group_type_check` (`20260701160000_blocks_group_type_pair_check.sql`) permits `('links','link')` and 15 named section types — `Block::GROUP_LINKS`/`GROUP_SECTIONS`/`TYPE_LINK` constants and the observers' referenced block types (`booking`, `services`, `public_contact`, `workplace`, `gallery`, `documents`) all fall inside the allowed set.
- `site.site_media.pool` CHECK (`gallery, content, design, product, brand_gallery, documents`) covers every `SiteMedia::POOL_*` constant in use.
- `audit.data_export_audit.status`/`email_delivery_status` CHECK sets match `DataExportAudit::STATUS_*`/`EMAIL_DELIVERY_*` constants exactly.
