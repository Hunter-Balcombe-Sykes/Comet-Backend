## P1 — Fix before pilot launch

- [ ] **MIG-1** · P1 — Backfill INSERT and DROP COLUMN auto-commit as separate statements — half-applied risk on `site.menu_items`
    - **Where:** supabase/migrations/20260701140100_menu_item_platforms_table.sql (entire file)
    - **Affects:** `site.menu_items` / `site.menu_item_platforms`. The dev DB (which per CLAUDE.md's "Laravel Cloud reality" note is the live DB serving both `dev-api.partna.au` and `api.partna.au` today) has 41 real legacy-shape items on one menu per this file's own comment — this is not a theoretical no-op backfill.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Wrap the `INSERT` and `ALTER TABLE ... DROP COLUMN` in a single `BEGIN`/`COMMIT` so they succeed or fail together.
        - Add `SET LOCAL lock_timeout = '2s'` before the `DROP COLUMN` so a blocked lock fails fast per `docs/migration-guidelines.md` §Lock and statement timeouts.
        - This is a safe edit to an already-applied file: per `docs/migration-guidelines.md` §"Editing already-applied migrations," Supabase tracks migrations by version timestamp, not content hash, so wrapping already-applied statements in a transaction is a no-op on dev (skipped, already recorded) and only changes behaviour on the next fresh apply — exactly the pending prod re-baseline.
    - **Technical:** The file has no `BEGIN`/`COMMIT` wrapper, so `CREATE TABLE`/`CREATE INDEX`, the `INSERT INTO site.menu_item_platforms ...` backfill, and `ALTER TABLE site.menu_items DROP COLUMN IF EXISTS platforms` each auto-commit independently. If `DROP COLUMN` fails or the deploy is interrupted after the `INSERT` commits, the migration is left half-applied (both the old JSONB column and the new relational rows exist). Worse, `site.menu_item_platforms` carries `UNIQUE (menu_item_id, platform)` with no `ON CONFLICT` clause on the `INSERT` — a retry of the whole file would fail immediately on that unique-constraint violation rather than cleanly resuming, requiring manual cleanup. Note this is a different failure class than `CONVENTIONS.md` §5 ("never backfill inside a migration transaction") warns about — that rule targets a *slow* full-table `UPDATE` inheriting a lock from a preceding DDL statement. Here the `INSERT` is bounded (one `CROSS JOIN LATERAL` over existing menu items, not a multi-million-row scan) and nothing precedes it that holds a lock, so wrapping it with the `DROP COLUMN` (itself metadata-only and fast) does not reintroduce that problem — it only buys atomicity.
    - **Plain English:** Imagine moving money from a safe to a bank vault: you carry the cash across the room first, then go back to close the safe. If something blocks you from closing the safe, the cash is already in the vault, but the safe is still open — two places now hold "the money," and running the whole move again just jams because the vault already has that cash logged. The fix is to make carrying the cash and closing the safe one atomic move, and to give up quickly and loudly if the safe door won't budge instead of standing there indefinitely.
    - **Evidence:**
        ```sql
        UNIQUE (menu_item_id, platform)
        ```
        ```sql
        INSERT INTO site.menu_item_platforms (id, menu_item_id, platform, pickup_price, pickup_url, delivery_price, delivery_url, created_at, updated_at)
        SELECT gen_random_uuid(), mi.id,
               e->>'platform',
               ...
        FROM site.menu_items mi
        CROSS JOIN LATERAL jsonb_array_elements(mi.platforms) AS e
        WHERE jsonb_typeof(mi.platforms) = 'array'
          AND e ? 'platform';

        ALTER TABLE site.menu_items DROP COLUMN IF EXISTS platforms;
        ```

- [ ] **MIG-3** · P1 — `DROP CONSTRAINT` and `ADD CONSTRAINT ... NOT VALID` auto-commit separately — momentary window with no CHECK active, on `site.sites` and `core.users`
    - **Where:** supabase/migrations/20260708140000_add_atlas_multipage_skeleton.sql, 20260708160000_remove_thread_sheet_skeletons.sql, 20260709041138_add_one_skeleton_id.sql, 20260710170000_skeleton_id_one_only.sql, 20260711000000_staff_account_type.sql, 20260712000000_retire_staff_account_type.sql
    - **Affects:** `site.sites.skeleton_id`/`architecture_id` (4 files) and `core.users.account_type` (2 files) — both canonical hot tables per this lens, both written continuously (pre-account site builds create `core.users` rows constantly; every dashboard save touches `site.sites`). This is unapplied on production, so it will run again during the gated prod re-baseline.
    - **Effort:** S (~1h for all 6 files)
    - **What to do:**
        - Wrap `DROP CONSTRAINT` + `ADD CONSTRAINT ... NOT VALID` in a single `BEGIN`/`COMMIT` in each file, matching the correct pattern already established elsewhere in this same migration set (`20260701160000_blocks_group_type_pair_check.sql`, `20260705120000`/`20260705120001`). Leave `VALIDATE CONSTRAINT` as a separate, un-transacted statement afterward — that part is already correct in all 6 files.
        - These are safe edits to already-applied dev migrations per the same version-timestamp reasoning as MIG-1/2 — hardens the pending prod re-baseline without touching dev's already-recorded state.
    - **Technical:** None of the 6 files wrap `DROP CONSTRAINT ... ; ADD CONSTRAINT ... NOT VALID;` in a transaction, so each statement auto-commits independently. Between the two commits, the table has **no CHECK constraint at all** on the affected column — a concurrent write (app bug, or an operator via the SQL editor) could insert a value outside the intended enum during that window. Because the constraint doesn't exist yet, that write succeeds silently; it would only surface later when `VALIDATE CONSTRAINT` scans and fails, aborting the migration in a confusing partially-applied state (constraint present but never validated) that requires manual cleanup. The correct pattern — DROP + ADD NOT VALID atomically, VALIDATE separately — is the established convention in this exact codebase (`supabase/migrations/CONVENTIONS.md` §2) and is demonstrably known and used correctly elsewhere in the same file set; these 6 files simply drifted from it.
    - **Plain English:** This is like changing a door lock — take the old lock off, walk to the toolbox for the new one, screw it on. For those few seconds the door has no lock at all. The right way is to have the new lock ready in your hand before removing the old one, so the door is never actually unlocked. In the database, that means removing the old rule and adding the new one (unvalidated) as one atomic step.
    - **Evidence:**
        ```sql
        -- 20260711000000_staff_account_type.sql (core.users — hot, continuously written):
        ALTER TABLE core.users DROP CONSTRAINT IF EXISTS users_account_type_check;

        ALTER TABLE core.users
            ADD CONSTRAINT users_account_type_check CHECK (account_type IN ('partna', 'business', 'staff')) NOT VALID;

        ALTER TABLE core.users VALIDATE CONSTRAINT users_account_type_check;
        ```
        ```sql
        -- 20260708140000_add_atlas_multipage_skeleton.sql (site.sites):
        ALTER TABLE site.sites DROP CONSTRAINT IF EXISTS sites_skeleton_id_check;

        ALTER TABLE site.sites ADD CONSTRAINT sites_skeleton_id_check
            CHECK (skeleton_id IN ('bento', 'dock', 'flick', 'deck', 'sheet', 'thread', 'atlas')) NOT VALID;
        ```

- [ ] **MIG-4** · P1 — `ADD COLUMN` + full-table `UPDATE` + `ADD CONSTRAINT`/`VALIDATE` combined in one transaction on `site.sites` — violates the codebase's own written convention
    - **Where:** supabase/migrations/20260701190000_promote_site_settings_columns.sql:1-52 (primary instance); same root-cause pattern also present in supabase/migrations/20260707030000_rename_skeleton_ids.sql and supabase/migrations/20260707120000_rename_skeleton_ids_bento_class.sql
    - **Affects:** `site.sites` — the single hottest table on the platform (public sitepage resolution, every dashboard save). Unapplied on prod today, so this exact sequence will re-run against whatever row count `site.sites` has at the gated re-baseline.
    - **Effort:** M (~2–4h) — requires splitting into the multi-file pattern, not a one-line fix
    - **What to do:**
        - Split each file per `docs/migration-guidelines.md` §"Full-table-scan data scrubs" and `CONVENTIONS.md` §5 ("Never backfill data inside a migration transaction"): file A does the fast `ADD COLUMN`/`DROP CONSTRAINT` DDL inside `BEGIN`/`COMMIT`; file B runs the `UPDATE` backfill **outside any transaction**; file C does `ADD CONSTRAINT ... NOT VALID` inside `BEGIN`/`COMMIT`; file D runs `VALIDATE CONSTRAINT` alone. This exact 3-4 file split is already the established pattern elsewhere in this migration set (`20260705120000`/`20260705120001`/`20260705120002`, whose own header comment documents doing precisely this split "so a blocked migration fails fast instead of queueing behind live traffic").
        - Add `SET LOCAL lock_timeout = '2s'; SET LOCAL statement_timeout = '10s';` to each DDL-bearing file per `docs/migration-guidelines.md` §"Lock and statement timeouts."
        - Safe to edit despite already being applied to dev (version-timestamp tracking; no-op on dev, hardens the fresh prod apply).
    - **Technical:** `site.sites.settings` is `jsonb DEFAULT '{}'::jsonb NOT NULL` (confirmed in the baseline), so `UPDATE site.sites SET ... WHERE settings IS NOT NULL` touches every row unconditionally. Because the file wraps `ADD COLUMN` (which briefly requires `ACCESS EXCLUSIVE`), the `UPDATE`, `ADD CONSTRAINT ... NOT VALID`, and `VALIDATE CONSTRAINT` all in **one** `BEGIN`/`COMMIT`, Postgres never releases or downgrades the `ACCESS EXCLUSIVE` lock acquired by the first `ADD COLUMN` — it is held for the entire transaction, meaning the full-table `UPDATE` scan and the constraint validation both run while **all** reads and writes to `site.sites` are blocked, not just concurrent writes. `docs/migration-guidelines.md` §"Full-table-scan data scrubs" documents this exact anti-pattern using `site.sites` as its own worked "avoid" example, and `CONVENTIONS.md` §5 gives the identical `ADD COLUMN` + `UPDATE` example verbatim as "BAD." The same combined-transaction shape (`DROP CONSTRAINT` + `UPDATE` + `ADD CONSTRAINT NOT VALID` in one `BEGIN`/`COMMIT`) recurs in `20260707030000` and `20260707120000`. Today's dev row count is tiny (`site.sites` was a "complete census" of 10 rows per `20260714200000`'s own comment) so the practical impact so far has been negligible, but per this lens's own framing, findings about deploy risk on migrations still unapplied to prod are elevated a tier until the re-baseline lands, and this pattern directly contradicts a rule the team already wrote down and follows correctly elsewhere.
    - **Plain English:** This migration is like repainting every room in a hotel while also locking every door in the building for the whole job — not just the room being painted. Right now the hotel has 10 rooms, so nobody notices. But the pattern assumes the hotel stays tiny forever. The team already figured out the right way to do this elsewhere in the same set of changes (paint one room, unlock the building, then check the paint later) — this file and two of its siblings just didn't get the memo.
    - **Evidence:**
        ```sql
        BEGIN;

        ALTER TABLE site.sites
          ADD COLUMN hero_title                  text,
          ADD COLUMN hero_subtitle              text,
          ...

        UPDATE site.sites SET
          hero_title                 = settings->>'hero_title',
          ...
        WHERE settings IS NOT NULL;

        ALTER TABLE site.sites
          ADD CONSTRAINT sites_booking_mode_check
          CHECK (booking_mode IS NULL OR booking_mode IN ('manual','none')) NOT VALID;

        ALTER TABLE site.sites VALIDATE CONSTRAINT sites_booking_mode_check;

        COMMIT;
        ```

## P2 — Should fix

- [ ] **MIG-5** · P2 — `VALIDATE CONSTRAINT` runs in the same transaction as `ADD CONSTRAINT ... NOT VALID` — wastes the two-step optimization
    - **Where:** supabase/migrations/20260701220000_promote_gb_apify_status_placeid.sql:11-19
    - **Affects:** `site.platform_connections` (not a canonical hot table, but real integration-sync traffic). Today's practical impact is nil — every existing row is guaranteed `NULL` for the brand-new column, so the scan is trivially fast regardless — but the pattern defeats the point of the split for any future constraint added the same way on this file.
    - **Effort:** S (~0.5h)
    - **What to do:**
        - For any future migration following this pattern, put `VALIDATE CONSTRAINT` in its own follow-up transaction/file, matching `CONVENTIONS.md` §2 exactly (already done correctly in `20260701160000` and `20260705120000`/`20260705120001`). No urgent edit needed to this specific already-applied file given the guaranteed-empty-column reasoning holds regardless of table size.
    - **Technical:** `ADD CONSTRAINT ... NOT VALID` is a fast, catalog-only operation, and `VALIDATE CONSTRAINT` only needs the lighter `SHARE UPDATE EXCLUSIVE` lock — but only when run in a *separate* transaction. Here both are inside the same `BEGIN`/`COMMIT`, so the transaction retains whatever lock level the earlier `ADD COLUMN`/`ADD CONSTRAINT` statements acquired for its whole duration, including through the `VALIDATE` scan. `scripts/guard-no-unsafe-migrations.php` (Check 3) only verifies `NOT VALID` is present — it does not check that `VALIDATE CONSTRAINT` runs in a separate transaction — so this class of gap is not CI-enforced.
    - **Plain English:** The two-step pattern is like announcing "we'll inspect every car later" and then actually inspecting them separately, so cars can keep driving through in between. Announcing and inspecting in the same breath means traffic still stops for the whole thing — even though, in this specific case, there happen to be no cars on the road yet (every row is empty), so nobody actually notices.
    - **Evidence:**
        ```sql
        BEGIN;
        ...
        ALTER TABLE site.platform_connections
            ADD CONSTRAINT platform_connections_apify_status_check
            CHECK (apify_status IS NULL OR apify_status IN ('pending', 'ok', 'unavailable')) NOT VALID;
        ALTER TABLE site.platform_connections VALIDATE CONSTRAINT platform_connections_apify_status_check;
        ```

- [ ] **MIG-8** · P3 — Widespread missing `SET LOCAL lock_timeout` / `statement_timeout` guards on DDL against live-traffic tables
    - **Where:** supabase/migrations/ — 30+ files touching `site.design_kits`, `site.sites`, `site.blocks`, `site.menus`, `site.menu_items`, or `core.users` without the timeout guards documented in `docs/migration-guidelines.md` §"Lock and statement timeouts", including 20260701000000, 20260701140000, 20260701190000, 20260701200000, 20260707030000
    - **Affects:** Deploy safety generally — any migration among these files that blocks on a live-traffic lock will hang indefinitely (Postgres default `lock_timeout` is 0 = wait forever) rather than failing fast. `20260701220000`, `20260705120000`/`20260705120001`/`20260705120002`, and `20260718010000` establish the correct pattern; most other hot-table-touching files predate or simply don't follow it.
    - **Effort:** M (~2–4h) — bulk-add the guards, or consider a runner-level default
    - **What to do:**
        - Add `SET LOCAL lock_timeout = '2s'; SET LOCAL statement_timeout = '10s';` after `BEGIN;` in each affected file per `docs/migration-guidelines.md` §"Lock and statement timeouts" — safe to backfill into already-applied files per the same version-timestamp reasoning as MIG-1 through MIG-4.
        - Longer term, consider whether `supabase db push` can be invoked with a session-level default so a future migration can't omit this by accident.
    - **Technical:** `docs/migration-guidelines.md` explicitly documents `SET LOCAL lock_timeout = '2s'; SET LOCAL statement_timeout = '10s';` as the required guard for DDL against `site.design_kits`, `site.sites`, and `site.blocks` (this lens additionally scopes `core.users` in). Without it, a migration that can't immediately acquire its lock queues silently rather than erroring, and — because `supabase db push` applies files sequentially — every subsequent migration in the same push waits behind it, turning one blocked lock into a stalled deploy with no obvious cause. None of `scripts/guard-no-unsafe-migrations.php`'s four checks verify this guard's presence, so it is entirely un-enforced by CI today.
    - **Plain English:** Most migrations that touch a busy table never say "give up after 2 seconds if you can't get in." Without that limit, a blocked migration can simply wait forever, quietly freezing the rest of the deploy behind it with no alarm going off. A small number of recent files already do this correctly — the rest should catch up.
    - **Evidence:**
        ```sql
        -- Exemplar (20260701220000) — HAS the guards:
        BEGIN;
        SET LOCAL lock_timeout = '3s';
        SET LOCAL statement_timeout = '30s';
        ALTER TABLE site.platform_connections ADD COLUMN IF NOT EXISTS apify_status text;
        ```
