## P1 — Fix before pilot launch

- [ ] **LIFE-1** · P1 — Cloudflare purge job can time out mid-purge for large catalogs, permanently stalling edge invalidation
    - **Where:** app/Services/Cloudflare/CloudflarePurgeService.php:66-72, 147-149, 163-165, 207; app/Jobs/Cloudflare/CloudflareCachePurgeJob.php:38
    - **Affects:** Every professional with a large shop catalog, menu, or events list (restaurants, retailers) — their product/menu/event detail pages can get permanently stuck serving stale edge content after every future edit, with the failure repeating on every retry.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Split `purgeHandle()`'s URL list across multiple delayed `CloudflareCachePurgeJob` dispatches (e.g. one dispatch per N chunks) instead of looping every chunk synchronously inside one job run, OR raise `$timeout` to a value computed from the enumerated entity count with a hard ceiling, and lower the per-lookup `limit()`s so a single job run is bounded by wall-clock time, not just row count.
        - Add a log line (or metric) when the enumerated URL count crosses a threshold so a catalog approaching the practical purge ceiling is visible before it starts failing outright.
    - **Technical:** Category (6) vendor-integration hygiene / job-correctness-under-load. `CloudflareCachePurgeJob::$timeout` is fixed at 15 seconds (line 38), but `CloudflarePurgeService::purgeHandle()` can enumerate up to 100 product handles + 150 menu-item ids + 100 event ids (deduplicated from `site.shop_products`/`shop_brands`, `site.menu_items`/`menus`, and `platform_connections` payloads respectively), each contributing a page URL *and* an SWR-shadow URL, across up to two hostnames when a custom domain is active. `purgeUrls()` then walks the combined list sequentially in blocking 30-URL chunks via `Http::...->post(...)->throw()` (lines 66-72) — worst case roughly 50 sequential blocking HTTP round-trips to the Cloudflare API inside one 15-second job. A busy catalog (a restaurant's full menu easily exceeds 100 items across categories) will routinely blow the timeout mid-loop; the job is killed, retried up to `$tries=3` re-running the *same* full sequential loop each time, and on exhaustion just `report()`s + logs an error (no on-call page unless `moderationCaseId` is set). The purge for that handle then reliably fails on every future edit, leaving product/menu/event detail pages permanently stale at the edge for exactly the platform's highest-content-volume users — the ones this per-entity purge feature (shipped 2026-07-16/17 per the file's own comments) was built to serve.
    - **Plain English:** When a professional edits their page, the system tells Cloudflare's edge network to throw out its old cached copies of every page — including one entry per menu item, product, or event they've listed. For someone with a big menu or catalog, that can mean sending Cloudflare fifty or more separate "forget this page" requests, one after another, inside a single background task that gets killed if it runs longer than 15 seconds. A restaurant with a full menu will regularly hit that ceiling, so the request gets cut off partway through and retried — over and over, failing the same way each time — meaning some of their menu pages may never actually refresh at the edge, and diners keep seeing outdated prices or items indefinitely.
    - **Evidence:**
        ```php
        // Cloudflare's purge_cache `files` accepts at most 30 URLs per request on
        // non-Enterprise plans. A full sitepage purge (root + 15 deep-link
        // sub-paths + each one's SWR shadow + the API subrequest) exceeds that, so
        // chunk into <=30-URL batches — one POST each.
        foreach (array_chunk(array_values($urls), 30) as $chunk) {
            Http::withToken($this->apiToken)
                ->asJson()
                ->acceptJson()
                ->post($this->url(), ['files' => $chunk])
                ->throw();
        }
        ```
        ```php
        public int $timeout = 15;
        ```

## P2 — Should fix

- [ ] **LIFE-2** · P2 — Subdomain-rename lock covers `subdomain_changed_at` but not `subdomain` itself, letting a rapid double-rename drop an alias hop
    - **Where:** app/Services/Site/RenameSubdomainAction.php:32, 45-49, 95-117, 158
    - **Affects:** Sites renamed twice in quick succession where the second rename passes `allow_subdomain_override=true` (the staff force-rename path, or any future caller of `UpdateSiteAction::execute` with that option that doesn't reload `$site` first — `ReclaimHandleAction` already mitigates this via `$professional->fresh()`). The intermediate subdomain silently loses its redirect alias and returns to the public pool instead of 301-ing, and the `HandleChangeLog` audit row for the second rename records the wrong `old_handle`.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Extend the existing `lockForUpdate()` query (line 45-48) to select `subdomain` alongside `subdomain_changed_at`, and assign the locked `subdomain` onto `$site` (and recompute `$current` from it) before the no-op check and the alias-creation/audit-log code below run — mirroring the fix already applied to `subdomain_changed_at`.
    - **Technical:** Category (2) race-safe read-modify-write. `$current = strtolower((string) $site->subdomain)` (line 32) is computed from the pre-transaction in-memory `$site` object before any lock is acquired. The subsequent `lockForUpdate()` block (lines 45-49) — added, per the inline comment, specifically to fix a prior cooldown-bypass race — re-reads *only* `subdomain_changed_at`, never `subdomain` itself. Both `$site->subdomain` (used to create/refresh the `SiteSubdomainAlias` row, lines 95-117) and `$current` (written as `HandleChangeLog.old_handle`, line 158) remain the stale pre-lock value for the rest of the function. When a site is renamed twice back-to-back under `allow_subdomain_override=true` — the second call's `lockForUpdate()` blocks until the first commits, then correctly reads the fresh `subdomain_changed_at` (so the cooldown-bypass bug this pattern was built to close stays fixed) — but its `$site->subdomain` is still the *pre-first-rename* value, so the alias insert for the intermediate handle collides with the one the first rename already created (silently absorbed by the `UniqueConstraintViolationException` catch, which just refreshes lifecycle timestamps on the wrong alias) and no alias row is ever created for the intermediate subdomain. That subdomain is dropped from `site.site_subdomain_aliases` entirely, returning to the unclaimed pool with no redirect rather than 301-ing per the handle-lifecycle contract. (The equivalent staleness on `$professional->handle`, used for `core.user_handle_aliases`, is not at risk — the file's own comment notes `trg_professional_handle_change` independently records the old handle from the DB row's true prior value at commit time.)
    - **Plain English:** When someone changes their page's web address, the system briefly locks that page's record so two rename requests can't collide. But the "what was the old address" bookkeeping used to set up a redirect is read from a snapshot taken *before* the lock, not from the record the lock protects. In an unusual back-to-back-renames scenario (currently only reachable via staff tooling), this stale snapshot causes the system to skip creating the redirect for an address that briefly existed, silently abandoning that address instead of properly forwarding visitors away from it.

- [ ] **LIFE-3** · P2 — Cloudflare purge product/menu/event lookup failures log at debug, invisible to Nightwatch and to production log level
    - **Where:** app/Services/Cloudflare/CloudflarePurgeService.php:150-153, 166-169, 208-211
    - **Affects:** Site owners whose product/menu/event pages silently stop refreshing at the edge if the underlying DB lookup starts failing (a schema change, a broken join). No alert fires and, since `Log::debug` typically isn't even persisted at production log levels, no log trail exists either — operations has zero signal.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Upgrade all three catch-log calls from `Log::debug` to `Log::warning`, keeping the existing per-lookup discriminating messages (`product-handle lookup failed` / `menu-item lookup failed` / `event-id lookup failed`) and context (`handle`, `error`).
    - **Technical:** Category (10) observability / Log-with-context pattern. `CloudflarePurgeService::purgeHandle()` enumerates product, menu-item, and event detail pages via three separate DB lookups, each wrapped in `catch (\Throwable $e)` that on failure logs at `Log::debug` and silently continues with an empty list, purging only the fixed page/subpage set. Nightwatch alerts on exceptions and auto-detected slow jobs/routes, never on log queries, and a debug-level log is invisible to both — Laravel's default production log configuration typically doesn't even persist debug-level entries. A broken join (this codebase has already hit two production incidents from schema drift between the test and production DB layers) would silently and permanently stop purging product/menu/event pages for every site on the platform, with zero signal until a professional reports stale content. The three log messages already discriminate by lookup type, satisfying the "distinct logs for distinct failure modes" pattern — only the log level needs to change.
    - **Plain English:** If the system can't look up a professional's product, menu, or event pages while clearing Cloudflare's cache, it quietly skips purging just those pages and writes the failure to a log level that isn't even kept around in production. Nobody is notified — those pages could keep showing outdated content indefinitely and no alert would ever fire to catch it.
