## P1 — Fix before pilot launch

- [ ] **#EDGE-1** · P1 — Reordering services or service categories never purges the edge cache
    - **Where:** app/Http/Controllers/Api/User/SiteManagement/UserServiceCategoryController.php:151 (`reorder`), app/Http/Controllers/Api/User/SiteManagement/UserServiceController.php:199 (`reorder`) and :213 (`reorderLayout`); app/Services/Site/ReorderService.php:22-55
    - **Affects:** Any professional who reorders their service categories or services (a routine, expected dashboard action) — the public sitepage keeps serving the old order until an unrelated site mutation happens to touch `sites.updated_at`, which can be a long time (or never) for a professional who only reorders and changes nothing else.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - In `UserServiceCategoryController::reorder`, resolve the site (`$site = $pro->site` / `currentSite()`) and pass `fn () => $site->touch()` as the 4th `$afterCommit` argument to `ReorderService::reorder`, matching `UserGalleryController::reorder` / `UserLinkBlockController::reorder` / `UserSectionBlockController::reorder`.
        - Do the same in `UserServiceController::reorder`.
        - `reorderLayout` doesn't use `ReorderService` at all (raw `DB::transaction` + per-row `Service::query()->update()` / `ServiceCategory::query()->update()`) — add an explicit `$pro->site?->touch();` after the transaction commits.
        - Add a regression test asserting `sites.updated_at` changes (and `CloudflareCachePurgeJob` is dispatched) after each of the three reorder actions.
    - **Technical:** `ReorderService::reorder()` performs its writes via `(clone $scopeQuery)->where('id', $id)->update([...])` — a query-builder mass update, which does not fire Eloquent model events. `ServiceObserver`/`ServiceCategoryObserver` (which normally call `touchParentSite()` / dispatch `CloudflareCachePurgeJob` directly on `created`/`updated`/`deleted`) therefore never run for a reorder. `ReorderService::reorder()` accounts for this with an optional 4th `$afterCommit` closure, and three sibling controllers correctly pass `fn () => $site->touch()` — but `UserServiceCategoryController::reorder` and `UserServiceController::reorder` omit the argument entirely, and `UserServiceController::reorderLayout` (which bypasses `ReorderService` altogether) has no touch call anywhere in the method. This is a genuine, currently-live caching gap — DeepSeek's EDGE lens missed it while flagging nine other cache-purge findings that turned out to be false (see the Standalone notes below); this is the real instance of the pattern it was looking for.
    - **Plain English:** When you drag-and-drop your services or service categories into a new order, your live public page is supposed to instantly reflect the new order — the system does this by "tapping" your site's timestamp, which tells the caching layer to refresh. Three sibling features (photo reordering, link reordering, section reordering) do this tap correctly. Service and service-category reordering forgot the tap, so your visitors can keep seeing the old order for a long time even though your dashboard shows the new one.
    - **Evidence:**
        ```php

            app(ReorderService::class)->reorder(
                $request->input('ids', []),

            return $this->success(['ok' => true]);
        }
        ```

    - **Technical:** `supabase/migrations/20260527070000_skeleton_system_cleanup.sql` creates `site.design_kits` with `site_id UUID PRIMARY KEY` and a trigger (`trg_create_empty_design_kit`) that auto-inserts a row on every `site.sites` INSERT — but the migration's own comment states "existing sites are backfilled separately (see Phase 2 step 2.4 in the plan — not in the [migration])," i.e. outside the tracked `supabase/migrations/` history. `writeDesignKit()` already defends against a missing row with `updateOrInsert()` (fixing an earlier bug where a plain `update()` on a missing row silently discarded the save with an HTTP 200 — see the code's own `SCHEMA-1:` comment). However, `DB::table(...)->where('site_id', $siteId)->lockForUpdate()->get()` acquires zero locks when no row exists, and Laravel's `updateOrInsert()` is not atomic (an `exists()` check followed by a separate `insert()`/`update()`) — so two concurrent requests that both see "no row yet" can both attempt an `INSERT`, and the loser hits a primary-key violation (a thrown exception surfaced as a 500, not silent data loss). The blast radius is narrow — only the shrinking population of sites still missing a backfilled row, hit only under genuine write concurrency (e.g. autosave racing an explicit save click).
    - **Plain English:** Every site is supposed to have one settings-storage row created automatically, but some older sites from before this system existed were meant to get that row filled in by hand — and the code has no way to confirm all of them actually did. The app has a safety net that creates the row on the fly, but that safety net isn't perfectly thread-safe: if two save requests for the very same still-missing row arrive at the exact same instant, one of them will fail with an error instead of quietly succeeding. Running the missing one-time backfill removes the gap entirely.
    - **Evidence:**
        ```php
        // SCHEMA-1: updateOrInsert (not update) so a missing kit row is
        // created rather than silently no-op'd. The trigger
        // trg_create_empty_design_kit guarantees a row for sites created
        // through the app, but pre-cleanup sites that missed the backfill
        // (or rows lost to a trigger bypass) would otherwise discard every
        // save with an HTTP 200. On insert the FK is taken from the match
        // attributes; $valid no longer carries site_id (stripped above).
        DB::connection('pgsql')
            ->table('site.design_kits')
            ->updateOrInsert(['site_id' => $siteId], $valid);
        ```
