## P1 — Fix before pilot launch

- [ ] **CCH-3** · P1 — SWR recompute failures propagate instead of falling back to the known-good stale value
    - **Where:** app/Services/Cache/CacheLockService.php:97-119 (`rememberLocked` SWR branch); app/Services/Cache/SiteCacheService.php:227-245 (`getPublicSitePayload` SWR branch)
    - **Affects:** Every cached read routed through `CacheLockService::rememberLocked`'s stale-while-revalidate path (site link blocks, dashboard/active services, customer counts) and — most critically — `SiteCacheService::getPublicSitePayload`, the payload the code itself documents as "MOST CRITICAL — 95% of traffic," i.e. the platform's hottest read path.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - In `CacheLockService::rememberLocked`, wrap the `$callback()` call (and the subsequent write) inside the non-blocking-lock SWR branch in a try/catch. On `Throwable`, `report()` the exception (so Nightwatch surfaces it) and return the already-fetched `$stale` value instead of letting the exception propagate.
        - Apply the identical try/catch around `$this->buildPayloadFromDb($subdomain, $key)` in `SiteCacheService::getPublicSitePayload`'s SWR fast path, falling back to the `$stale` copy (run through the existing `ensureBlockCollections`/`safeHydrateSitePayload` healing already used elsewhere in this method for old-shape stale copies) on exception.
        - Add a Pest test per method that forces the recompute closure/query to throw while a valid `:stale` entry exists, asserting the stale value is returned instead of an exception reaching the HTTP layer.
    - **Technical:** Both `CacheLockService::rememberLocked` and the hand-rolled equivalent in `SiteCacheService::getPublicSitePayload` implement the same stale-while-revalidate shape: when the primary key is expired but a `:stale` copy is live, the request that wins the non-blocking fill-lock recomputes the value inline — there is no background worker, recomputation happens synchronously inside the winning request's own execution. In both places the recompute call sits inside `try { ... } finally { $lock->release(); }` with no `catch`, so a transient failure (a Postgres blip, a `MediaVariant::query()` timeout) propagates all the way out and becomes a 500 for that one request, even though a perfectly good `$stale` value was already fetched into scope one line above. Every *other* concurrent request during the same window still gets the stale value fine (they lose the non-blocking lock race and take the "another worker is refreshing" branch) — only the unlucky lock-winner pays for the failure, which is exactly the scenario stale-while-revalidate exists to protect against. Because Postgres/Redis blips are a normal, expected operational reality — not a hypothetical deploy mistake — this gap will fire in practice, on the platform's single hottest endpoint.
    - **Plain English:** This cache system is designed so that if the "fresh" copy of a page's data expires, one visitor's request quietly rebuilds it in the background while everyone else keeps seeing the still-good older copy — nobody should ever notice. But there's a gap: if that background rebuild hits a hiccup (say the database blinks for a moment), the one unlucky visitor whose request happened to be doing the rebuilding gets an error page instead of just being handed the older-but-still-fine copy sitting right there in memory. It's like a bakery that hands every customer yesterday's loaf while today's batch bakes — except the one customer who walks in exactly when the oven trips a fuse gets sent away empty-handed instead of getting yesterday's loaf like everyone else did.
    - **Evidence:**
        ```php
        // app/Services/Cache/CacheLockService.php — rememberLocked() SWR branch
        $lock = Cache::lock('lock:'.$key, $lockSeconds);
        if ($lock->get()) {
            try {
                // Re-check primary after acquiring — another process may have
                // just filled it while we were racing for the lock.
                $fresh = Cache::get($key);
                if ($fresh !== null) {
                    return $fresh;
                }

                $value = $callback();
                $this->writeWithJitter($key, $staleKey, $value, $ttl);

                return $value;
        ```
        ```php
        // app/Services/Cache/SiteCacheService.php — getPublicSitePayload() SWR branch
        if ($fillLock->get()) {
            try {
                // Re-check primary: another process may have filled it while we raced.
                $rechecked = Cache::get($key);
                if ($rechecked === self::MISS_SENTINEL) {
                    return null;
                }
                if (is_array($rechecked) && array_key_exists('services', $rechecked)) {
                    return $this->withoutResolvedMarker($rechecked);
                }

                return $this->buildPayloadFromDb($subdomain, $key);
            } finally {
                $this->releaseLockQuiet($fillLock);
            }
        }
        ```

- [ ] **WHK-1** · P1 — `SyncSubdomainToKvJob::uniqueId()` doesn't discriminate a delete-triggered retire dispatch from a routine sync — the retire can be silently dropped
    - **Where:** app/Jobs/Cloudflare/SyncSubdomainToKvJob.php:66-71 (`uniqueId()`); app/Observers/User/UserObserver.php:77, 178, 203 (the divergent dispatch call sites)
    - **Affects:** The Cloudflare `SUBDOMAIN_KV` routing table — a deleted, suspended, or moderation-actioned user's subdomain can keep resolving publicly (continuing to serve their page) instead of being retired, if a routine reconciliation sync for the same user is in flight when the retire dispatch fires.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Fold a discriminator for the retire/`capturedHandle` path into `uniqueId()`, mirroring the existing `retireCustomDomain` handling, e.g.: `$this->userId.($this->capturedHandle !== null ? ':retire-handle:'.strtolower($this->capturedHandle) : '').($this->retireCustomDomain ? ':retire:'.strtolower(trim($this->retireCustomDomain)) : '')`.
        - Add a regression test: dispatch a plain sync for a user, then — before it's processed — dispatch a delete-triggered retire for the same user within the 45s `uniqueFor` window; assert both jobs actually run (the retire is never silently skipped).
    - **Technical:** `SyncSubdomainToKvJob implements ShouldBeUnique` with `uniqueFor = 45`. Laravel derives the dedup lock key purely from the job class plus `uniqueId()` (`Illuminate\Bus\UniqueLock::getKey()`), and if a job with the same key is already locked, the *entire dispatch is silently dropped* — `Illuminate\Foundation\Bus\PendingDispatch::__destruct()` just returns when `shouldDispatch()` is false, with no exception, no log entry, nothing observable (verified against the vendored Laravel 12 source). `uniqueId()` already special-cases `retireCustomDomain` for exactly this reason — the inline comment says so explicitly: "Include the retire-domain in the unique key so a domain-removal sync is not collapsed into a concurrent plain sync (which would drop the deletion)." But `capturedHandle` — the other field that also signals "this dispatch must retire, not reconcile" (set only by `UserObserver::deleted()`) — never got the same treatment. `UserObserver::updated()` (on handle change) and `UserObserver::restored()` both dispatch a bare `SyncSubdomainToKvJob::dispatch((string) $professional->id)`, producing the *identical* `uniqueId()` as a `deleted()`-triggered retire dispatch for the same user (`$this->userId` with no suffix, since `retireCustomDomain` is also null there). If a rename or restore sync for a user is still holding the 45s unique lock when that same user is deleted/suspended/moderation-actioned moments later, the retire dispatch is dropped and the KV entry is never removed — the exact class of bug this same file has already had to fix multiple times under other names (its own comments cite EDGE-1, EDGE-3, JOB-101, JOB-102).
    - **Plain English:** This job is the only thing allowed to update the internet's routing table that says "this web address points to this person's page." When someone's account is deleted or taken down, this job is supposed to erase their entry so their page stops showing up. But the job also runs for harmless reasons, like a routine "double-check the address is right" after someone renames their handle — and both kinds of runs share the same "don't repeat yourself within 45 seconds" rule. If the harmless routine run happens to be mid-flight at the exact moment the "erase this person" run gets triggered, the system thinks "I'm already doing this" and quietly throws away the erase instruction — leaving a deleted or banned person's page live on the internet with nobody aware anything went wrong. The code already fixed this exact mistake once for a related case (removing a custom domain) but missed applying the same fix here.
    - **Evidence:**
        ```php
        // app/Jobs/Cloudflare/SyncSubdomainToKvJob.php:66-71
        // Include the retire-domain in the unique key so a domain-removal sync is not
        // collapsed into a concurrent plain sync (which would drop the deletion).
        public function uniqueId(): string
        {
            return $this->userId.($this->retireCustomDomain ? ':retire:'.strtolower(trim($this->retireCustomDomain)) : '');
        }
        ```
        ```php
        // app/Observers/User/UserObserver.php:77 — plain sync (handle change)
        SyncSubdomainToKvJob::dispatch((string) $professional->id);

        // app/Observers/User/UserObserver.php:178 — retire dispatch (delete)
        SyncSubdomainToKvJob::dispatch((string) $professional->id, (string) $professional->handle);
        ```

## P3 — Nice to have

- [ ] **TXN-1** · P3 — Inconsistent `->afterCommit()` usage on job dispatches inside `SiteObserver::saved()`
    - **Where:** app/Observers/Core/SiteObserver.php:46, 60, 76
    - **Affects:** Developers reading the observer; no runtime impact — `SiteObserver::$afterCommit = true` (verified: Laravel 12's `Dispatcher::handlerShouldBeDispatchedAfterDatabaseTransactions()` defers the entire event handler, not just queued dispatches, when a listener class carries this property) already guarantees the whole `saved()` body, including every `::dispatch()` call inside it, runs after commit.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Pick one convention: either drop the redundant `->afterCommit()` calls and add a one-line comment above the dispatches explaining that the class-level `$afterCommit = true` already covers it, or add `->afterCommit()` to the `SyncSubdomainToKvJob::dispatch()` call for visual consistency.
    - **Technical:** `SiteObserver::$afterCommit = true` causes Laravel to defer the entire `saved()`/`deleted()` method body — via the dispatcher's transaction-manager callback — until after the enclosing DB transaction commits. `CloudflareCachePurgeJob` and `WarmPublicSiteCacheJob` additionally chain `->afterCommit()` on their own dispatch, which is a harmless no-op re-registration on an already-empty transaction stack; `SyncSubdomainToKvJob::dispatch($userId)` uses a bare dispatch, which is equally safe. The inconsistency risks a future reader "fixing" the bare dispatch by adding the modifier, or worse, assuming the class-level flag isn't reliable and adding redundant per-dispatch modifiers everywhere.
    - **Plain English:** Three packages are shipped from a warehouse after the truck is already loaded and the doors are closed. Two of them have an extra "ship after loading" sticker on top of the warehouse-wide policy that already guarantees that. The third doesn't. All three still arrive at the same time — the stickers don't change anything — but they could confuse the next warehouse manager into thinking the policy doesn't apply everywhere.
    - **Evidence:**
        ```php
        // app/Observers/Core/SiteObserver.php:46
        CloudflareCachePurgeJob::dispatch($handle, $customDomain)->afterCommit();

        // app/Observers/Core/SiteObserver.php:60
        WarmPublicSiteCacheJob::dispatch(strtolower($site->subdomain))->afterCommit();

        // app/Observers/Core/SiteObserver.php:76
        SyncSubdomainToKvJob::dispatch($userId);
        ```

- [ ] **CCH-2** · P3 — No shared `:stale`-key helper — the suffix is hand-concatenated at every invalidation site
    - **Where:** app/Services/Cache/SiteCacheService.php:548-551 (`bustWithStale`, private); app/Services/Cache/UserCacheService.php:270, 291; app/Observers/Core/ServiceCategoryObserver.php:53, 55
    - **Affects:** Any future rename of the `:stale` suffix convention (e.g. to `:swr`) requires a manual grep-and-replace across three classes instead of one central definition.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add a `CacheKeyGenerator::staleKey(string $key): string` static method that appends `:stale`.
        - Use it in `SiteCacheService::bustWithStale`, `UserCacheService::invalidateUser`, `UserCacheService::invalidateCustomerCount`, and wherever `ServiceCategoryObserver::bust()` ends up living after CCH-1 is fixed.
    - **Technical:** `SiteCacheService` has a private `bustWithStale(string $key): array` helper (`return [$key, $key.':stale'];`) that is not shared outside that class. `UserCacheService::invalidateUser` and `UserCacheService::invalidateCustomerCount` each hand-concatenate `.':stale'` directly, as does `ServiceCategoryObserver::bust()`. A single `CacheKeyGenerator::staleKey()` method — alongside `CacheKeyGenerator`'s existing role as the one place all key naming flows through — would make the suffix a single point of change.
    - **Plain English:** Every room in a building has a matching storage closet labelled "room-name:stale." Right now, each caretaker writes that label by hand on their own sticky note. If the closets are ever renamed to "room-name:swr," every caretaker has to remember to re-label their own notes. It's simpler to have one label-maker that prints every sticky note from a single template.
    - **Evidence:**
        ```php
        // SiteCacheService.php:548-551 — has the helper but it's private:
        private static function bustWithStale(string $key): array
        {
            return [$key, $key.':stale'];
        }

        // UserCacheService.php:291 — invalidateUser, manual concat:
        $modelKey.':stale',

        // UserCacheService.php:270 — invalidateCustomerCount, manual concat:
        Cache::deleteMultiple([$key, $key.':stale']);

        // ServiceCategoryObserver.php:53,55 — bust(), manual concat:
        CacheKeyGenerator::professionalDashboardServices($userId).':stale',
        ```

- [ ] **CCH-1** · P3 — `ServiceCategoryObserver` bypasses the cache-service layer for services-key invalidation
    - **Where:** app/Observers/Core/ServiceCategoryObserver.php:51-56
    - **Affects:** Cache-key management consistency; other observers (`CustomerObserver`) explicitly route through a `UserCacheService` method to preserve this invariant — this one doesn't.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add a `UserCacheService::invalidateServices(string $userId)` method that does the same 4-key delete.
        - Replace the raw `Cache::deleteMultiple([...])` in `ServiceCategoryObserver::bust()` with a call to that new method.
    - **Technical:** The observer directly constructs and deletes `professionalDashboardServices` and `professionalServices` keys (and their `:stale` companions) via the `Cache` facade, while the read path for those same keys lives in `UserCacheService` through `rememberLocked`. `CustomerObserver` explicitly documents avoiding this: "Uses `UserCacheService::invalidateCustomerCount()` to stay within the GS-1 service-layer rule (no raw `Cache::` calls outside cache services)." `ServiceCategoryObserver` doesn't follow that same rule for the identical services-cache case, creating a second code path that must stay in exact key alignment with two `CacheKeyGenerator` methods by hand.
    - **Plain English:** The services catalogue has two doors — one for reading and one for clearing. Right now the clearing door is on a different building (the observer) with its own handwritten key labels, even though a sibling observer (for customer counts) correctly keeps both doors in the same building. If the lock is ever renamed, someone has to remember to update both buildings instead of just one.
    - **Evidence:**
        ```php
        Cache::deleteMultiple([
            CacheKeyGenerator::professionalDashboardServices($userId),
            CacheKeyGenerator::professionalDashboardServices($userId).':stale',
            CacheKeyGenerator::professionalServices($userId),
            CacheKeyGenerator::professionalServices($userId).':stale',
        ]);
        ```
