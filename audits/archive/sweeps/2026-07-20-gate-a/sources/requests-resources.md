## P1 — Fix before pilot launch

- [ ] **#SEC-1** · P1 — Document upload has no downstream content validation at any layer
    - **Where:** app/Http/Requests/Api/User/Documents/UploadDocumentRequest.php:14-19
    - **Affects:** The document-upload endpoint used by every professional. Uploaded files are later served for direct download to unauthenticated sitepage visitors via `DocumentMediaResource::download_url` / `PublicDocumentController`.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add a document-specific whitelist + assertion method to `SniffsFileMimeType` (e.g. a `DOCUMENT_MIME_WHITELIST = ['application/pdf','image/jpeg','image/png']` const and an `assertDocumentMimeBytes()` method) — keep it separate from the existing `IMAGE_MIME_WHITELIST`, since widening that shared constant would let non-image files quietly pass the pure-image upload lanes (`UploadContentImageRequest`, `UploadDesignMediaRequest`, `UploadImageRequest`'s image path) too.
        - `use SniffsFileMimeType;` in `UploadDocumentRequest` and add a `withValidator()` that calls the new assertion, mirroring the pattern already used in the three image-only Form Requests.
    - **Technical:** `UploadDocumentRequest` validates only via Laravel's client-trusted `mimes:pdf,jpg,jpeg,png` rule — confirmed no `SniffsFileMimeType` usage and no `withValidator()`. This is meaningfully worse than it looks at the Form Request layer alone: I traced the two sibling upload paths and found they both have a downstream safety net that documents lack. Image uploads get a `finfo` byte-sniff a second time inside `ImageVariantService::assertRealMimeType()` (`app/Services/Media/ImageVariantService.php:500-508`) before any variant is generated. Video uploads get validated by `ffprobe` inside `VideoVariantService` — a container that isn't a real video throws `InvalidVideoFileException` (`app/Services/Media/Exceptions/InvalidVideoFileException.php`) and is rejected before transcoding. `MediaUploadService.php` has no document-handling branch at all, and `DocumentMediaResource` serves `Storage::disk($mediaDisk)->url($media->path)` straight from whatever was stored — so `UploadDocumentRequest`'s client-trusted `mimes:` check is the *only* gate in the entire pipeline. A file with real content that isn't a PDF/JPG/PNG (renamed with a `.pdf` extension and a spoofed `Content-Type`) passes upload, is stored, and is served verbatim to any visitor who clicks "download" on a professional's sitepage.
    - **Plain English:** Every other file type this platform accepts gets checked twice — once at the door, and once again by a second machine before it's actually used (photos get re-checked before resizing; videos get re-checked before playback works at all). Documents only get checked once, at the door, and that check only reads the label someone can write themselves — it never opens the file to see what's actually inside. Since anyone can sign up and create a public page, a bad actor could upload something harmful disguised as a PDF, and a visitor who trusts the professional would download it believing it's a real document.
    - **Evidence:**
        ```php
        'file' => [
            'required',
            'file',
            'mimes:pdf,jpg,jpeg,png',
            'max:10240', // KB
        ],
        ```

## P2 — Should fix

- [ ] **#PRIV-1** · P2 — StaffFeedbackResource exposes the submitting professional's email to every staff member, bypassing the platform's own PII-gate pattern
    - **Where:** app/Http/Resources/Staff/StaffFeedbackResource.php:26-31
    - **Affects:** Every professional who submits dashboard feedback — their `primary_email` is visible to any staff account that can list feedback, not just admin staff.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add a `$showPii` constructor gate to `StaffFeedbackResource`, matching `UserStaffResource` and `StaffUserListResource`, and null out `email` when it's false.
        - Update `StaffFeedbackController` (wherever it constructs this resource) to pass `$showPii` based on the requesting staff member's role, the same way the professional-list controllers already do.
    - **Technical:** `StaffFeedbackResource::toArray()` unconditionally includes `'email' => $this->user->primary_email` inside the nested `user` array. The codebase has an established, repeated pattern for exactly this situation — `UserStaffResource` and `StaffUserListResource` both take a `private readonly bool $showPii = false` constructor parameter and null out `primary_email`/`phone` unless the controller has verified the caller is admin staff. `StaffFeedbackResource` is the one PII-carrying staff resource in the codebase that has no such gate, so any staff member with feedback-list access — not just admins — sees the submitting professional's email. The resource's own docblock argues staff "need full context," but email isn't required to triage a UI bug report (the resource already surfaces `handle` for follow-up lookups).
    - **Plain English:** When a professional reports a bug through the dashboard, every staff member who opens the feedback queue can see that professional's personal email address — even staff whose job has nothing to do with contacting users directly. The platform already has a rule elsewhere ("only admin staff see email addresses") but this one screen was built without it. It's a small inconsistency, not an external breach, but it means more people can see personal contact details than the platform's own design intends.
    - **Evidence:**
        ```php
        'user' => $this->when($this->relationLoaded('user'), fn () => $this->user === null ? null : [
            'id' => (string) $this->user->id,
            'handle' => $this->user->handle,
            'display_name' => $this->user->display_name,
            'email' => $this->user->primary_email,
        ]),
        ```

## P3 — Nice to have

- [ ] **#PRIV-2** · P3 — Analytics endpoints store the raw referrer URL with no query-string minimisation
    - **Where:** app/Http/Requests/Api/PublicSite/Analytics/PageviewRequest.php:27, ClickRequest.php:37, SectionSeenRequest.php:36, ItemSeenRequest.php:54
    - **Affects:** Sitepage visitors — the full `document.referrer` value (path + query string, when the referring page sends one) is captured on pageview, click, section-seen, and item-seen events.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Strip the query string from `referrer` before storage (keep scheme + host + path only), most naturally in the analytics write path rather than the request validator so the beacon never blocks.
        - No config or cross-file coordination needed beyond that one write-path function — a single-file change.
    - **Technical:** Four analytics Form Requests accept `referrer` as an unvalidated string capped only at `max:2048`, sourced from the browser's `document.referrer`. DeepSeek's original framing overstated the exposure — most referring origins (Google, Facebook, Instagram) now default to `Referrer-Policy: strict-origin-when-cross-origin` or stricter for outbound clicks, so a full search query or path typically does *not* reach `document.referrer` on a cross-origin navigation in a modern browser. The real, narrower risk is referring pages/apps that don't set a restrictive policy (older sites, some in-app webviews, internal share links), which can still pass a path or query string through unminimised. Given `utm_*` params are already captured as separate structured fields, the raw query string adds no analytics value, so stripping it is cheap, unconditional insurance rather than a fix for an active leak.
    - **Plain English:** When someone visits a professional's sitepage after clicking a link elsewhere, the platform records the full web address they came from. Most modern browsers and major sites already trim this down before it ever reaches Partna, so today's actual exposure is narrow — but a few less careful referring sites or apps could still pass along more detail than needed (like a search phrase or a tracking code). Since the platform doesn't use that extra detail for anything, trimming it down to just "which site sent this visitor" closes the gap for good at very low cost.
    - **Evidence:**
        ```php
        // PageviewRequest.php / ClickRequest.php / SectionSeenRequest.php / ItemSeenRequest.php
        'referrer' => ['nullable', 'string', 'max:2048'],
        ```

- [ ] **#PRIV-3** · P3 — PublicCustomerLeadRequest trims but doesn't strip_tags the `notes` field, unlike the sibling public-form pattern
    - **Where:** app/Http/Requests/Api/PublicSite/CustomerLeads/PublicCustomerLeadRequest.php:23,35
    - **Affects:** Professionals' customer-lead lists — a visitor submitting the public lead form can leave unescaped HTML in `notes`, which `PublicEnquiryRequest` already strips for its equivalent `message` field.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - In `PublicCustomerLeadRequest::prepareForValidation()`, apply `strip_tags()` (or `BaseFormRequest::cleanString()`) to `notes`, matching the treatment `name`/`message` already get in `PublicEnquiryRequest`.
    - **Technical:** `PublicEnquiryRequest` strip_tags's `name`, `phone`, and `message` as defense-in-depth. `PublicCustomerLeadRequest` — same risk profile (unauthenticated public submitter, free-text field, `max:2000`) — only trims `notes`. This is a real inconsistency, not a design choice: both fields flow into a professional's dashboard views. Actual exploitability depends on whether the frontend auto-escapes rendered text (typical for modern JS frameworks unless `dangerouslySetInnerHTML`/`v-html` is used), which isn't verifiable from the backend alone — hence P3, not P2.
    - **Plain English:** A visitor filling out a professional's "become a customer" form can type hidden code into the notes box, and unlike the similar contact form elsewhere on the platform, that code isn't cleaned up before being saved. It's a small gap in an otherwise-consistent defense the platform already applies everywhere else visitors submit free text.
    - **Evidence:**
        ```php
        // prepareForValidation()
        'notes' => is_string($this->notes) ? trim($this->notes) : $this->notes,
        // rules()
        'notes' => ['nullable', 'string', 'max:2000'],
        ```

- [ ] **#SEC-2** · P3 — Video upload path skips the Form-Request-level magic-byte check the image path already has
    - **Where:** app/Http/Requests/Api/User/Uploads/UploadImageRequest.php:36-42 (video rules), contrast with the image byte-sniff call at line 73
    - **Affects:** Video uploads to the gallery/content pools — a minor consistency gap, not an open vulnerability.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add a video-specific whitelist + assertion (`video/mp4`, `video/quicktime`, `video/webm`) to `SniffsFileMimeType` and call it from `UploadImageRequest::withValidator()` alongside the existing image check — bundle with #SEC-1 since it's the same trait.
    - **Technical:** `UploadImageRequest` byte-sniffs the image field (`assertImageMimeBytes`) but not the video field — confirmed, only `mimes:mp4,mov,webm` (client-trusted) gates it. Unlike the document-upload gap (#SEC-1), this one already has a real downstream safety net: `VideoVariantService` runs the file through `ffprobe` before any processing, and a container that isn't a genuine video throws `InvalidVideoFileException` (mapped to a 422 by the controller), so a disguised non-video file is rejected before it's ever transcoded or served. The value of this fix is failing fast at the HTTP boundary and matching the codebase's own established pattern, not closing a live hole.
    - **Plain English:** The video-upload lane doesn't do the same quick ID check the image lane does — but unlike the document problem above, a second, more thorough check further down the line (the tool that actually processes the video) will still catch and reject a fake file before it can be played back or shown to anyone. This is worth tidying up for consistency, but it's not something that puts visitors at risk today.
    - **Evidence:**
        ```php
        'video' => [
            'sometimes',
            'nullable',
            'file',
            'mimes:mp4,mov,webm',   // trusts client Content-Type
            "max:{$videoMaxKb}",
        ],
        ```
