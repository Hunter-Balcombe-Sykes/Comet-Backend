## P2 — Should fix

- [ ] **SCHEMA-1** · P2 — `site.workplaces` tenant-data table created without RLS
    - **Where:** supabase/migrations/20260701150000_create_workplaces.sql:11-27
    - **Affects:** Every PostgREST / Supabase-client-reachable read path touching workplace card data (business name, address, phone, website, description) for every user's site.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add `ALTER TABLE site.workplaces ENABLE ROW LEVEL SECURITY; ALTER TABLE site.workplaces FORCE ROW LEVEL SECURITY;`
        - Replicate the **current** (not the earlier) house pattern from `supabase/migrations/20260710140000_rls_policies_new_tables.sql`: an owner-select policy `TO authenticated` joining `site.sites` → `core.users` on `auth.uid()`, a staff-select policy against `core.partna_staff`, and a `FOR ALL TO service_role` policy. Do **not** add a policy `TO app_backend` — `app_backend` carries `BYPASSRLS`, so a policy targeting it is a no-op; `20260710140000` established `service_role`/`authenticated` as the actual belt-and-braces targets for tables created after it, superseding the earlier `app_backend`-targeted policy on `site.design_kit_contributions` (20260701130000).
        - Add a regression-guard test in `tests/Feature/Security/`, mirroring `DesignKitsRlsTest.php`.
    - **Technical:** `site.workplaces` is a 1:1 tenant-scoped table (`site_id uuid PRIMARY KEY REFERENCES site.sites`) holding per-site business identity data. The migration creates it with no `ENABLE ROW LEVEL SECURITY`, no `FORCE`, and no policies. `app_backend` has `BYPASSRLS`, so the application path (gated by `SitePolicy`, confirmed registered for `Workplace::class` in `AppServiceProvider::boot()`) works today — this is purely a defence-in-depth gap against direct PostgREST/Supabase-client exposure. Every comparable post-baseline `site.*` table (`design_kit_contributions`, `shop_brands`, `shop_products`, `menus`/`menu_categories`/`menu_items`/`menu_platform_links`/`menu_item_platforms` via `20260702000000_rls_parity_platform_connections_menus.sql`) ships with RLS enabled and forced, so this table's silence is a real deviation from established convention, not a stylistic nit.
    - **Plain English:** Think of a filing cabinet with client contact cards. The front desk (the app) checks your ID before handing you a file — that's today's protection. But the cabinet itself has no lock, and there's a back door (a more direct database connection) a stranger could walk through if they found it. Row-level security is the lock on the cabinet itself. Every comparable drawer built around the same time got a lock; this one didn't.
    - **Evidence:**
        ```sql
        CREATE TABLE IF NOT EXISTS site.workplaces (
            site_id          uuid PRIMARY KEY REFERENCES site.sites (id) ON DELETE CASCADE,
            name             text,
            address          text,
            address_line1    text,
            city             text,
            state            text,
            postcode         text,
            country          text,
            latitude         double precision,
            longitude        double precision,
            phone            text,
            website          text,
            previous_website text,
            category         text,
            description      text,
            created_at       timestamptz,
            updated_at       timestamptz
        );
        ```

- [ ] **SCHEMA-4** · P3 — `CREATE UNIQUE INDEX` without `CONCURRENTLY` on the live `site.platform_connections` table
    - **Where:** supabase/migrations/20260704140000_add_platform_connection_canonical_key.sql:56-59
    - **Affects:** Write traffic on `site.platform_connections` for the duration of the index build, if this migration were ever re-run against a populated table.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Accept the exemption as-is for pre-beta scale — the file already carries `guard:no-unsafe-migrations:disable-file` and documents that dev holds zero `acct-*` rows today.
        - If a future migration needs to touch this same index shape on a populated table, split index creation into its own file and use `CREATE UNIQUE INDEX CONCURRENTLY`, per the pattern in `20260711160100_add_analytics_purge_indexes.sql` and `20260701220200_gb_place_id_idx.sql`.
    - **Technical:** The migration bundles a column `ADD`, a data backfill, a dedup `DELETE`, and a `CREATE UNIQUE INDEX` in one transaction. `CREATE INDEX` (even a partial one) always takes `ACCESS EXCLUSIVE` on the whole table for the scan, regardless of the `WHERE` predicate — but the table has zero matching rows pre-beta, so the scan is instant. This is a pattern-consistency flag, not a live risk; re-tiered P3 to match SCHEMA-5/6's identical self-documented-exemption class rather than treating it as a standalone concern.
    - **Plain English:** Installing a new lock usually needs a special tool that doesn't block the doorway while people walk through. Here, the crew skipped that tool because they'd already closed off the whole room for other work, and the room is currently empty. Harmless today; if the room fills up before this exact renovation runs again, the tool becomes mandatory.
    - **Evidence:**
        ```sql
        CREATE UNIQUE INDEX IF NOT EXISTS idx_platform_connections_canonical
            ON site.platform_connections (user_id, platform, canonical_key)
            WHERE canonical_key IS NOT NULL AND deleted_at IS NULL;
        ```

    - **Affects:** Writes on `site.sites` and `core.users` during the (currently sub-millisecond) constraint-validation scan.
