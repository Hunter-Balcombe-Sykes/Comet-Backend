## P2 — Should fix

- [ ] **#CFG-1** · P2 — Nightwatch enabled by default but token has no explicit fallback or production guard
    - **Where:** config/nightwatch.php:17-18
    - **Affects:** Every environment deployed without explicitly setting `NIGHTWATCH_TOKEN` — the agent starts but has nothing to authenticate with, silently dropping all observability data (exceptions, slow routes/jobs) with no self-alarm.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add an explicit empty-string default: `env('NIGHTWATCH_TOKEN', '')`.
        - Add a production boot-time guard in `AppServiceProvider::boot()` alongside the two guards that already exist there (`APP_DEBUG` must be false in production; `FEEDBACK_IP_HASH_PEPPER` must be set in production) — the same `if (app()->isProduction() && empty(...)) { throw ... }` pattern, applied to `NIGHTWATCH_TOKEN` when `NIGHTWATCH_ENABLED` is true.
        - Add `NIGHTWATCH_TOKEN` to `.env.example`.
    - **Technical:** `enabled` defaults `true` (config/nightwatch.php:17), but `token` has no second argument (`env('NIGHTWATCH_TOKEN')` → `null` when unset). Verified in `AppServiceProvider::boot()` (app/Providers/AppServiceProvider.php:273-282) that this exact fail-hard-in-production pattern already exists for two other critical config values (`app.debug`, `partna.feedback.ip_hash_pepper`) — `NIGHTWATCH_TOKEN` is the odd one out that ships silent instead of loud. Since Nightwatch is the sole exception/slow-job alerting surface in this codebase (per architecture doctrine, "a failure that needs attention must throw... bare Log::warning is invisible"), a deploy that loses its own monitoring has no mechanism to notice.
    - **Plain English:** A security camera system that's switched on by default but ships without a cable to the monitor. The light blinks green, so you assume you're covered — but nothing is being recorded. Nightwatch is the system's only way to notice exceptions and slow requests; if the connecting token is missing, it fails silently instead of refusing to start, so the team could go for months believing they have monitoring when they don't.
    - **Evidence:**
        ```php
        'enabled' => env('NIGHTWATCH_ENABLED', true),
        'token' => env('NIGHTWATCH_TOKEN'),
        ```
        ```php
        // app/Providers/AppServiceProvider.php — the existing fail-hard pattern to mirror
        if (app()->isProduction() && config('app.debug')) {
            throw new \RuntimeException('APP_DEBUG must be false in production.');
        }
        if (app()->isProduction() && empty(config('partna.feedback.ip_hash_pepper'))) {
            throw new \RuntimeException('FEEDBACK_IP_HASH_PEPPER must be configured in production (ip_hash disabled without it).');
        }
        ```

- [ ] **#SEC-1** · P2 — Early-access marketing form is the only public mutation route with no bot-token gate
    - **Where:** routes/api.php (`/public/early-access` POST)
    - **Affects:** Marketing site visitors and the early-access signup pipeline — open to spam signups and list-pollution from automated scripts.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - If the marketing site can be updated to bootstrap a bot token cross-origin, wire `bot.token:early-access` like every sibling public endpoint.
        - If the cross-origin constraint genuinely can't be lifted, tighten `throttle:early-access` with a per-IP cap materially below the shared `public-site` bucket, mirroring the dedicated `signup_availability_per_minute`/`_per_hour` pattern already used for other enumeration-sensitive endpoints in `config/partna.php`.
    - **Technical:** Every other public mutation route in `routes/api.php` (subscribe, signup/availability, pre-account build, login-identifier, customer leads, enquiries, report) carries `bot.token:<name>` in addition to its throttle. The early-access route is the sole exception — the route comment itself documents this as a deliberate tradeoff ("the marketing site posts cross-origin without a token bootstrap; honeypot + timing check + the dedicated `early-access` throttle carry the abuse load"), but honeypot/timing checks are client-side signals a scripted request can simply omit satisfying, leaving the per-IP throttle as the only real server-side gate.
    - **Plain English:** Every door into the building has a security guard checking IDs, except the early-access entrance, which just has a sign asking bots not to come in. Well-behaved visitors respect the sign; a script that ignores it walks straight through, limited only by how fast the hallway lets people in.
    - **Evidence:**
        ```php
        // OV-A: early-access marketing form (no bot.token — the marketing site posts
        // cross-origin without a token bootstrap; honeypot + timing check + the
        // dedicated `early-access` throttle carry the abuse load) and the invite-token
        // resolve used by /signup?invite=<token> to autofill + lock the email.
        Route::post('/public/early-access', [PublicEarlyAccessController::class, 'store'])
            ->middleware('throttle:early-access');
        ```

- [ ] **#SEC-2** · P2 — Analytics ingest endpoints validate no site/subdomain ownership, only rate limit
    - **Where:** routes/api.php (all `/public/analytics/*` routes)
    - **Affects:** Every professional's analytics can be poisoned by a script posting synthetic events for a `site_id`/`subdomain` it doesn't control; the analytics queue absorbs the write load.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Embed a per-site nonce in the sitepage's public config payload that the analytics client echoes back; the ingest endpoint validates the nonce resolves to the claimed site before accepting the event.
        - Alternatively, add an `Origin`/`Referer` check requiring a `*.partna.au` origin before accepting a write (defense-in-depth only — CORS itself doesn't block non-browser callers).
    - **Technical:** All eight analytics ingest routes carry only `throttle:analytics` (plus `throttle:analytics-click` on the click route). CORS's `allowed_origins_patterns` governs which *browsers* are allowed to call these endpoints via fetch/XHR, but CORS is enforced by the browser, not the server — a `curl` request or a script hosted anywhere can POST the exact same payload with an arbitrary `site_id`, and nothing validates the caller actually has that site loaded. The throttle bounds request *volume* per IP but not *legitimacy* of the claimed site.
    - **Plain English:** The analytics system is like a suggestion box that accepts slips from anyone who walks by. Real visitors drop in genuine feedback, but nothing stops a competitor from stuffing the box with thousands of fake slips claiming to be about someone else's page. The box only accepts so many slips per minute — but it never checks whether the person dropping them off actually visited that page.
    - **Evidence:**
        ```php
        Route::post('/public/analytics/pageviews', [AnalyticsController::class, 'pageview'])
            ->middleware('throttle:analytics');
        Route::post('/public/analytics/clicks', [AnalyticsController::class, 'click'])
            ->middleware(['throttle:analytics', 'throttle:analytics-click']);
        Route::post('/public/analytics/section-seen', [AnalyticsController::class, 'sectionSeen'])
            ->middleware('throttle:analytics');
        ```

- [ ] **#PRIV-1** · P2 — Feedback PII (email, handle, ip_hash) has no retention window or scheduled cleanup for non-deleted rows
    - **Where:** config/partna.php (`feedback` block); routes/console.php (no feedback-prune schedule entry)
    - **Affects:** All rows in `core.feedback` that staff never soft-delete. Submitter email, handle, and hashed IP accumulate indefinitely.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add a `feedback_retention_days` key to `config/partna.php` (e.g. 730 days, matching the pattern used for `early_access.retention_days`).
        - Add a new scheduled command (mirroring `PruneEarlyAccessSignupsCommand`'s shape) that hard-deletes/redacts feedback older than the window and hasn't been actioned by staff, and register it in `routes/console.php` alongside the other weekly Sunday sweeps.
    - **Technical:** Verified — `config/partna.php`'s `feedback` block declares `notify_emails`, rate limits, `duplicate_window_seconds`, and `ip_hash_pepper`, but no retention key. Verified via `Grep` across all 36 files in `app/Console/Commands/` (plus `routes/console.php`) that no feedback-specific prune command exists — `partna:purge-soft-deletes` only reaches feedback rows staff have explicitly soft-deleted as spam; legitimate feedback that sits in the triage queue un-deleted has no expiry path at all. This stands out against the rest of the codebase, which has a scheduled prune for essentially every other PII-bearing table (`early-access:prune-old-signups`, `notifications:prune-unsubscribed-subscriptions`, `handles:prune-audit-logs`, `moderation:prune-resolved-signal-pii`) — feedback is the one gap in an otherwise-consistent retention pattern.
    - **Plain English:** When someone sends product feedback, it includes their email and username. If staff mark it as spam, it's cleaned up after 30 days. But feedback that's just read and left in the queue is kept forever, with no expiration date — like a suggestion box where cards are never cleared out. Every other type of personal data in this system already has a "shred by this date" rule; feedback is the one exception.
    - **Evidence:**
        ```php
        'feedback' => [
            'notify_emails' => array_values(array_filter(array_map(
                'trim',
                explode(',', (string) env('FEEDBACK_NOTIFY_EMAILS', ''))
            ))),
            'rate_limit_per_hour' => (int) env('FEEDBACK_RATE_LIMIT_HOUR', 10),
            'rate_limit_per_day' => (int) env('FEEDBACK_RATE_LIMIT_DAY', 30),
            'duplicate_window_seconds' => (int) env('FEEDBACK_DUPLICATE_WINDOW', 60),
            'ip_hash_pepper' => env('FEEDBACK_IP_HASH_PEPPER'),
            'max_message_length' => 5000,
        ],
        ```

## P3 — Nice to have

- [ ] **#CFG-2** · P3 — Horizon dashboard domain unset means `/horizon` is reachable from every visitor subdomain, not one admin host
    - **Where:** config/horizon.php:6
    - **Affects:** Attack-surface reduction for the Horizon dashboard. Not an open dashboard in production (verified — see below), but a wider brute-force surface than necessary.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Set `HORIZON_DOMAIN` in every environment to a dedicated admin host (e.g. `ops.partna.au`) so `/horizon` isn't registered against every `<handle>.partna.au` request.
        - Add `HORIZON_DOMAIN` to `.env.example` with a comment explaining the scoping intent.
    - **Technical:** Verified against `AppServiceProvider::authorizeHorizonRequest()` (app/Providers/AppServiceProvider.php:334-349): this is **not** the open-dashboard risk DeepSeek's draft described — in production, when `HORIZON_DASHBOARD_USERNAME`/`PASSWORD` are unset the gate returns `false` (sealed); it only opens unconditionally in non-production ("dev/staging convenience," per the code comment). The real, narrower gap: an unset `HORIZON_DOMAIN` means `Route::domain(null)`, which registers `/horizon` against *any* incoming Host header — including every professional's own subdomain — rather than one dedicated admin host. In production this extra surface is still gated by the Basic-auth callback, so it's hardening (reduce where a credential brute-force could be attempted from), not a live bypass.
    - **Plain English:** The Horizon dashboard is a control panel for background jobs. Right now, its front door can be reached through any professional's mini-website address instead of one dedicated staff entrance — like a back office reachable from every shopfront in a mall instead of its own door. There's still a lock on that door in production, so a stranger can't walk in without a password, but the door itself shouldn't be reachable from everywhere. Giving it one specific address closes off unnecessary exposure.
    - **Evidence:**
        ```php
        'domain' => env('HORIZON_DOMAIN'),
        ```
        ```php
        // app/Providers/AppServiceProvider.php — verified actual behavior
        public static function authorizeHorizonRequest(Request $request): bool
        {
            if (! app()->isProduction()) {
                return true;
            }
            $expectedUser = (string) config('horizon.dashboard.username', '');
            $expectedPassword = (string) config('horizon.dashboard.password', '');
            // Unset credentials = sealed prod (matches prior behavior).
            if ($expectedUser === '' || $expectedPassword === '') {
                return false;
            }
        ```
