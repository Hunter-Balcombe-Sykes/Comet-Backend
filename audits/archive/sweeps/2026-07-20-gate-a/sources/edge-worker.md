## P2 — Should fix

- [ ] **EDGE-1** · P2 — `Vary` header from origin isn't sanitized before the response is written to the edge cache
    - **Where:** cloudflare-worker/src/index.js:214-239 (`withCacheTtl`)
    - **Affects:** Cache efficiency and defense-in-depth against accidental personalization leakage on public sitepage responses.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - In `withCacheTtl`, delete/override the `Vary` header on the cloned response before it's stored, so the edge cache is never keyed on visitor-specific request headers.
        - Add a regression test asserting a cached response never carries a `Vary` header other than (at most) `Accept-Encoding`.
    - **Technical:** `withCacheTtl` clones the origin response's headers, strips `Set-Cookie`, and rewrites `Cache-Control`, but never touches `Vary`. Cloudflare's Cache API keys subsequent `cache.match()` lookups against any `Vary` header present on the stored response. Partna's sitepages are meant to be visitor-agnostic (per `AI_CONTEXT.md`/CLAUDE.md, auth is Supabase JWT via `Authorization` header, not session cookies), so nothing in the documented architecture currently causes the Astro origin (`partna-monorepo/apps/pages`, out of this repo) to emit `Vary: Cookie` or similar. Because that origin isn't in this repo, the risk can't be confirmed either way — this is a cheap edge-side normalization that closes the gap regardless of what the origin currently does.
    - **Plain English:** When the edge server stores a copy of a page, it can be told by the origin website "store a different copy depending on this visitor detail." Right now the edge server would honor that instruction blindly if the origin ever sent it, even though our pages are supposed to look the same for everyone. Stripping that instruction at the door means the edge server always treats the page as one shared copy, which is what we actually want.
    - **Evidence:**
        ```javascript
        async function withCacheTtl(response, ttlSeconds) {
          const body = await response.clone().arrayBuffer();
          const headers = new Headers(response.headers);

          // EDGE-1: a cached copy must never carry a per-visitor cookie.
          headers.delete("Set-Cookie");

          const original = headers.get("Cache-Control") ?? "";
          const directives = original
            .split(",")
            .map((s) => s.trim())
            .filter((s) => s.length > 0 && !s.toLowerCase().startsWith("s-maxage="));
          directives.push(`s-maxage=${ttlSeconds}`);
          if (!directives.some((d) => d.toLowerCase() === "public")) {
            directives.unshift("public");
          }
          headers.set("Cache-Control", directives.join(", "));

          return new Response(body, {
            status: response.status,
            statusText: response.statusText,
            headers,
          });
        }
        ```

    - **Effort:** M (~2–4h)

DeepSeek's proposed fix — fetching the list from a live backend endpoint on Worker startup — would add a network dependency to the highest-traffic code path in the system; a CI-time diff check achieves the same "single source of truth" goal without that risk.

That list is written twice: once in the backend, once in the edge router. Today they match exactly, but nothing stops them from drifting apart the next time someone updates one and forgets the other. Instead of having the edge router phone home on every single visitor request to check the list (which would slow down every page load), the fix is to have an automated check that catches the two lists disagreeing before it ever ships.

- [ ] **EDGE-2** · P2 — Visitor `Cookie`/`Authorization` headers are forwarded unfiltered to the sitepage origin
    - **Where:** cloudflare-worker/src/index.js:342-349 (`withHandleHeader`), :366 (call site in `serveIndividual`)
    - **Affects:** Defense-in-depth for every visitor to a cached public sitepage — a belt-and-braces guard against the origin ever using request credentials to vary rendering.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - In `withHandleHeader` (or immediately before the `PARTNA_PAGES.fetch` calls), delete `Cookie` and `Authorization` from the forwarded request headers alongside the existing `x-partna-handle` stripping.
        - Add a test asserting the request forwarded to `PARTNA_PAGES` never carries either header regardless of what the inbound request had.
    - **Technical:** `withHandleHeader` only deletes/re-sets `x-partna-handle`; every other inbound header, including `Cookie` and `Authorization`, passes through to `env.PARTNA_PAGES.fetch(originRequest)` untouched, and a GET response from that origin can be written into the shared edge cache. DeepSeek's draft tiered this P0 on the premise that the origin "might" use those headers to personalize rendering, which would let one visitor's session leak into everyone's cached copy. That premise doesn't hold up against this codebase's documented architecture: Partna authenticates via Supabase JWT passed as `Authorization`, not session cookies (CLAUDE.md, "Partna uses JWT, not session cookies"), and normal browser page navigation to a public sitepage doesn't attach an `Authorization` header at all — only explicit JS calls do. The one plausible cross-origin path (the `/account/design` preview iframe from `app.partna.au`, per the CSP `frame-ancestors` comment at line 284) is already gated by an explicit `?architecture=`/`?skeleton=` query param that's excluded from caching (lines 372-375), not by cookies. There is no code path in this repo showing the origin varies rendering on inbound credentials — this is hardening against a mechanism that doesn't currently exist, which is the P2 bar, not a live P0.
    - **Plain English:** When the edge router asks the page-building system for a sitepage, it currently forwards along anything the visitor's browser sent, including private login information if any happened to be present. Nothing today actually uses that private information to change what gets shown — Partna's login system doesn't work that way for public pages — but it's cheap insurance to strip it out before forwarding, so a future change elsewhere can't accidentally turn this into a real problem.
    - **Evidence:**
        ```javascript
        function withHandleHeader(request, handle) {
          const headers = new Headers(request.headers);
          headers.delete("x-partna-handle");
          if (handle) {
            headers.set("x-partna-handle", handle);
          }
          return new Request(request, {headers});
        }
        ```

- [ ] **CFG-2** · P3 — Production domain is a hardcoded constant with a half-wired staging environment already in the repo
    - **Where:** cloudflare-worker/src/index.js:42 (`PARTNA_DOMAIN`) · cloudflare-worker/wrangler.toml:37-53 (`[env.staging]`)
    - **Affects:** Subdomain routing/redirect validation correctness if a staging deploy of this Worker is ever exercised against a non-`partna.au` hostname.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Replace `const PARTNA_DOMAIN = "partna.au";` with `env.PARTNA_DOMAIN` bound via `wrangler.toml` `[vars]`, defaulting to `"partna.au"` for production and overridden under `[env.staging]` if staging ever serves a different domain.
    - **Technical:** `wrangler.toml` already defines a real `[env.staging]` block (separate `PARTNA_PAGES` service binding `partna-pages-staging`, and a dedicated `SUBDOMAIN_KV` namespace flagged EDGE-10 specifically to stop a staging deploy poisoning the production KV table) — so this isn't hypothetical, staging deploys of this Worker are an active, partially-built concern in this repo. That said, the staging KV namespace ids are still literal placeholders (`REPLACE_WITH_STAGING_KV_NAMESPACE_ID`) with a `TODO(josh)` marker, confirming staging isn't fully wired yet — hence P3, not higher. If/when staging is completed and ever serves under a hostname other than `*.partna.au`, every `hostname.endsWith("." + PARTNA_DOMAIN)` check, the reserved-subdomain gate, and the alias-redirect host validation would silently misbehave.
    - **Plain English:** The edge router has the real production web address hardcoded everywhere it needs to know "is this our domain." The project's config file already has a half-built staging setup with its own settings — so if that ever gets finished with a different address, the router would still be checking against the production address only, breaking its own routing logic on staging.

- [ ] **PRIV-1** · P3 — Worker error logs include the raw handle/hostname/URL in structured fields
    - **Where:** cloudflare-worker/src/index.js:324, 329, 436, 457, 491 (five `console.error` call-sites)
    - **Affects:** Minimal — the handle/hostname is the visitor's own public URL, already visible to Cloudflare on every request by nature of using it as a CDN; this is a hygiene tightening, not a new exposure.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Where practical, keep the identifier out of the structured log field (log a truncated/hashed form) while retaining enough breadcrumb (status, error message) to debug KV/cache failures.
    - **Technical:** All five call-sites pass `subdomain`, `hostname`, or `cacheKey.url` (which embeds the handle as the URL's host) into `console.error`, which lands in Cloudflare's own Worker log/tail pipeline. The handle is a user-chosen, intentionally-public routing identifier — it's the literal contents of the URL bar for every visitor to that site — and Cloudflare already sees every hostname on every request simply by virtue of terminating the connection, so this doesn't introduce a new class of exposure. It's still tidier to keep identifiers out of ad-hoc error-log fields as a matter of hygiene, hence P3 rather than a compliance-risk tier.
    - **Plain English:** When something goes wrong at the edge — a cache write fails, a routing lookup times out — the error note includes the visitor's website address (their own public web address, already shown in every browser that visits it). It's a low-priority tidy-up to leave that detail out of the error note, not a real leak, since that address is already public and already visible to the same infrastructure on every normal page load.
    - **Evidence:**
        ```javascript
        console.error("KV lookup failed", {subdomain, err: String(err)});
        ```
        ```javascript
        console.error("KV custom-domain lookup failed", {hostname, err: String(err)});
        ```
        ```javascript
        console.error("alias redirect parse failed", {subdomain, err: String(err)});
        ```
        ```javascript
        console.error("primary cache.put failed", {url: cacheKey.url, err: String(err)});
        ```
        ```javascript
        console.error("shadow cache.put failed", {url: cacheKey.url, err: String(err)});
        ```
