## P1 — Fix before pilot launch

- [ ] **#EDGE-1** · P1 — Alias 301 redirect in `show()` ships with no `Cache-Control`, unlike its sibling `showByHeader()`
    - **Where:** app/Http/Controllers/Api/PublicSite/PublicSiteController.php:49
    - **Affects:** Visitors following a link/bookmark to a subdomain that has since been renamed (alias hit) via the primary domain-routed path. Browsers that cache the 301 without a validator can strand a returning visitor on the old subdomain permanently — including after that subdomain is later reclaimed by a different professional once the alias's 90-day `expires_at` passes.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add an explicit `Cache-Control` header to the `show()` alias redirect, matching (or intentionally tightening past) `showByHeader()`'s existing `public, max-age=300` policy.
        - Fix together with #EDGE-2 and #CFG-3 (same file, same header) so the two redirect methods converge on one documented policy instead of drifting further apart.
    - **Technical:** `show()`'s alias branch returns `redirect()->to($url, 301)` with no `Cache-Control` header at all (line 49), so browsers fall back to heuristic 301 caching — which several browsers treat as effectively permanent, independent of any server-side edge purge. `showByHeader()`, the parallel header-based fallback for the Next.js proxy, handles the identical alias-redirect case in the same file and already sets `Cache-Control: public, max-age=300` (line 94). A handle rename is the exact documented lifecycle event this alias machinery exists for (`docs/handle-redirects.md`), and the platform explicitly supports a reclaimed handle being claimed by a different user after `expires_at`. A visitor whose browser cached the unheadered 301 has no way to notice the target changed — the request never reaches Partna's origin or the Cloudflare edge again, so no purge job can reach it.
    - **Plain English:** When someone renames their page's web address, we send old visitors a "permanently moved" signal pointing at the new address. One of our two code paths that does this tells the browser "check back every 5 minutes"; the other tells the browser nothing, which most browsers read as "remember this forever." If that address is ever renamed again, or the old one is later given to a different person, anyone using the un-timed path is stuck being sent to the wrong place indefinitely, with no way for us to fix it after the fact.
    - **Evidence:**
        ```php
                    return redirect()->to($url, 301);
        ```

## P2 — Should fix

- [ ] **#PRIV-1** · P2 — Newsletter signup infers and stores a subscriber's real name from their email address without consent
    - **Where:** app/Http/Controllers/Api/PublicSite/PublicEmailSubscriptionController.php:91-92, 122-127
    - **Affects:** Any visitor who subscribes to a professional's mailing list without typing a name — the platform guesses one from their email's local-part and writes it to both `EmailSubscription.full_name` and `Customer.full_name`, the latter visible to the professional in their dashboard.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Only persist `full_name` when `$providedName !== ''`; drop the `inferNameFromEmail()` fallback from the persisted value.
        - If the inferred name is wanted for something like a friendlier confirmation email, compute it at send-time only and never write it back to `EmailSubscription`/`Customer`.
    - **Technical:** When `full_name` isn't provided, `inferNameFromEmail()` parses the email local-part against a curated first-name list and a compound-name heuristic, and the result flows into `$resolvedName`, which is then written to `subscription->full_name` (lines 122-127) and threaded into `upsertMarketingCustomer()`, landing on the `Customer` record the professional sees. This is a deliberately built feature (the code invests real effort in name-matching), not an oversight, so this is a product call rather than a pure bug — but it does create PII (a plausible real name) the subscriber never supplied, attributed with unverified confidence, and exposes it to a third party (the professional) who may not expect to learn a subscriber's name from just an email address.
    - **Plain English:** When someone signs up for a newsletter with only their email, the code tries to guess their real name — for example turning `j.smith@email.com` into "J Smith" — and saves that guess where the professional can see it. The subscriber never actually told us their name, and the guess can be wrong. It's a bit like a shop guessing a customer's name from their email and writing it on a mailing list without asking. This is a genuine, intentionally-built feature, so it's a product decision rather than an emergency fix — but it's worth a deliberate call on whether guessed names should be stored at all.
    - **Evidence:**
        ```php
        $providedName = is_string($data['full_name'] ?? null) ? trim((string) $data['full_name']) : '';
        $resolvedName = $providedName !== '' ? $providedName : $this->inferNameFromEmail($email);
        ```
        ```php
        if ($resolvedName) {
            $existingName = is_string($subscription->full_name ?? null) ? trim((string) $subscription->full_name) : '';
            if ($overwriteName || $existingName === '') {
                $subscription->full_name = $resolvedName;
            }
        }
        ```

- [ ] **#EDGE-2** · P2 — `show()` and `showByHeader()` handle the same alias redirect differently: one preserves the visited path, the other always sends visitors to the homepage
    - **Where:** app/Http/Controllers/Api/PublicSite/PublicSiteController.php:47-49 (`show()`) vs 91-94 (`showByHeader()`)
    - **Affects:** Visitors who land on an aliased (renamed) subdomain via a deep link — behaviour differs depending on which of the two routing paths (direct subdomain DNS vs the Next.js header-based proxy) served the request.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Pick one behaviour and apply it to both: either both preserve `$request->getRequestUri()` (better UX — a bookmarked deep link keeps working after a rename) or both hard-redirect to `/`.
        - While unifying, also unify the `Cache-Control` header per #EDGE-1/#CFG-3 so this becomes one documented redirect policy instead of two.
        - Consider adding the same explicit `is_published` gate `showByHeader()` already has (`Site::query()->where('is_published', true)->find(...)`) to `show()`'s branch, even though it's currently covered indirectly via `getPublicSitePayload()` returning null for unpublished sites.
    - **Technical:** `show()` builds the redirect target as `$host.$request->getRequestUri()`, preserving the full path and query string; `showByHeader()` builds it as `$host.'/'`, always landing on the homepage. Both are resolving the identical alias-lookup case for the same underlying resource — they just arrive at the controller via different routing (domain-based vs `X-Site-Subdomain` header, used by the Next.js proxy for path-based routing). A visitor with a bookmarked deep link under a renamed handle gets a materially different experience depending on which path served their request, which is confusing but not a security issue — hence P2, not P1.
    - **Plain English:** There are two "front doors" that handle someone visiting a renamed page's old address — one for regular domain visits, one for a proxy path used by the frontend. One door remembers exactly which page the visitor wanted and sends them straight there; the other always drops them on the homepage, losing the deep link. They should behave the same way.
    - **Evidence:**
        ```php
                    $url = $request->getScheme().'://'.$host.$request->getRequestUri();

                    return redirect()->to($url, 301);
        ```
        ```php
                $url = $request->getScheme().'://'.$host.'/';

                return redirect()->to($url, 301)->header('Cache-Control', 'public, max-age=300');
        ```
