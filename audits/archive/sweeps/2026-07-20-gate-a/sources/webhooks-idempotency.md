## P1 — Fix before pilot launch

- [ ] **WHK-1** · P1 — Auth-hook idempotency short-circuit always replays `continue`, silently converting a lost REJECT into an allow on Supabase's retry
    - **Where:** app/Http/Controllers/Api/Webhooks/SupabaseAuthHookController.php:53-59 (dedup short-circuit), :108-123 (reject decision)
    - **Affects:** Users under active brute-force MFA attack — if the original REJECT response never reaches Supabase (timeout, network partition, worker recycle between response-flush and Supabase's receipt), the mandatory retry hits the dedup cache and gets an unconditional `continue`, promoting the session to AAL2 despite the brute-force threshold already being crossed.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Store the decision alongside the anchor (e.g. `Cache::put("supabase:auth-hook:decision:{$id}", 'reject', $ttl)` immediately before returning the reject JSON, `'continue'` before the continue paths) and read it back on the dedup-hit branch instead of hardcoding `['decision' => 'continue']`.
        - Default to `continue` only when no stored decision is found (matches today's behavior for the benign "duplicate of a success" case).
        - Add an `AuthFactorEventRepository` metadata note (or a distinct event type) when a decision is served from replay, so the forensic trail in `audit.auth_factor_events` distinguishes "original reject" from "replayed reject" — useful when investigating a brute-force incident later.
    - **Technical:** The dedup guard at line 53 (`Cache::add("supabase:auth-hook:{$id}", true, ttl)`) only records *that* a webhook-id was processed, not *what* was decided. The existing `WHK-1`-labeled comment in the file (added by a prior audit round) already reverts this anchor via `Cache::forget` when the repository call throws — but that only covers the DB-outage case. It does not cover the case where `record()`/`countRecentFailures()` both succeed, the reject JSON is correctly returned (line 119-122), and the response is then lost in transit before Supabase reads it. Supabase's mandatory retry re-sends the same `webhook-id`; `Cache::add` returns `false` (the key already exists from the first attempt); the controller unconditionally returns `{decision: continue}` at line 58 — regardless of what was actually decided the first time. Because the auth hook is synchronous and Supabase acts on whichever response it receives, this flips a correctly-computed reject into an allow with no DB inconsistency to signal it (the `verify_rejected_by_hook` row is still there — only the live session's fate diverges from it).
    - **Plain English:** Picture a bouncer who, the moment someone fails an ID check, stamps "DENIED" in a logbook and tells the front desk. If that message to the front desk gets lost — say the phone line drops — and the front desk calls back asking "did you already check this person?", the bouncer currently just says "yep, already checked" without repeating what the answer was. The front desk waves the person through by default. The logbook is correct, but the person who should have been turned away is already inside. The fix is simple: the bouncer should repeat the actual answer ("DENIED"), not just confirm that a check happened.
    - **Evidence:**
        ```php
        if (! Cache::add(
            "supabase:auth-hook:{$id}",
            true,
            (int) config('partna.cache.ttls.webhook_idempotency'),
        )) {
            return response()->json(['decision' => 'continue']);
        }
        ```
        ```php
        if ($recentFailures >= $maxFailures) {
            $this->repo->record(
                userId: $userId,
                eventType: 'verify_rejected_by_hook',
                factorId: $factorId,
                factorType: $factorType,
                ip: $ip,
                userAgent: $userAgent,
                metadata: ['recent_failures' => $recentFailures, 'window_seconds' => $windowSeconds],
            );

            return response()->json([
                'decision' => 'reject',
                'message' => 'Too many failed verification attempts. Try again in '.ceil($windowSeconds / 60).' minutes.',
            ]);
        }
        ```

## P2 — Should fix

- [ ] **CCH-1** · P2 — JWKS-outage throttle lock relies on the default cache store resolving to the `cache_locks` connection instead of pinning explicitly
    - **Where:** app/Http/Middleware/Auth/VerifySupabaseJwt.php (in `jwksOutage()`)
    - **Affects:** Nightwatch alert throttling during a sustained JWKS infrastructure outage. Correct today, but the guarantee is implicit — a future change to `CACHE_STORE` (e.g. a queue-worker-only container defaulting to `database`) silently moves this lock off the isolated connection with no error, and a `Cache::flush()` on that other store could then release it mid-outage, flooding Nightwatch with duplicate reports.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Replace `Cache::lock('jwt:jwks-failure-reported', 60)` with `Cache::store('cache_locks')->lock('jwt:jwks-failure-reported', 60)` so the isolation is enforced at the call site, not inferred from config.
        - No config change needed — `config/cache.php` already sets `'lock_connection' => env('REDIS_CACHE_LOCK_CONNECTION', 'cache_locks')` on the `redis` store and `CACHE_STORE` defaults to `redis` — but the explicit pin removes the dependency on that chain staying intact.
    - **Technical:** Verified against `config/cache.php`: `'default' => env('CACHE_STORE', 'redis')` (line 18) and the `redis` store's `'lock_connection' => env('REDIS_CACHE_LOCK_CONNECTION', 'cache_locks')` (line 80, comment: "Isolated DB so Cache::flush() on the data connection never releases locks held by in-flight workers"). So the code comment's claim is accurate *today*. But `Cache::lock(...)` at the call site delegates to whatever the default store resolves to at call time — it does not pin `cache_locks` itself. The `apcuStore()` method in the same file already avoids this by calling `Cache::store('cache_locks')->add(...)` directly (verified verbatim in the file). This one `Cache::lock()` call is the outlier that still depends on the config chain rather than being self-documenting.
    - **Plain English:** Think of this lock as a "don't send another alert for 60 seconds" sticky note. The note is currently on a separate, locked corkboard — but only because the whiteboard on the wall happens to point to that corkboard right now. If someone repoints the whiteboard later, the note silently ends up back on the shared whiteboard, where erasing it (unrelated cache-clearing elsewhere) can trigger a flood of duplicate alerts during exactly the kind of outage this throttle exists to protect against. Sticking the note directly to the corkboard removes that dependency entirely.
    - **Evidence:**
        ```php
        try {
            $lock = Cache::lock('jwt:jwks-failure-reported', 60);
            if ($lock->get()) {
                report($outage);
            }
        } catch (\Throwable) {
            // Throttle layer unreachable — surface the outage anyway.
            report($outage);
        }
        ```

- [ ] **WHK-2** · P2 — Email-hook dedup TTL is hardcoded 300s, duplicated (not shared) with the signature verifier's replay-tolerance window
    - **Where:** app/Http/Controllers/Api/Internal/SupabaseEmailHookController.php:82
    - **Affects:** Email hook resilience — a future change to `StandardWebhookVerifier::TIMESTAMP_TOLERANCE` without a matching change here opens a window where a validly-signed replay can re-acquire the dedup anchor and re-queue an already-sent auth email (OTP, password reset, magic link, invite).
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Source the TTL from `config('partna.cache.ttls.webhook_idempotency')`, matching the pattern the auth hook already uses at `SupabaseAuthHookController.php:56` — or, if the 300s figure must stay pinned to the signature tolerance specifically (not the 24h general webhook-idempotency TTL), reference `StandardWebhookVerifier::TIMESTAMP_TOLERANCE` directly so the two values can't drift apart.
        - Document in a comment which of the two options was chosen and why (dedup-anchor lifetime vs. signature-replay window are different concerns that currently happen to share a number).
    - **Technical:** Verified verbatim: `SupabaseEmailHookController.php:82` uses `now()->addSeconds(300)`; `StandardWebhookVerifier::TIMESTAMP_TOLERANCE` is a separate `private const` also `300`. They are in sync today, and the accompanying comment (lines 76-80) correctly explains that a replay outside the tolerance window fails signature verification before it can reach the dedup check — so the two values being equal is intentional. But nothing enforces that; they're two independent literals in two different files. The auth hook already avoids this exact drift risk by reading its TTL from `config('partna.cache.ttls.webhook_idempotency')` (confirmed present in `config/partna.php:1583`, default 86400s) rather than hardcoding it — the email hook should follow the same pattern, or explicitly reference the verifier's constant.
    - **Plain English:** Two deadbolts on the same door are both currently set to auto-lock after 5 minutes, so the door stays secure. But they're not physically linked — someone could adjust one to 10 minutes later without touching the other, opening a 5-minute gap where an old key still works. Since the code doesn't tie the two timers together, whether they stay matched depends entirely on whoever edits one of these files remembering to edit the other.

        // Signature verifier — also 300 but in a different file:
        private const TIMESTAMP_TOLERANCE = 300;

        (int) config('partna.cache.ttls.webhook_idempotency'),
