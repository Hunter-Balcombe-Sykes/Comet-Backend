## P1 — Fix before pilot launch

- [ ] **#PRIV-1** · P1 — `Customer::redact()` cascade skips `LeadSubmission`, leaving visitor PII behind after a redaction
    - **Where:** app/Models/Core/User/Customer.php (`redact()` method)
    - **Affects:** Every customer a professional redacts — the linked lead-capture telemetry (hashed IP, browser fingerprint) is never scrubbed even though the customer's own record and every linked enquiry are.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add a bulk `LeadSubmission::where('customer_id', $this->id)->update(['ip_hash' => null, 'user_agent' => null, 'referrer' => null])` call inside `Customer::redact()`, following the exact bulk-UPDATE pattern already used for `Enquiry` in the same method (SCALE-4 style — one UPDATE, not N loads).
        - Add a test asserting `$customer->redact()` scrubs both linked `Enquiry` rows AND linked `LeadSubmission` rows for that customer.
    - **Technical:** `Customer::redact()` already bulk-redacts every linked `Enquiry` (nulling `name`/`email`/`phone`/`message`/`ip_hash`/`user_agent`) and scrubs the linked notification's title/body — a deliberate, already-optimized pattern (the method's own comment references the prior SCALE-4 fix that replaced N per-row `Enquiry::redact()` calls with one bulk UPDATE). `analytics.lead_submissions` carries the same `customer_id` FK and the same `ip_hash`/`user_agent` PII columns (confirmed in `app/Models/Analytics/LeadSubmission.php`'s `$fillable`), but the cascade stops at `Enquiry` — `LeadSubmission` rows tied to a redacted customer are never touched. This is a genuine, verified completeness gap in an established and otherwise-correct redaction cascade, not a hypothetical.
    - **Plain English:** When a professional deletes a customer from their records, our system already scrubs every enquiry that customer ever sent. But it forgets to scrub the separate lead-capture record — the log entry created the moment that visitor first filled out a form, holding their hashed IP address and browser fingerprint. It's like shredding the main file but leaving a carbon copy on the desk.
    - **Evidence:**
        ```php
        // From Customer::redact() — Enquiries handled in bulk, LeadSubmission absent:
        Enquiry::where('customer_id', $this->id)->update([
            'name' => null,
            'email' => null,
            'phone' => null,
            'message' => null,
            'ip_hash' => null,
            'user_agent' => null,
            'redacted_at' => now(),
        ]);

        // app/Models/Analytics/LeadSubmission.php — same FK, same PII, not touched:
        protected $fillable = [
            'occurred_at',
            'subdomain',
            'site_id',
            'user_id',
            'customer_id',
            'ip_hash',
            'user_agent',
            'referrer',
            'outcome',
            'form_started_at_ms',
        ];
        ```

## P2 — Should fix

- [ ] **#SEC-1** · P2 — Eleven models declare permissive mass-assignment (`$guarded = ['id']`, `$guarded = []`, or `$fillable` including tenancy FKs/system-managed fields), deviating from the codebase's own established doctrine
    - **Where:** app/Models/Moderation/{ActionLogEntry,AuditEvent,CaseSignal,Decision,Evidence,ModerationCase}.php (`$guarded = ['id']`); app/Models/Core/Site/ContentSelection.php, app/Models/Core/Site/Enquiry.php, app/Models/Core/Feedback.php, app/Models/Core/User/User.php, app/Models/Core/Site/IntegrationConnection.php, app/Models/Core/Notifications/EmailSubscription.php, app/Models/Core/EarlyAccess/EarlyAccessSignup.php, app/Models/Core/Site/Block.php (`$fillable` includes tenancy FK or system-managed columns); app/Models/Views/{AllSiteData,PublicSitePayload}.php (`$guarded = []`)
    - **Affects:** Defense-in-depth only today — every currently-reachable write path was individually verified safe (see Technical). The risk is to future maintainers: any new endpoint, staff script, or refactor that calls `Model::create($request->all())` on one of these 11 models would cross a tenant boundary with no structural guard.
    - **Effort:** L (~1–2d) — touches 11 files, several with call sites that construct these models via array-literal for the **skeleton authorization pattern** (see Technical), which must be migrated to explicit property assignment rather than deleted outright, plus test fixtures that construct rows the same way.
    - **What to do:**
        - Replace `$guarded = ['id']` with an explicit `$fillable` allowlist on the six moderation models; replace `$guarded = []` with `$guarded = ['*']` on the two read-only view models (they have no write path — this just makes the read-only intent fail-fast instead of silently permissive).
        - Remove the tenancy FK / system-managed columns from `$fillable` on `ContentSelection` (`site_id`), `Enquiry` (`user_id`, `site_id`, `status`, `notification_id`, `customer_id`), `Feedback` (`user_id`, `status`, `internal_notes`, `tags`), `User` (`status`, `handle`, `admin_notes`, `deletion_token_hash`, `deletion_requested_at`, `deletion_confirmed_at`, `deletion_previous_status`, `deletion_mail_sent_at` — **keep `account_type` and `primary_email` fillable, they are legitimate user-settable fields**, see Technical), `IntegrationConnection` (`user_id`), `EmailSubscription` (`user_id`, `email_lc`), `EarlyAccessSignup` (`status`, `invited_at`, `invite_token_hash`, `invite_meta`, `invited_by`, `signed_up_at`), and `Block` (`user_id`, `site_id`) — mirroring the exclusion pattern already documented in `SiteMedia.php`, `PartnaStaff.php`, and `DesignKitContribution.php`.
        - **Before deleting**, grep every `new Block([...])` / `new IntegrationConnection([...])` skeleton-pattern call site (e.g. `UserLinkBlockController::store()` line 71: `new Block(['user_id' => $pro->id, 'site_id' => $site->id])`) and switch each to explicit property assignment (`$skeleton->user_id = $pro->id; $skeleton->site_id = $site->id;`) so the pre-create policy check still receives the values it needs — a blind field removal would silently break ownership checks on these skeletons.
        - Update the handful of tests that construct rows directly via array literal (`ContentSelectionTest.php`, `SitePolicyTest.php`) to use explicit assignment or factories instead.
    - **Technical:** This codebase has an established doctrine — visible verbatim in `SiteMedia.php` ("`site_id` is the tenancy FK — deliberately excluded from mass-assignment (SEC-1)") and `PartnaStaff.php` ("Mass-assignment posture (SEC-1): `role` is intentionally NOT `$fillable`") — of excluding tenancy FKs and system-managed columns from `$fillable`, referencing a prior audit finding. The 11 models above never received that fix. However, every currently-reachable write path was traced and verified NOT exploitable: `ContentSelectionService::persist()` builds rows with `'site_id' => $site->id` hardcoded (never from client input); `PublicEnquiryController::submit()` builds the `Enquiry::create([...])` array explicitly with `user_id`/`site_id` from the server-resolved `$site`, omitting `status`/`notification_id`; `FeedbackService::submit()` never includes `status`/`internal_notes`/`tags` in its `create()` call (staff sets `status` via a separate `updateStatus()` method); `UserSelfController::update()` / `StaffUserController::update()` both call `$model->fill($request->validated())` where the Form Request scopes the array (handle/status/admin_notes/deletion fields are absent from `UpdateUserRequest`'s rules) — note `account_type` IS a legitimate self-service field per the documented "Change account type" flow, so DeepSeek's claim that it's an escalation vector is incorrect; `ManagesIntegrationConnection::writeConnection()` uses `updateOrCreate(['user_id' => $user->id, ...], $values)` with `user_id` in the lookup key, never the payload; `PublicEmailSubscriptionController` sets `email_lc` explicitly from the validated, lower-cased `$email` server-side. Because none of these are live vulnerabilities, this is hardening/consistency work (P2), not an active bypass.
    - **Plain English:** Eleven database tables have a "please take anything" sign on the door — technically anyone filling in a form could try to set fields like "which user owns this" or "what's this account's status." We checked every place these tables actually get written to today, and in every single case the code carefully sets those sensitive fields itself rather than trusting the form. So nobody can exploit this right now. But the sign is still up, and the codebase already has a rule (proven by two other models that fixed this exact issue) saying that sign should come down — so a future shortcut by a rushed developer wouldn't be caught by anything.
    - **Evidence:**
        ```php
        // app/Models/Moderation/ModerationCase.php
        protected $guarded = ['id'];

        // app/Models/Core/Site/ContentSelection.php — contradicts its own docblock
        // ("site_id is the tenancy FK ... intentionally excluded"):
        protected $fillable = [
            'site_id',
            'position',
            'entry_type',
            'media_id',
            'external_ref',
        ];

        // app/Models/Core/User/User.php
        protected $fillable = [
            'handle',
            'display_name',
            // ...
            'status',
            // ...
            'deletion_token_hash',
            'deletion_requested_at',
            'deletion_confirmed_at',
            'deletion_previous_status',
            'deletion_mail_sent_at',
            'admin_notes',
        ];

        // app/Models/Views/AllSiteData.php — read-only view
        protected $guarded = [];
        ```

- [ ] **#PRIV-2** · P2 — `UserDeletionAuditEntry.professional_email_snapshot` has no retention bound or scheduled purge
    - **Where:** app/Models/Core/User/UserDeletionAuditEntry.php
    - **Affects:** Every professional who deletes their account — their plaintext email lives in `audit.user_deletion_audit` indefinitely.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Add a scheduled command mirroring the existing `PruneHandleAuditLogs` pattern (the only place `audit_retention_years` config is currently consulted) that purges/anonymizes `audit.user_deletion_audit` rows past the retention window.
        - Decide and document the retention period (align with `config('partna.audit_retention_years', 7)` used by `PruneHandleAuditLogs`, or a shorter, purpose-specific window).
    - **Technical:** The model's own docblock states these rows deliberately survive the professional's hard-delete ("Rows survive the professional's hard delete via handle/email snapshots captured at write time") — this is a legitimate, intentional design for fraud/dispute investigation, not a bug. `$hidden` correctly prevents serialization leaks. However, unlike `audit.handle_change_log` (which has a dedicated `PruneHandleAuditLogs` command consulting `config('partna.audit_retention_years')`), no equivalent purge command references `UserDeletionAuditEntry` — confirmed by grepping for the model across `app/Console`. The retention is therefore unbounded in practice, not just by design.
    - **Plain English:** When someone deletes their account, we write a log entry noting it happened — including their actual email address. That's reasonable for fraud and dispute investigation. But there's a sibling log (for handle renames) that automatically cleans itself up after several years, and this one doesn't. Their email just sits there forever with no expiry date, even though a similar system elsewhere in the app already knows how to do this correctly.
    - **Evidence:**

        ```php
        /**
        ```

## P3 — Nice to have

- [ ] **#PRIV-4** · P3 — `Enquiry::redact()` leaves `subject` unscrubbed
    - **Where:** app/Models/Core/Site/Enquiry.php (`redact()` method)
    - **Affects:** Enquiry submitters whose subject line happens to contain their name or other identifying context.
    - **Effort:** S (~0.5h)
    - **What to do:** Add `'subject' => null` to the `$this->update([...])` call inside `Enquiry::redact()`.
    - **Technical:** `redact()` thoroughly nulls `name`, `email`, `phone`, `message`, `ip_hash`, `user_agent`, and cascades to the linked notification — but leaves `subject` (a free-text field the submitter fills in) untouched. Minor completeness gap in an otherwise well-structured redaction path.
    - **Plain English:** When we scrub a contact-form message, we blank out the name, email, phone, and message body — but not the subject line. If someone wrote "Hi, it's Sarah" as their subject, Sarah's name survives the scrub.
    - **Evidence:**
        ```php
        // app/Models/Core/Site/Enquiry.php
        public function redact(): void

            $this->update([
                'name' => null,
                'email' => null,
                'phone' => null,
                'message' => null,
                'ip_hash' => null,
                'user_agent' => null,
                'redacted_at' => now(),
            ]);

            if ($this->notification_id) {
                Notification::where('id', $this->notification_id)
                    ->update(['title' => '[redacted]', 'body' => '[redacted]']);
            }
        }
        ```
