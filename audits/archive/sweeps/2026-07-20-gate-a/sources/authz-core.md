## P2 — Should fix

- [ ] **#PRIV-1** · P2 — Auth-factor audit log stores raw IP and User-Agent with no minimisation
    - **Where:** `app/Services/Auth/AuthFactorEventRepository.php` (`record()` method)
    - **Affects:** Every user whose MFA factor events are recorded (enroll / verify / unenroll) — raw IP addresses and full User-Agent strings are persisted indefinitely in `audit.auth_factor_events`, which is an append-only compliance table (`app_backend` has SELECT/INSERT only, no purge grant visible from this schema).
    - **Effort:** M (~2–4h) — this isn't a one-line swap; the reusable minimisation logic in the codebase is currently locked behind `private` visibility (see Technical).
    - **What to do:**
        - Extract IP/UA minimisation into a small shared helper (e.g. a trait or a class in `App\Support`) used by both `TokenRevocationService::trackForUser()` and `AuthFactorEventRepository::record()`. `TokenRevocationService::truncateIp()`, `::parseUaBrowserFamily()`, and `::parseUaPlatform()` are currently `private` instance methods — they cannot be called from `AuthFactorEventRepository` as-is, so a straight "reuse them" fix will not compile.
        - For the IP specifically, prefer `hash_hmac('sha256', $ip, config('app.key'))` (the scheme `HashesClientData` already uses elsewhere) over `TokenRevocationService`'s octet-truncation scheme — `AuthFactorEventRepository::countRecentFailures()` already correlates events by exact match (`user_id` + `factor_id`), and exact-match IP hashing preserves "was this the same source IP across two events" without ever storing the raw address; truncation would blur that signal instead.
        - Keep the change additive: new rows get minimised fields going forward. Do not attempt to rewrite historical rows in an append-only table.
    - **Technical:** `record()` inserts `$ip` and `$userAgent` verbatim (see Evidence). `TokenRevocationService::trackForUser()` — writing to a Redis session-metadata hash for the *same* underlying purpose (auditable client identification on an auth-adjacent event) — already truncates the IP to its network prefix and reduces the UA to a browser-family/platform pair, explicitly citing PII minimisation as the reason. `AuthFactorEventRepository` has no equivalent. Note the tension worth flagging to the fix implementer: `audit.*` is an append-only compliance/forensics schema by design, so full-fidelity IP data has some legitimate investigative value (e.g. correlating an MFA brute-force burst to a known-bad IP range) — hashing preserves correlation without the raw address; truncation would lose more forensic value here than it does for the "Active Sessions" UI use case it was built for.
    - **Plain English:** One part of the system (device/session tracking) is careful to store only a rough summary of where a login came from — not the exact address, not the full description of the device — because keeping less is safer for users. The record kept every time someone sets up, checks, or removes two-factor login, however, keeps the complete address and device fingerprint, forever, in a log designed never to be edited or deleted. That's more personal detail retained than is actually needed for the security purpose the log serves, and it should be trimmed to match the more careful approach already used elsewhere in the same system.
    - **Evidence:**
        ```php
        public function record(
            string $userId,
            string $eventType,
            ?string $factorId = null,
            ?string $factorType = null,
            ?string $sessionId = null,
            ?string $ip = null,
            ?string $userAgent = null,
            array $metadata = [],
        ): string {
            $id = (string) Str::uuid();

            DB::connection('pgsql')->table(self::TABLE)->insert([
                'id' => $id,
                'user_id' => $userId,
                'session_id' => $sessionId,
                'event_type' => $eventType,
                'factor_id' => $factorId,
                'factor_type' => $factorType,
                'ip' => $ip,
                'user_agent' => $userAgent,
                'metadata' => json_encode($metadata),
                'created_at' => now()->toIso8601String(),
            ]);

            return $id;
        }
        ```

## P3 — Nice to have

- [ ] **#SEC-1** · P3 — `EnsurePartnaAdmin`'s staff-lookup fallback is dead code given the app's fixed middleware order
    - **Where:** `app/Http/Middleware/Auth/EnsurePartnaAdmin.php` (`handle()`, the `$staff` fallback query)
    - **Affects:** No live security or correctness impact — this is a redundant-code / maintainability finding, not a bug. Confirmed via `routes/api/staff.php:179`: every `staff.admin`-gated route group is declared as `['supabase.jwt', 'require.email_verified', 'staff', 'require.aal2', 'staff.admin', 'throttle:staff', 'staff.audit']`. Middleware runs in array order, so `EnsurePartnaStaff` (`staff`) always populates the `partna_staff` request attribute before `EnsurePartnaAdmin` (`staff.admin`) runs — the fallback DB query never actually fires in the current codebase.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Delete the fallback query and instead treat a missing `partna_staff` attribute as a hard failure (401/500) — it can only mean `staff.admin` was applied without `staff` first, which is a route-wiring bug, not a normal request path worth silently working around.
        - Optionally add a one-line assertion/test pinning the ordering invariant (`staff` before `staff.admin`) so a future route group can't reintroduce the extra query by accident.
    - **Technical:** DeepSeek's original framing treated this as a live "wasted DB round-trip on some request paths" risk. Having checked the only `staff.admin` route group in the repo, the ordering is fixed and consistent, so the fallback branch is unreachable in practice today — this is a "delete now-dead code" cleanup, not a hardening item. Low value, but harmless to fix opportunistically since it also removes a second, easy-to-drift code path for resolving staff identity (per the codebase's own "single source of truth" principle for staff auth).
    - **Plain English:** There's a check at the front door that verifies you're staff, and a second check further inside that verifies you're an admin. The admin check has a backup plan for "what if nobody checked you're staff yet" — but that backup plan can never actually run, because every admin-only door in the building already has the staff-check standing right in front of it. It's harmless, just unnecessary code that could be removed to keep the "who checks who's staff" logic in exactly one place.
    - **Evidence:**
        ```php
        $staff = $request->attributes->get('partna_staff');

        // If EnsurePartnaStaff ran before this, we already have the staff record
        if (! $staff) {
            $staff = PartnaStaff::query()->where('auth_user_id', $uid)->first();
        }
        ```

- [ ] **#CFG-1** · P3 — Hardcoded HTTP timeouts in `SupabaseAdminService` instead of the existing shared config key
    - **Where:** `app/Services/Auth/SupabaseAdminService.php` (`createUser`, `findUserByEmail`: `->timeout(10)`; `unenrollMfaFactor`: `Http::timeout(5)`)
    - **Affects:** Every outbound call to the Supabase Admin API — server-side user creation during the setup-wizard flow, email-existence lookups for signup-availability checks, and MFA factor unenroll.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Replace the three hardcoded `timeout()` calls with `config('supabase.http_timeout_seconds', 5)`.
        - No config or `.env.example` change is needed — `config/supabase.php:20` already defines `http_timeout_seconds` (backed by `SUPABASE_HTTP_TIMEOUT_SECONDS`), and `VerifySupabaseJwt` already reads it for the JWKS fetch and Auth-Server fallback calls. This is purely a matter of using the key that already exists, not adding a new one.
    - **Technical:** `config/supabase.php` centralises a shared HTTP timeout specifically so "clock-skew tolerance... and the Http client timeout used for both the JWKS fetch and the Auth-Server fallback" stay in one place (per its own inline comment). `SupabaseAdminService` was written before or independently of that consolidation and carries three separate hardcoded values (10, 10, 5) instead. Tuning Supabase Admin API tolerance today means finding three literals scattered across the class instead of one config value.
    - **Plain English:** Part of the app has a single, shared stopwatch setting for "how long to wait before giving up" on calls to Supabase, so it can be tuned in one place. The admin-side calls (creating users, looking up emails, removing two-factor devices) ignore that shared setting and use their own hardcoded numbers instead. If Supabase ever needs more patience during a slow period, someone has to remember to update three separate spots in the code instead of one setting.
    - **Evidence:**
        ```php
        $response = Http::withHeaders($this->headers())
            ->timeout(10)
            ->post("{$this->baseUrl}/auth/v1/admin/users", [
                'email' => $email,
                'email_confirm' => true,
                'user_metadata' => $metadata ?: (object) [],
            ]);
        ```

- [ ] **#CFG-3** · P3 — Platform refresh intervals hardcoded in `PlatformRegistryServiceProvider`
    - **Where:** `app/Providers/PlatformRegistryServiceProvider.php` (multiple `refreshEvery()` calls with arithmetic expressions)
    - **Affects:** The hourly refresh dispatcher for connected platforms — every platform's re-fetch cadence is fixed in source code.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Add per-platform refresh-interval defaults in `config/partna.php` (e.g. `partna.refresh.intervals.<platform>`), mirroring the existing `partna.refresh.rate_limits.*` pattern used a few lines below in the same provider.
        - Replace the hardcoded seconds with config reads, keeping today's values as defaults so no behaviour changes on deploy.
    - **Technical:** Cadences like `6 * 3600` (events), `12 * 3600` (watch/listen content), and `2 * 86400` (Google Business) are literal arithmetic in the provider's `boot()`/`register()` wiring. The provider already establishes the config-driven pattern for the adjacent concept (`config("partna.refresh.rate_limits.{$job->platform}", ...)` in the `platform-refresh` rate limiter), so extending the same pattern to the interval itself is a natural, low-risk follow-on rather than a new architectural decision.
    - **Plain English:** The app checks connected accounts (YouTube, Google Business, ticketing sites, and so on) on a fixed schedule — some every few hours, some every couple of days. Right now that schedule is baked into the code. If something like a busy events weekend calls for faster updates, someone has to edit and redeploy the code rather than just changing a setting.
    - **Evidence:**
        ```php
        $r->get('eventbrite')->refreshEvery(6 * 3600);
        $r->get('humanitix')->refreshEvery(6 * 3600);
        $r->get('shop')->refreshEvery(6 * 3600);
        ...
        $r->get('google-business')->refreshEvery(2 * 86400);
        ```

- [ ] **#CFG-2** · P3 — Several rate limits hardcoded in `AppServiceProvider` instead of config-driven, inconsistent with the pattern already used nearby
    - **Where:** `app/Providers/AppServiceProvider.php` (rate-limiter closures for `analytics`, `analytics-click`, `leads`, `authenticated`, `staff`, `webhooks`, `bootstrap`, `early-access`, `public-subscribe`, `session-writes`, `document-download`)
    - **Affects:** Traffic shaping across public, authenticated, staff, and webhook endpoints — these specific limiters' caps cannot be tuned during a traffic spike or abuse burst without a deploy.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Extract the literal `perMinute(N)`/`perHour(M)` caps in the listed limiters into `config/partna.php` under `partna.throttle.*`, with the current numbers as defaults.
        - Follow the pattern already established in the *same file* — `signup-availability`, `subdomain-availability`, `login-identifier`, and `feedback-submit` already read their caps from `config('partna.throttle.*', ...)`. This finding is about extending that existing pattern consistently, not introducing a new one.
    - **Technical:** The limiters listed hardcode their caps as literal integers (`analytics`: 120/min, `leads`: 3/min + 100/min, `authenticated`/`staff`: 300/min, `webhooks`: 200/min, `bootstrap`/`claim`: 5/min, `early-access`: 5/min + 12/hr, `public-subscribe`: 5/min + 12/hr). Roughly half the limiters in this same `configureRateLimiting()` method already read from `config('partna.throttle.*')` — the inconsistency, not the existence of hardcoding per se, is the finding.
    - **Plain English:** Some doors in the building have a "max people allowed" number painted directly on the wall; others have a dial at the front desk that can be turned up or down. If a specific door needs tightening during an incident — say, a flood of fake login attempts — the ones with a dial can be adjusted immediately, but the painted-on ones need a repaint (a code deploy) first.
    - **Evidence:**
        ```php
        RateLimiter::for('analytics', function (Request $request) use ($throttleEnabled) {
            ...
            return Limit::perMinute(120)
                ->by((string) $key);
        });
        ```
        ```php
        return [
            // Per IP:  3 submissions per minute
            Limit::perMinute(3)
                ->by((string) $key)
            ...
            // Per subdomain: 100 submissions per minute (prevent abuse)
            Limit::perMinute(100)
                ->by($subdomain)
        ```
