## P1 — Fix before pilot launch

- [ ] **#EDGE-1** · P1 — Claim transition never purges the Cloudflare edge cache — visitors can see stale pre-claim content for up to 7 days
    - **Where:** app/Services/PreAccount/ClaimSiteService.php:76-84; app/Observers/User/UserObserver.php:38-43
    - **Affects:** Visitors to any site whose pre-account build was published (staff/ManyChat-triggered marketing builds support `publish=true`) before the professional claimed it. They keep seeing the pre-claim edge-cached render — including any "claim this profile" UI cue — for up to the primary cache TTL, with the SWR stale-shadow extending that window further.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - In `ClaimSiteService::claim()`, after the existing post-commit `SyncSubdomainToKvJob::dispatch(...)` line, add `CloudflareCachePurgeJob::dispatch($handle, $customDomain)->afterCommit()` — mirror `SiteObserver::saved()`'s exact pattern (lower-cased handle, custom domain only when `custom_domain_status === 'active'`).
        - Add a `Queue::assertPushed(CloudflareCachePurgeJob::class, ...)` assertion to `tests/Feature/PreAccount/ClaimSiteServiceTest.php` — verified there is currently no test covering this dispatch, so a future regression would go undetected.
    - **Technical:** `ClaimSiteService::claim()` transitions `status` from `'unclaimed'` to `'active'` via direct property assignment (not mass assignment, so it bypasses `$fillable` — see `SEC-2` below for the model-layer half of this). Verified the observer chain: `UserObserver::updated()` only cascades to `SiteObserver` (which is the ONLY place `CloudflareCachePurgeJob` gets dispatched for a `Site`/`User` mutation) when `wasChanged(self::PUBLIC_PROFILE_USER_FIELDS)` is true, and that constant is `['handle', 'display_name', 'first_name', 'last_name']` — it deliberately excludes `status`. Since claim never touches `handle`/`display_name`/`first_name`/`last_name` (those were already set at build time) and never saves the `Site` row itself, no code path in the repo dispatches an edge purge for a claim event. `ClaimSiteService` already dispatches `SyncSubdomainToKvJob` (routing-table update) and `SiteCacheService::invalidateSite()` (Redis-only), but the Cloudflare Worker's `caches.default` entry — populated with a 24h `s-maxage` plus a 7-day `/_swr-shadow` per the platform's edge-cache doctrine — is untouched. Confirmed via `Grep` that `tests/Feature/PreAccount/ClaimSiteServiceTest.php` fakes the queue and only anticipates `SyncSubdomainToKvJob`, so this gap has no test coverage today.
    - **Plain English:** When someone claims their pre-built profile page, the system updates its internal "who owns this" record and its routing table, but it forgets to tell Cloudflare's edge cache — the fast copy of the page served to visitors around the world — that the page has changed. Anyone who saw the page before the claim keeps seeing that old version, potentially including a "claim this page!" banner, for up to a week after the real owner has already claimed it. It's like renovating a shop but forgetting to update the photo on the storefront directory listing.
    - **Evidence:**
        ```php
        // app/Observers/User/UserObserver.php — PUBLIC_PROFILE_USER_FIELDS excludes 'status'
        private const PUBLIC_PROFILE_USER_FIELDS = [
            'handle',
            'display_name',
            'first_name',
            'last_name',
        ];
        ```
        ```php
        // app/Services/PreAccount/ClaimSiteService.php:76-84 — no CloudflareCachePurgeJob dispatch
        $this->userCache->invalidateUser($result['professional']);
        $this->siteCache->invalidateSite($result['site']);
        SyncSubdomainToKvJob::dispatch((string) $result['professional']->id);

        return $result;
        ```
