- [ ] **#JOB-1** · P1 — `SendEnquiryNotificationJob` silently discards a missing-enquiry permanent failure
    - **Where:** app/Jobs/Notifications/SendEnquiryNotificationJob.php (missing-enquiry branch inside `handle()`)
    - **Affects:** Horizon/Nightwatch observability — a notification email for an enquiry deleted between dispatch and handle vanishes with zero trace of failure.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Replace the `Log::warning` + `return` with `$this->fail(new \RuntimeException('Enquiry not found for notification email'));` when `$enquiry` is null. Keep the `Log::warning` alongside for log-context richness.
    - **Technical:** A missing enquiry (deleted between dispatch and handle) is a permanent, non-transient failure — retrying can't resurrect it. Returning cleanly makes Horizon mark the job "completed" across all `$tries`; Nightwatch alerts on exceptions and auto-detected slow jobs, not on `Log::warning` calls, so this failure mode is invisible to the on-call rotation. `$this->fail()` marks the job failed immediately instead of silently succeeding.
    - **Plain English:** A delivery driver shows up at an empty lot where the house used to be, shrugs, and marks the package "delivered." The sender never finds out it didn't arrive. The fix is to radio back "address doesn't exist" so someone notices.
    - **Evidence:**
        ```php
        if ($enquiry === null) {
            Log::warning('SendEnquiryNotificationJob: enquiry not found', [
                'enquiry_id' => $this->enquiryId,
            ]);

            return;
        }
        ```

- [ ] **#JOB-4** · P1 — `DispatchEnquiryNotificationsJob`'s idempotency guard is non-atomic and sequenced after the side effect it's supposed to guard
    - **Where:** app/Jobs/Notifications/DispatchEnquiryNotificationsJob.php:60-66 (`handle()`)
    - **Affects:** Professionals receiving duplicate in-app/email enquiry notifications on a retry, or (rarer) on a concurrent worker execution.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Replace the `Cache::has()` + late `Cache::put()` pair with a single atomic `Cache::add('enquiry:notified:'.$this->enquiryId, true, now()->addDay())` call, gating the dispatch on its boolean return: `if (! Cache::add(...)) { return; }`.
        - Dispatch the notifications only after the atomic `add()` succeeds, so the marker is committed before the side effect runs, not after.
    - **Technical:** Two related gaps in one guard. First, sequencing: the marker is written *after* `$dispatcher->dispatch()` returns, so a worker that crashes or throws mid-dispatch never writes it — a retry then finds `Cache::has()` false and re-fans-out every adapter (email + in-app) a second time. Second, atomicity: `Cache::has()` (read) and `Cache::put()` (write) are two separate Redis round-trips, so two concurrent executions of the same job (Horizon scale-out, or a manual re-dispatch racing a slow retry) can both pass the `has()` check before either writes the marker. `Cache::add()` (Redis `SETNX`) closes both gaps in one atomic call.
    - **Plain English:** Two kitchen timers go off at the same moment for the same dish. Both cooks check the whiteboard, see "not sent yet," and both plate the dish — the diner gets two identical meals. An atomic check-and-set is like one cook grabbing the marker and writing "claimed" in the same motion the other cook can see before they start cooking.
    - **Evidence:**
        ```php
        // Idempotency guard — a retry after partial success must not re-send the notification.
        if (Cache::has('enquiry:notified:'.$this->enquiryId)) {
            return;
        }

        $dispatcher->dispatch($enquiry, $block);

        Cache::put('enquiry:notified:'.$this->enquiryId, true, now()->addDay());
        ```

- [ ] **#TXN-1** · P1 — Redis blocklist write runs inside a DB transaction, breaking atomicity on rollback
    - **Where:** app/Http/Controllers/Api/User/Customers/UserEnquiryController.php (`markSpam()`, `DB::transaction` closure)
    - **Affects:** Spam-marking action for the enquiry inbox — the professional's Redis blocklist and the enquiry's DB status can drift apart under a transaction failure.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Move the `EnquirySpamBlocklist::add()` call outside the `DB::transaction` closure and dispatch it via `DB::afterCommit(fn () => ...)` so the Redis write only fires once the DB changes are durably committed.
        - Wrap the after-commit write in its own try/catch (see LIFE-2) so a Redis failure there doesn't surface as a request-level error after the response has effectively already succeeded.
    - **Technical:** `Redis::zadd()` (inside `EnquirySpamBlocklist::add()`) is not part of the Postgres transaction. If `DB::commit()` itself fails after the closure body has already run — a deadlock on the `Customer::lockForUpdate()` row, a constraint violation — the Redis write may have already gone through while the DB status change rolls back, leaving the blocklist entry live with no corresponding spam record to explain it. `config('queue.default')`'s `after_commit` is `false` platform-wide, so there's no blanket safety net; every external write inside a transaction must be explicitly deferred.
    - **Plain English:** Marking an enquiry as spam is like writing someone's name on a blacklist and putting a "spam" sticker on their envelope. If you write on the blacklist but the sticker step then fails and gets undone, your blacklist says "blocked" with no record explaining why — and later messages from that sender get silently discarded with no trace of the decision. Finish sealing the envelope first, then write on the blacklist.
    - **Evidence:**
        ```php
        DB::transaction(function () use ($enquiry, $user) {
            $enquiry->markSpam();

            if ($enquiry->customer_id) {
                $customer = Customer::whereKey($enquiry->customer_id)

                    ->first();

                if ($customer && $customer->source === 'enquiry') {
                    $hasOtherEnquiries = Enquiry::query()
                        ->where('customer_id', $customer->id)
                        ->where('id', '!=', $enquiry->id)
                        ->exists();

                    $hasSubscription = EmailSubscription::query()
                        ->where('user_id', (string) $user->id)
                        ->whereRaw('lower(email) = ?', [strtolower((string) $customer->email)])
                        ->exists();

                    if (! $hasOtherEnquiries && ! $hasSubscription && empty($customer->external_id)) {
                        $customer->delete();
                    }
                }
            }

            app(EnquirySpamBlocklist::class)
                ->add((string) $user->id, (string) $enquiry->email);
        });
        ```

- [ ] **#WHK-1** · P1 — `EnquiryNotificationDispatcher` swallows per-adapter failures; the job then reports success and no channel is ever retried
    - **Where:** app/Services/Notifications/EnquiryNotificationDispatcher.php:35-49; app/Jobs/Notifications/DispatchEnquiryNotificationsJob.php (`handle()`)
    - **Affects:** Professionals who enable email and/or in-app enquiry notifications — a transient adapter failure (Redis down when the email adapter queues `SendEnquiryNotificationJob`, a `NotificationPublisher` DB error) is caught, `report()`'d, and the job still completes normally, so the failed channel is permanently dropped and Horizon's failed-job counter never reflects it.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - In the dispatch loop, collect which adapters threw instead of only reporting and continuing.
        - After the loop, if any adapter failed, throw (re-throw the first captured exception, or a composite) so `DispatchEnquiryNotificationsJob::handle()` sees a real exception — its existing `$tries = 3` / `backoff` will retry, and a genuine permanent failure will surface via `failed()`.

    - **Plain English:** You hand a courier three envelopes — one for the in-app bell, one for email, one for a future channel. The courier drops the email envelope in a puddle, shrugs, and tells you "all delivered!" You never learn the email never arrived, and nobody ever tries again.
    - **Evidence:**

            try {
                $adapter->dispatch($enquiry, $block);
