- [ ] **#DINT-1** · P2 — Session heartbeat upsert silently drops rows on a session-ID collision across two different sites
    - **Where:** app/Services/Analytics/Writers/PostgresEventWriter.php, `upsertSession()`
    - **Affects:** Session/duration/live-visitor tracking for any two sites that happen to receive a ping carrying the same client-minted session UUID (e.g. a bug in the frontend tracker reusing a session ID across subdomains, rather than a realistic UUID-guessing attack).
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Change the primary key to a composite `(id, site_id)` (migration + unique constraint change) so the same client-minted UUID on two different sites is never treated as the same row.
    - **Technical:** `INSERT ... ON CONFLICT (id) DO UPDATE ... WHERE site_sessions.site_id = EXCLUDED.site_id` — in Postgres, when a row conflicts on the PK but the `WHERE` condition evaluates false, **both** the UPDATE and the (already-blocked) INSERT are skipped: the write is a silent no-op. The `WHERE` clause guards against writing into a different site's session row, but its side effect is that the second site's ping is dropped entirely rather than being recorded under its own identity. This requires a session-UUID collision across two different sites, which is astronomically unlikely for a properly-random client-generated UUID and not currently an attacker-controlled input — hence P2 rather than P0/P1 — but a composite key removes the possibility entirely rather than relying on UUID randomness.
    - **Plain English:** Each visitor session gets a unique ticket number generated by their browser. The database's "update this session" logic assumes ticket numbers are only ever reused by the SAME site. If two different sites' visitors ever ended up with the same ticket number, the second one's ping would be silently thrown away instead of recorded, with no error anywhere. This isn't something an attacker can easily trigger today, but it's a real gap in an assumption the code is making.
    - **Evidence:**
        ```php
        DB::connection('pgsql')->statement(
            "INSERT INTO analytics.site_sessions
                (id, user_id, site_id, visitor_id, started_at, last_seen_at, duration_seconds,
                 country_code, region_code, device_type, referrer, created_at)
             VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)
             ON CONFLICT (id) DO UPDATE SET
        ```
