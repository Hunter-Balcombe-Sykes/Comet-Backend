## P1 — Fix before pilot launch

- [ ] **#MONEY-1** · P1 — A billed effect that succeeds is mislabeled 'failed' and its paid-for result is discarded if the settlement UPDATE throws
    - **Where:** app/Ingest/Runtime/EffectLedger.php:107-170 (`once()`'s second try block)
    - **Affects:** Every billed effect (Places details, Instagram actor runs) whose vendor call succeeds but whose immediately-following settlement `UPDATE` fails — deadlock, connection loss, or Supavisor pool exhaustion (a documented recurring failure mode on this project's free-tier Postgres pooler). Money is spent, the paid result is thrown away, and the digest is locked 'failed' for the full 7-day freshness window (`partna.ingest.effect_freshness_seconds`, default 604800s) with a misleading `QueryException` in `meta` instead of any signal that the vendor call actually succeeded.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Split effect execution from result persistence into two distinct failure domains instead of one shared `catch (\Throwable $e)`.
        - After `$effect()` returns successfully, wrap only the settlement `UPDATE` in its own try-catch. On failure there, do **not** run the generic-failure `UPDATE` that stamps `status = 'failed'` — that block's own comment says it exists for "we know it happened and what it cost," which is false here.
        - Leave the row `claimed`/unsettled on a persistence-write failure instead, so `reconcileAbandoned()` picks it up honestly after the abandon window (`partna.ingest.effect_abandon_after_seconds`, default 900s) and files the existing `effect_abandoned` critical anomaly ("vendor may have charged") — which is the truthful state, versus a `'failed'` row that actively tells an operator nothing was charged.
        - At minimum, log the persistence failure at `critical`/`report()` severity distinctly from a normal effect failure so it doesn't read as an ordinary vendor error in Nightwatch.
    - **Technical:** `once()`'s second try block does two things under one exception boundary: `$result = $effect()` performs the paid vendor call, then a separate `DB::table('ingest.effects')->where('digest', $digest)->update([...'status' => 'ok'...])` persists the result and settles the row. If that `UPDATE` throws — a deadlock, a dropped connection, a Supavisor session-mode pool exhaustion event (this project has hit `EMAXCONNSESSION` before per prior incident notes) — the outer `catch (\Throwable $e)` at line 162 catches it. That block is documented as being for genuine effect failures ("A failure IS settled: we know it happened and what it cost"), but here the effect did NOT fail — the vendor already answered and `$result` is sitting in a local variable, discarded. The row is stamped `status = 'failed'`, `settled_at = now()`, with `meta.error` = the DB exception class, and since `settled_at` is non-null, `reconcileAbandoned()` never sees this row — the anomaly sweep that would otherwise page on-call for exactly this class of ambiguity never fires. This conflates two distinct failure domains (effect failure vs. persistence failure) that the class's own design elsewhere is careful to keep separate — see how `EffectNotAttempted` and `EffectNoAnswer` each get their own catch block for precisely this reason.
    - **Plain English:** Imagine you pay for a meal at a restaurant, the kitchen cooks it perfectly, but the waiter trips and drops the plate on the way to your table. The restaurant's system marks your order "failed," as if the kitchen never made it. You paid, you're hungry, and nobody working there knows the food actually got made. That's what happens here: the paid API call works and gets an answer, but a database hiccup while saving that answer throws the result away and files it as if the call itself failed — hiding, for a full week, that money was spent for nothing.
    - **Evidence:**
        ```php
        try {
            $result = $effect();

            // Persist the result WITH the settlement: a replay (same-run
            // sibling stream, or a retry) must return the data that was paid
            // for, or charge-once quietly turns "ok" into "no data".
            $meta = ['summary' => $this->summarise($result)];
            $encoded = json_encode($result, JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE);
            if ($encoded !== false && strlen($encoded) <= self::RESULT_INLINE_MAX_BYTES) {
                $meta['result'] = $result;
            } else {
                $meta['result_omitted'] = true;
            }

            DB::table('ingest.effects')->where('digest', $digest)->update([
                'status' => 'ok',
                'settled_at' => now(),
                'meta' => json_encode($meta),
            ]);

            return ['status' => 'ok', 'result' => $result, 'cached' => false];
        } catch (EffectNotAttempted $e) {
            ...
        } catch (EffectNoAnswer $e) {
            ...
        } catch (\Throwable $e) {
            // A failure IS settled: we know it happened and what it cost. It
            // is the UNKNOWN (process death) that must never auto-retry.
            DB::table('ingest.effects')->where('digest', $digest)->update([
                'status' => 'failed',
                'settled_at' => now(),
                'meta' => json_encode(['error' => class_basename($e), 'message' => mb_substr($e->getMessage(), 0, 500)]),
            ]);

            throw $e;
        }
        ```

## P3 — Nice to have

- [ ] **#MONEY-2** · P3 — Places driver takes a ledger claim before its budget/config denial is known, causing an unnecessary insert-then-delete cycle and a (small) stranding window
    - **Where:** app/Ingest/Runtime/Effects/PlacesDetailsDriver.php:46-90, contrasted with app/Services/Platforms/GoogleBusinessService.php:232-246 and app/Ingest/Runtime/Effects/InstagramActorDriver.php:56-63
    - **Affects:** Every `places.details` effect request where the per-user Places budget is exhausted or `GOOGLE_MAPS_SERVER_API_KEY` is unset. Wastes one DB INSERT + DELETE per attempt via `EffectLedger::once()`, and on a process crash between the two, strands a `claimed` ledger row that blocks the digest until `reconcileAbandoned()` marks it `abandoned` (~15 min, `partna.ingest.effect_abandon_after_seconds`) and an operator resolves it.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add a cheap pre-check in `PlacesDetailsDriver::run()` before calling `GoogleBusinessService::fetchPlaceDetailsRaw()`, using the existing `PlacesBudget::remaining('details', $ctx->userId) > 0` and a config-key presence check for `services.google_maps.server_api_key`, and throw `EffectNotAttempted` directly from the driver when either fails — before the ledger's `once()` callback (and therefore before its INSERT) ever runs.
        - Keep `fetchPlaceDetailsRaw()`'s own `claim()` call as-is: it is the real authority and must stay, because `PlacesBudget::remaining()` is explicitly documented as advisory/racy ("for coarse 'should I keep dispatching?' decisions, not a hard gate. `claim()` is the sole authority") — the pre-check only reduces the common-case insert/delete churn, it cannot replace the hard gate.
    - **Technical:** The flow today is: `EffectLedger::once()` INSERTs a `claimed` row for the digest → `PlacesDetailsDriver::run()` calls `GoogleBusinessService::fetchPlaceDetailsRaw()` → deep inside that method (after an API-key check and inside a `for` loop), `PlacesBudget::claim('details', $userId)` runs and may return non-`Granted` → the driver maps that (and a missing-key `NotConfigured` result) to `EffectNotAttempted` → `once()` DELETEs the row it just inserted. This is charge-once-safe (no double billing), but every predictable-exhaustion request pays for two DB writes it didn't need, and the crash window between INSERT and DELETE is wider than it needs to be because the checks that would let the driver refuse cheaply are buried behind a full method call. Contrast with `InstagramActorDriver::run()`, which checks `isConfigured()` and `tryClaim('instagram')` — both cheap, both pre-vendor-call — before the effect callback does anything else. `PlacesBudget::remaining()` (app/Services/Cache/PlacesBudget.php:102) already exists and is exactly the advisory check needed for a driver-level pre-check; it must not be substituted for `claim()`'s own hard gate given its documented raciness.
    - **Plain English:** The Places driver walks into the ledger's office, takes a numbered claim ticket, then walks down the hall to the budget office and discovers the budget is empty — so it walks back and returns the ticket. Most of the time this is harmless extra paperwork. But if the building's fire alarm goes off while the driver is still in the hallway, the ticket never gets returned, and it sits in the system as an unresolved claim until someone notices and cleans it up roughly fifteen minutes later. The Instagram driver checks the budget before ever taking a ticket, so it never has one to lose.
    - **Evidence:**
        ```php
        // PlacesDetailsDriver::run() — no pre-check before calling into GoogleBusinessService

        } catch (PlacesBudgetExhaustedException $e) {

                "places.details budget denied mid-retry for {$placeId} ({$e->reason->value})"
            );
        }
        ```
        ```php

        $key = config('services.google_maps.server_api_key');
        if (! is_string($key) || $key === '') {
            return PlaceDetailsResult::failed(PlaceDetailsFailure::NotConfigured);
        }
        ...
        for ($attempt = 1; $attempt <= $maxAttempts; $attempt++) {
            $claim = $this->budget->claim('details', $userId);
            if ($claim !== PlacesClaim::Granted) {
                if ($attempt === 1) {

                }
                throw new PlacesBudgetExhaustedException('details', $claim, $placeId);
        ```
