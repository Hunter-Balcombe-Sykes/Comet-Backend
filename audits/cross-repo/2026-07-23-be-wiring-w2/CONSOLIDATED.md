## P3 — Nice to have

- [ ] **#SLOP-1** · P3 — Stale, untracked `TODO(v1)` copy-pasted across four route files
    - **Where:** routes/api.php:28, routes/api/publicSite.php:12, routes/api/staff.php:33, routes/api/user.php:39
    - **Affects:** Developers reading route files — an untracked TODO with no ticket, owner, or date, duplicated four times, that signals nothing actionable.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Decide whether `/v1/` route prefixing is actually planned. If yes, replace all four comments with a single dated reference to a real tracking ticket (e.g. `// @ticket PARTNA-xxx: prefix routes /v1/ once frontend migrates`).
        - If it's indefinitely deferred, delete all four comments — an untracked TODO that's survived this many feature releases isn't tracking anything.
    - **Technical:** The same TODO (two near-identical wordings — `api.php` says "all routes below", the other three say "all routes in this file") is duplicated across `routes/api.php`, `routes/api/publicSite.php`, `routes/api/staff.php`, and `routes/api/user.php`, with no ticket reference, owner, or date. Verified via `grep -n "TODO(v1)"` across the repo — exactly these four hits, no tracking artifact anywhere else. Untracked, duplicated TODOs are exactly the graveyard pattern CLAUDE.md's commenting rubric ("purposeful, not extensive") warns against — nobody acts on a TODO with no owner and no deadline.
    - **Plain English:** Four sticky notes saying "fix this later" are stuck on four different route files, with no name or date on any of them. After surviving dozens of feature releases untouched, they've become invisible wallpaper — including to whoever wrote them. Either give the task a real owner and deadline, or throw the notes away.
    - **Evidence:**
        ```php
        // TODO(v1): all routes below should be prefixed /v1/ once frontend is ready for the migration
        ```
        ```php
        // TODO(v1): all routes in this file should be prefixed /v1/ once frontend is ready for the migration
        ```

- [ ] **#SLOP-2** · P3 — Empty ceremonial `register()` override in `DatabaseServiceProvider`
    - **Where:** app/Providers/DatabaseServiceProvider.php:11-17
    - **Affects:** None functionally — Laravel's `Illuminate\Support\ServiceProvider::register()` is already a no-op; this override changes nothing at runtime, only adds a stub every reader has to scan past.
    - **Effort:** S (~0.5h)
    - **What to do:**
        - Delete lines 11–17 (the docblock and the empty `register()` method) entirely. `DatabaseServiceProvider` needs only `boot()`.
    - **Technical:** The class overrides `register()` with an empty body (just a `//` placeholder) and a docblock that describes nothing, purely for symmetry with `boot()`. Confirmed via repo-wide grep that `DatabaseServiceProvider` is referenced only once, in `bootstrap/providers.php` (the standard provider-registration list) — nothing calls `register()` directly or depends on the override existing. Every other provider in this same directory (`AppServiceProvider`, `BotProtectionServiceProvider`, `PlatformRegistryServiceProvider`) only defines `register()` when it actually does something; `EventServiceProvider` omits it entirely when unneeded, confirming this is the odd one out rather than a house convention. Violates CLAUDE.md's "Make every change as simple as possible" — a method that does nothing is not simple, it's noise a reader still has to parse.
    - **Plain English:** This is a light switch mounted on the wall that isn't wired to anything — it's there because the room next door has one, and leaving it off felt incomplete. Taking it off the wall changes nothing about how the room works, and the room looks cleaner without it.
    - **Evidence:**
        ```php
        /**
         * Register services.
         */
        public function register(): void
        {
            //
        }
        ```
