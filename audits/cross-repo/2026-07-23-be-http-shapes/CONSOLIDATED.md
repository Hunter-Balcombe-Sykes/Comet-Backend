## P2 — Should fix

- [ ] **#SLOP-1** · P2 — `UpdateSiteRequest` and `StaffUpdateSiteRequest` duplicate the entire legacy-normalization block instead of using this codebase's own shared-trait convention
    - **Where:** app/Http/Requests/Api/User/Site/UpdateSiteRequest.php:54-80, app/Http/Requests/Api/Staff/UserSite/StaffUpdateSiteRequest.php:21-49
    - **Affects:** Every user-driven and staff-driven site update (subdomain casing, legacy `skeleton_id`/architecture-id collapse, legacy page-id normalization in `settings.manual_page_order`).
    - **Effort:** S (~1–2h)
    - **What to do:**
        - Extract the shared `prepareForValidation()` body (subdomain lowercasing, `skeleton_id` → `architecture_id` compat, `LEGACY_ARCHITECTURE_IDS` collapse, and the `normalizeOrderingPageIds` call) into a new trait, e.g. `App\Http\Requests\Concerns\NormalizesSiteUpdateInput`.
        - Have both `UpdateSiteRequest` and `StaffUpdateSiteRequest` `use` the new trait, matching the pattern already established by `DesignKitValidationRules` and `SiteOrderingValidationRules` (which both classes already share).
        - Keep `LEGACY_ARCHITECTURE_IDS` defined once on `UpdateSiteRequest`, referenced by FQCN from the trait exactly as `StaffUpdateSiteRequest` already does today.
    - **Technical:** Both classes already `use DesignKitValidationRules, SiteOrderingValidationRules` specifically because their own docblocks cite a "TEST-5 / LIFE-4" doctrine: the user-facing and staff-facing site-update requests must not drift out of parity. Despite that stated doctrine in the very same files, the ~20-line `prepareForValidation()` — subdomain casing, the `skeleton_id` legacy-field compat, the `LEGACY_ARCHITECTURE_IDS` collapse, and the ordering page-id normalization — is pasted verbatim, differing only in a comment and a `self::` vs `UpdateSiteRequest::` qualifier. A future edit to the legacy-collapse logic (e.g. a new legacy architecture id, per the ongoing 'one' → 'staple' collapse history visible in `LEGACY_ARCHITECTURE_IDS`) applied to one file and not mirrored in the other would silently make staff-driven and user-driven site updates diverge — exactly the failure mode the existing shared traits were built to prevent.
    - **Plain English:** Two nearly-identical "translate old data into the new format" recipes live in two different files — one for when a user edits their own site, one for when staff edits it on their behalf. This codebase already learned the lesson that these two files must be kept in lockstep (it shares two other rules between them for exactly that reason), but this particular recipe still got copy-pasted instead. If someone updates one copy and forgets the other, staff-made changes and user-made changes could quietly start behaving differently.
    - **Evidence:**
        ```php
        // UpdateSiteRequest.php
        if (is_string($this->skeleton_id ?? null) && $this->architecture_id === null) {
            $merge['architecture_id'] = $this->skeleton_id;
        }
        if (is_string($merge['architecture_id'] ?? $this->architecture_id ?? null)) {
            $v = $merge['architecture_id'] ?? $this->architecture_id;
            $merge['architecture_id'] = self::LEGACY_ARCHITECTURE_IDS[$v] ?? $v;
        }

        // StaffUpdateSiteRequest.php — identical control flow, pasted
        if (is_string($this->skeleton_id ?? null) && $this->architecture_id === null) {
            $merge['architecture_id'] = $this->skeleton_id;
        }
        if (is_string($merge['architecture_id'] ?? $this->architecture_id ?? null)) {
            $v = $merge['architecture_id'] ?? $this->architecture_id;
            $merge['architecture_id'] = UpdateSiteRequest::LEGACY_ARCHITECTURE_IDS[$v] ?? $v;
        }
        ```

    - **Where:** app/Http/Resources/ApiResource.php:27
    - **Affects:** Readers of the `ApiResource` base-class contract; no runtime impact.
    - **Effort:** S (~0.5h)
    - **What to do:**
        - Delete `stringId()` and the "or `$this->stringId()`" clause from the class docblock — nothing calls it.
    - **Technical:** `ApiResource` is the base class for roughly 50 Resource classes, and its docblock presents `(string) $this->id` and `$this->stringId()` as equally-valid spellings. A repo-wide grep for `stringId(` turns up only the method's own declaration/docblock and a mention inside an archived audit markdown file (`audits/archive/foundation-audit-v3/...`) that once recommended adopting it — but the resources it recommended it for (`CaseResource`, `CaseSignalResource`, `DecisionResource`, `EvidenceResource`) all shipped with the plain `(string) $this->id` cast instead. Zero call sites exist in `app/`, `routes/`, `config/`, or `tests/`.
    - **Plain English:** There's a small helper that was added as an optional shortcut for casting an ID to text, but nobody in the codebase actually uses it — every file that needed this wrote it out by hand instead. It's harmless, but it's a tool sitting unused in a drawer, and the comment above it claims it's a live option when it isn't.
    - **Evidence:**
        ```php
        /**
         * Null-safe string cast of `$this->id`. Use when the underlying model
         * may legitimately have a null id (skeleton / not-yet-persisted shapes)

        protected function stringId(): ?string
        ```

        **Dead-code verification:** `Grep -n "stringId\("` across the whole repo (`app/`, `routes/`, `config/`, `tests/`) returns only `app/Http/Resources/ApiResource.php`'s own declaration and a reference inside `audits/archive/foundation-audit-v3/audit-2026-05-31-raw-eloquent-model-leakage-inconsistent-resource-s.md` (an archived recommendation, not live code) — no call sites anywhere.

- [ ] **#SLOP-6** · P3 — Duplicate `isAllowedScheme` method in Store and Update link block requests
    - **Where:** app/Http/Requests/Api/User/Site/StoreLinkBlockRequest.php:214-219, app/Http/Requests/Api/User/Site/UpdateLinkBlockRequest.php:159-164
    - **Affects:** Developers maintaining the http/https scheme allowlist for custom link URLs (an XSS/exfiltration defense: blocking `javascript:`, `data:`, `file:`, `ftp:`).
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Extract `isAllowedScheme(string $url): bool` into a shared trait (bundle with SLOP-4/SLOP-5's helpers — see Bundle 2 below) and call it from both classes.
    - **Technical:** Both classes define an identical private method that parses a URL's scheme and checks it against an `['http', 'https']` allowlist. Unlike the generic "array of distinct UUIDs" rule sets that recur elsewhere in this Requests directory (correctly left un-abstracted per "three similar lines > a premature abstraction" — those are trivial and semantically stable), this is a security-relevant allowlist: if it is ever widened (e.g. to accept `mailto:` for a future contact-link feature) in one file and not the other, one write path silently keeps the old, stricter behavior while the other silently gains a new attack surface.
    - **Plain English:** We wrote the exact same link-safety check — "only allow http/https links, block sneaky script links" — in two different files. If that safety rule ever needs to change, someone has to remember to update it in both places, and it's easy to update one and forget the other.
    - **Evidence:**
        ```php
        // Identical in StoreLinkBlockRequest.php and UpdateLinkBlockRequest.php:
        private function isAllowedScheme(string $url): bool
        {
            $scheme = parse_url($url, PHP_URL_SCHEME);

            return is_string($scheme) && in_array(strtolower($scheme), ['http', 'https'], true);
        }
        ```
