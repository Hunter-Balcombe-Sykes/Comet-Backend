## P2 — Should fix

- [ ] **SLOP-1** · P2 — `mirrorOne`/`mirrorVideo` copy-paste drift: only one carries the Content-Length fast-reject
    - **Where:** app/Services/Platforms/InstagramConnectionSeeder.php:283-292 (`mirrorOne`), :323-352 (`mirrorVideo`)
    - **Affects:** Anyone connecting Instagram whose account's latest reel returns an oversized/slow response — the request pays for the full download before the on-disk `filesize()` cap catches it, where the image path bails early on the declared `Content-Length`.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Extract a shared `mirrorMedia(string $url, string $path, int $timeoutSeconds, int $maxBytes, string $acceptHeader): ?string` covering the common 6-step pipeline (host allowlist → `SafeUrlFetcher::assertSafe` → temp file → HTTP sink → content-type guard → Content-Length fast-reject → on-disk size cap → stream to R2 → cleanup).
        - Have `mirrorOne`/`mirrorVideo` become thin callers passing their own timeout/byte-cap/accept-header constants, OR fold the Content-Length check directly into `mirrorVideo` if a full extraction is judged too invasive for this pass.
        - Re-run `tests/Feature/Platforms/InstagramImageMirrorStreamingTest.php` (the existing SCALE-102 regression suite) — it already tests this exact area and must stay green.
    - **Technical:** Category 6 (copy-paste duplication with drift). `mirrorOne` (app/Services/Platforms/InstagramConnectionSeeder.php:283-286) fast-rejects on a declared oversized `Content-Length` header before the response body finishes streaming to the temp file; `mirrorVideo` has no equivalent early check — it only catches an oversized file via `filesize($tmp)` (:349-351) after the full body has already been sunk to disk. This file has a proven track record of exactly this failure mode: `TRIAGE-2-P2.md` (#SCALE-102) already fixed a prior `mirrorOne`/`mirrorVideo` asymmetry (buffering vs. streaming) in this same pair of methods, and three earlier audit rounds (2026-07-01, 2026-07-08, 2026-06-13) each flagged a different asymmetry between the two (SSRF guard depth, disk resolution, logging). Violates `CLAUDE.md` "Make every change as simple as possible" — each lesson learned in one copy keeps failing to propagate to the other, and per the tier calibration anchor, duplicated logic proven to drift out of sync is a P2, not P3.
    - **Plain English:** Two nearly-identical safety checks exist for photos and videos, but one has an extra "check the size before downloading" shortcut that the other is missing. This isn't the first time these two copies have drifted apart — a very similar gap was already fixed once before. Without a shared version, every future fix has to be remembered and applied twice, and history shows that doesn't reliably happen.
    - **Evidence:**
        ```php
        // mirrorOne (has the fast-reject):
        // Fast rejection when the server declares the size upfront.
        $contentLength = $response->header('Content-Length');
        if ($contentLength !== null && (int) $contentLength > self::MAX_IMAGE_BYTES) {
            return null;
        }

        // Hard cap enforced on what actually landed on disk — covers absent
        // or inaccurate Content-Length headers. Nothing over the limit
        // reaches R2.
        if ((int) filesize($tmp) > self::MAX_IMAGE_BYTES) {
            return null;
        }
        ```
        ```php
        // mirrorVideo (no fast-reject — jumps straight to the on-disk cap):
        $contentType = strtolower(trim(explode(';', (string) $response->header('Content-Type'))[0]));
        if (! str_starts_with($contentType, 'video/')) {
            return null;
        }

        // Oversized reel → drop the video (the poster still renders).
        if ((int) filesize($tmp) > self::MAX_VIDEO_BYTES) {
            return null;
        }
        ```
