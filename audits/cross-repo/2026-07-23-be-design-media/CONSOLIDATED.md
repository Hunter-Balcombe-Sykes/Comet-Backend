## P2 — Should fix

- [ ] **#SLOP-1** · P2 — `PlaceholderLimitExceededException` is dead code that misleads about the real limit-enforcement path
    - **Where:** app/Services/Media/PlaceholderLimitExceededException.php:1-7
    - **Affects:** Any developer scanning `app/Services/Media/` who assumes this class is the live pool/placeholder-limit exception — it sits alongside `PoolLimitExceededException`, which is the one actually thrown by `MediaUploadService`.
    - **Effort:** S (~0.25h)
    - **What to do:**
        - Delete `app/Services/Media/PlaceholderLimitExceededException.php`.
        - Confirm `composer test` and `composer analyse` stay green (no references exist, so this is a pure deletion).
    - **Technical:** Category 3 (dead code). Verified by `Grep 'PlaceholderLimitExceededException'` across `app/`, `tests/`, and `routes/` — the only hit is the class's own definition; it is never thrown, caught, or imported anywhere. This isn't newly introduced slop: a prior audit (`audits/archive/foundation-audit-v2/audit-2026-05-25-architecture-hygiene-service-boundary-correctness.md`, finding HYGN-6) already flagged this exact class as dead code pre-dating the standalone strip and recommended deletion — it was never actioned. `PoolLimitExceededException` (also in this directory, actively thrown by `MediaUploadService::createMediaRow`/`createSingletonRow`) is the real successor. Both extend `\DomainException` with near-identical names, so the risk isn't just clutter — a future `catch (PlaceholderLimitExceededException $e)` would silently miss every real pool-limit exception.
    - **Plain English:** This is a leftover error type from an old version of the upload-limit feature that nothing in the app throws anymore — the real one has a slightly different name (`PoolLimitExceededException`). Leaving the old one in place is like keeping a disconnected doorbell button next to the real one: someone could press the wrong one and think nothing happened.
    - **Evidence:**
        ```php
        class PlaceholderLimitExceededException extends \DomainException
        {
            public function __construct(int $max)
            {
                parent::__construct("Placeholder image limit reached (max {$max}).");
            }
        }
        ```

- [ ] **#SLOP-7** · P3 — Redundant FILTER_NULL_ON_FAILURE + null-coalesce dance in ImageVariantService
    - **Where:** app/Services/Media/ImageVariantService.php (inside `processVariants`, variant-definition loop)
    - **Affects:** Developer maintaining variant processing — the 6-line block collapses to one line with identical behavior.
    - **Effort:** S (~0.25h)
    - **What to do:**
        - Replace the block with: `$preserveResolution = filter_var($def['preserve_resolution'] ?? false, FILTER_VALIDATE_BOOLEAN);`
        - Drop the `FILTER_NULL_ON_FAILURE` flag and the follow-up `?? false` reassignment — `FILTER_VALIDATE_BOOLEAN` alone already returns `false` for any non-boolean-ish input, so the flag + coalesce pair is a no-op round trip.
    - **Technical:** Category 4 (redundant defensive cruft). `FILTER_NULL_ON_FAILURE` makes `filter_var` return `null` instead of `false` on a non-boolean value; the code then immediately coalesces that `null` back to `false` — reproducing exactly what `filter_var` returns by default without the flag. This is the only finding in the batch that's real code rather than a comment, so it's the highest-value item to land here.
    - **Plain English:** It's like putting on a raincoat, taking it off, then putting it back on. The first step already handles every case — the extra flag and reassignment are wasted motion that don't change the outcome.
    - **Evidence:**
        ```php
                $preserveResolution = filter_var(
                    $def['preserve_resolution'] ?? false,
                    FILTER_VALIDATE_BOOLEAN,
                    FILTER_NULL_ON_FAILURE,
                );
                $preserveResolution = $preserveResolution ?? false;
        ```
