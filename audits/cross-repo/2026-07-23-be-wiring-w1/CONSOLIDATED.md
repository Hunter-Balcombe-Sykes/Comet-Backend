## P3 — Nice to have

- [ ] **#SLOP-1** · P3 — Duplicate `'whatsapp'` entry in `link_block_icon_keys`
    - **Where:** config/partna.php:164,180 (`link_block_icon_keys` array)
    - **Affects:** Nobody at runtime — `Rule::in()` membership checks are unaffected by a repeated value. Only affects future maintainers reading/editing this list.
    - **Effort:** S (~0.5h)
    - **What to do:**
        - Delete the second `'whatsapp',` occurrence (currently listed under the "Social platform icons" grouping, line 180) — `whatsapp` is already present under "Functional / custom-link icons" (line 164).
    - **Technical:** `config/partna.php`'s `link_block_icon_keys` array lists `'whatsapp'` twice — once under the "Functional / custom-link icons" heading and again under "Social platform icons (mirrored in social_platforms registry below)". This is consumed by `Rule::in(config('partna.link_block_icon_keys', []))` in both `UpdateLinkBlockRequest` and `StoreLinkBlockRequest` (verified via `Grep`), so the duplicate has zero functional effect — `Rule::in` only checks set membership. It is copy-paste drift: `whatsapp` is genuinely both a direct-contact icon and a social-platform icon, and it looks like it was added to both groupings without anyone noticing it already appeared once. Low-risk to fix, but leaving two entries invites a future editor to "fix" one occurrence and wonder if the other was intentional.
    - **Plain English:** In a settings list of allowed icon names, "WhatsApp" is written down twice by mistake — like listing a phone number twice in a contact list. It doesn't break anything today, but it's confusing clutter that should be tidied up.
    - **Evidence:**
        ```php
        'link_block_icon_keys' => [
            // Functional / custom-link icons
            'scissors',
            'calendar',
            'map',
            'phone',
            'website',
            'link',
            'email',
            'whatsapp',
            // Social platform icons (mirrored in social_platforms registry below)
            'instagram',
            'facebook',
        ```

- [ ] **#SLOP-2** · P3 — Misleading comment and dead commented-out code in empty `options` array
    - **Where:** config/database.php (pgsql connection, `options` key)
    - **Affects:** Developers reading the pgsql connection config; no runtime impact.
    - **Effort:** S (~0.5h)
    - **What to do:**
        - Delete the `options` key entirely (an empty array is functionally identical, and PDO defaults are fine for the pgsql driver) — or, if it's being kept as a deliberate extension point, replace the comment with an accurate one.
        - Delete the commented-out `PDO::ATTR_EMULATE_PREPARES => true,` line.
    - **Technical:** The pgsql connection's `options` array contains nothing but comments (functionally `[]`). The comment `// Set a lock timeout to prevent deadlocks` sits directly above a commented-out `PDO::ATTR_EMULATE_PREPARES` line — the two don't describe each other, and the actual lock timeout is configured two keys down as the sibling `'lock_timeout' => env('DB_LOCK_TIMEOUT', 10000)'` entry (itself correctly commented `// Set lock timeout (10 seconds)`). This is stale copy-paste drift, not a load-bearing note: `Grep` for `ATTR_EMULATE_PREPARES` across the repo returns only this one commented-out line (plus an unrelated archived audit log), confirming it has no active callers or purpose. Cheap to clean up, and the misplaced comment risks misleading a future reader into thinking lock-timeout config lives inside `options`.
    - **Plain English:** There's a small, empty drawer in the filing cabinet labeled "contains spoons" — but the actual spoons are in a different, correctly-labeled drawer nearby. The empty drawer with the wrong label should either be removed or relabeled honestly so nobody wastes time looking in the wrong place.
    - **Evidence:**
        ```php
        'options' => [
            // Set a lock timeout to prevent deadlocks
            // PDO::ATTR_EMULATE_PREPARES => true,
        ],
        ```
