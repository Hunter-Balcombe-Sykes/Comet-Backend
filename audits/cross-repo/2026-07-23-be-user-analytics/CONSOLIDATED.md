## P3 — Nice to have

- [ ] **SLOP-1** · P3 — Four methods in DataExportPayloadBuilder carry a floating, tool-invisible docblock stacked above the real one
    - **Where:** app/Services/User/DataExport/DataExportPayloadBuilder.php:725-733 (streamNotificationPreferences), :919-922 (streamNotifications), :938-946 (streamNotificationReceipts), :957-965 (streamConfirmationPreferences)
    - **Affects:** Maintainers and any docblock-reading tooling (IDE hover, phpDocumentor, PHPStan `@return` inference) — only the docblock immediately preceding a declaration is treated as attached; the earlier block becomes orphaned prose that renders nowhere.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - In each of the four methods, merge the first block's unique explanatory content into the surviving docblock (which already carries the `PRIV-2:` allow-list marker), then delete the now-empty duplicate `/** */` pair. None of the four first blocks are literal duplicates of the second — each carries distinct, non-obvious WHY content (GDPR Article 15 scope rationale, EDPB guideline citation, structural-symmetry rationale, broadcast-vs-personal distinction) that must be preserved, not dropped.
        - Example for `streamNotificationPreferences` — merge into one block:
          ```php
          /**
           * Per-category email opt-in/out preferences. Required for GDPR Article 15
           * (right of access) — users must be able to see every preference we store
           * about them, not just the marketing subscription list.
           *
           * PRIV-2: explicit allow-list, equal to the table's current full column set.
           */
          private function streamNotificationPreferences(string $userId): Generator
          ```
    - **Technical:** PHP/IDE tooling (phpDocumentor, PHPStorm, PHPStan) attaches only the docblock immediately preceding a declaration — a second, earlier `/** */` block separated only by another comment is orphaned and invisible to that tooling, even though it contains real content. This is a mechanical artifact of the `PRIV-2:` allow-list tagging pass being layered on top of pre-existing docblocks without merging them. The earlier DeepSeek draft mischaracterized `streamNotificationPreferences`'s evidence as two byte-identical `PRIV-2` blocks — verified against source, the actual first block is a distinct, load-bearing GDPR-scope explanation, so the correct fix is "merge," not "delete," for all four methods (DeepSeek's own "what to do" only got this right for `streamNotifications`).
    - **Plain English:** Four spots in the GDPR-export code have two explanation notes stacked on top of each other above the same function, but only the bottom one is actually "attached" — tools like the code editor's tooltip only ever show the bottom note. The top note isn't a wasted duplicate though; it explains a real reason (like a privacy-law citation) that's currently invisible to anyone using those tools. The fix is to combine both notes into one so nothing gets lost.
    - **Evidence:**
        ```php
        // streamNotificationPreferences (L725-733) — floating block has DISTINCT content from the attached one:
        /**
         * Per-category email opt-in/out preferences. Required for GDPR Article 15
         * (right of access) — users must be able to see every preference we store
         * about them, not just the marketing subscription list.
         */
        /**
         * PRIV-2: explicit allow-list, equal to the table's current full column set.
         */
        private function streamNotificationPreferences(string $userId): Generator

        // streamNotifications (L919-922) — same doubled-block pattern:
        /**
         * PRIV-2: explicit allow-list, equal to the table's current full column set.
         */
        private function streamNotifications(string $userId): Generator
        ```

- [ ] **SLOP-2** · P3 — `compose()` and `composeStaff()` in AnalyticsCacheService duplicate the same totals/CTR computation
    - **Where:** app/Services/Analytics/AnalyticsCacheService.php:245-253 (compose), :351-356 (composeStaff)
    - **Affects:** Maintainers adding or fixing a totals metric — the same visits/clicks/CTR computation must be updated in two places, and the two have already partially diverged (compose additionally pulls `sessionsAgg`).
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Extract a private `baseTotals(string $proId, Carbon $from, Carbon $to): array` returning `visitsAgg`, `clicksAgg`, `totalVisits`, `totalClicks`, `ctr` (or just the `totals` sub-array plus the raw aggregates compose() still needs for `sessionsAgg`-derived fields).
        - Call it from both `compose()` and `composeStaff()`; each still layers its own extra sections (`breakdowns`/`charts`/`top_*`/`conversions` vs. the staff view's narrower `charts`/`top_links`).
    - **Technical:** Both methods independently call `visitsAggregate`/`clicksAggregate` and compute `$totalVisits`/`$totalClicks`/`$ctr` with byte-identical logic (`round(($totalClicks / $totalVisits) * 100, 2)`). This is copy-paste duplication with real drift risk: a future change to CTR rounding, a zero-guard, or an added totals field is only one `grep` away from being patched in one method and forgotten in the other — exactly the "parallel methods that were copied and have since drifted" pattern this lens flags. The duplication is real (not premature abstraction to fix) since there are already two genuine callers (`summary()` and `staffSummary()`) sharing the exact same computation.
    - **Plain English:** Two report-building functions both start by calculating the same "total visits, total clicks, click-through rate" numbers, using the exact same formula typed out twice. If someone later needs to fix how that rate is calculated, it's easy to fix it in one place and forget the other — like editing one copy of a shared recipe card and leaving the other copy out of date.
    - **Evidence:**
        ```php
        // compose() L245-253:
        $proId = $professional->id;

        $visitsAgg = $this->queries->visitsAggregate($proId, $from, $to);
        $clicksAgg = $this->queries->clicksAggregate($proId, $from, $to);
        $sessionsAgg = $this->queries->sessionsAggregate($proId, $from, $to);

        $totalVisits = (int) ($visitsAgg->total_visits ?? 0);
        $totalClicks = (int) ($clicksAgg->total_clicks ?? 0);
        $ctr = $totalVisits > 0 ? round(($totalClicks / $totalVisits) * 100, 2) : 0.0;

        // composeStaff() L351-356 — same computation, minus sessionsAgg:
        $proId = $professional->id;
        $visitsAgg = $this->queries->visitsAggregate($proId, $from, $to);
        $clicksAgg = $this->queries->clicksAggregate($proId, $from, $to);
        $totalVisits = (int) ($visitsAgg->total_visits ?? 0);
        $totalClicks = (int) ($clicksAgg->total_clicks ?? 0);
        $ctr = $totalVisits > 0 ? round(($totalClicks / $totalVisits) * 100, 2) : 0.0;
        ```
