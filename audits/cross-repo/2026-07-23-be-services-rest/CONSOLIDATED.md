## P3 — Nice to have

- [ ] **#SLOP-1** · P3 — Decorative banner comments duplicate the `group` field in `SectorTaxonomy`
    - **Where:** app/Services/Profile/SectorTaxonomy.php:45-138
    - **Affects:** Maintainers reading/editing the `SECTORS` constant; no user impact.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Delete the 11 Unicode box-drawing divider comments, one per group (`Food & Drink`, `Beauty & Personal Care`, `Health & Fitness`, `Professional Services`, `Retail & Shopping`, `Home & Trade Services`, `Hospitality & Events`, `Automotive`, `Creative & Entertainment`, `Education & Coaching`, `Other`).
        - Keep the blank line between groups for visual separation — that alone is sufficient since every row already carries `'group' => '...'`.
    - **Technical:** `CLAUDE.md` calls out "Decorative banner comments... ASCII art separators" as comment noise to avoid. Verified: each of the 11 groups in the `SECTORS` array is preceded by a `// ── <Group Name> ──...` divider (confirmed via direct `Read` of the file, lines 45–138), and every row in that group already carries the identical string in its `'group'` key. The divider adds zero information a reader doesn't already get from scanning the `group` values — it's pure decoration on top of data that's already there.
    - **Plain English:** Like putting a printed label on top of a filing cabinet drawer that already has a label built into every folder inside it. The folders already say "Food & Drink," "Beauty," etc. — the extra sign on the drawer is just clutter, not new information.
    - **Evidence:**
        ```php
        // ── Food & Drink ────────────────────────────────────────────────
        ['slug' => 'restaurant', 'label' => 'Restaurant', 'group' => 'Food & Drink', 'bucket' => SectorStylePresets::FOOD_DRINK],
        ```
        ```php
        // ── Beauty & Personal Care ──────────────────────────────────────
        ['slug' => 'hair-salon', 'label' => 'Hair salon', 'group' => 'Beauty & Personal Care', 'bucket' => SectorStylePresets::BEAUTY_PERSONAL_CARE],
        ```

- [ ] **#SLOP-2** · P3 — Redundant `(string)` casts on already-string UUID plucks in `SegmentResolver`
    - **Where:** app/Services/Segments/SegmentResolver.php:33, 40
    - **Affects:** None functionally; minor reading friction for maintainers of segment resolution.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Line 33: replace `$dynamic->pluck('id')->map(fn ($id) => (string) $id)->all();` with `$dynamic->pluck('id')->all();`
        - Lines 39–41: drop the `->map(fn ($id) => (string) $id)` step entirely, leaving `->pluck('id')->all();`
    - **Technical:** Both `pluck('id')` calls here resolve through the Eloquent query builder's `pluck()`, which forwards to the underlying `QueryBuilder` and returns raw column values straight from PDO — it does not pass through model casts. `core.users.id` is a Postgres `uuid` column (CLAUDE.md: "UUID primary keys everywhere"), and Laravel's pgsql driver returns `uuid` columns as native PHP strings, so `(string) $id` is a no-op identity map on both call sites. It's harmless, but it's the same pattern copy-pasted twice in one file (category 6 drift risk) and reads as a defensive cast against a type change that the DB driver already guarantees won't happen (category 4).
    - **Plain English:** Like double-bagging a grocery bag that's already sturdy — the extra bag adds handling without adding protection. The user IDs are already plain text when they come out of the database; telling the code "turn this text into text" does nothing useful, just extra words to read.
    - **Evidence:**
        ```php
        if ($dynamic = $this->dynamicQuery($segment)) {
            $ids = $dynamic->pluck('id')->map(fn ($id) => (string) $id)->all();
        }
        ```
        ```php
        $manual = User::query()
            ->whereIn('id', $segment->members()->pluck('user_id'))
            ->pluck('id')
            ->map(fn ($id) => (string) $id)
            ->all();
        ```
