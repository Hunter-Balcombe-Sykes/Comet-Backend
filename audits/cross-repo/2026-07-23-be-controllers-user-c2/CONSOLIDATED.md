## P3 — Nice to have

- [ ] **SLOP-1** · P3 — Stale comment describes a FK behavior the schema no longer has
    - **Where:** app/Http/Controllers/Api/Staff/UserSiteManagement/StaffServiceCategoryManagementController.php:150
    - **Affects:** Developer reading `forceDestroy()`; no runtime impact (the actual `ON DELETE CASCADE` still detaches memberships correctly).
    - **Effort:** S (~0.5h)
    - **What to do:**
        - Replace the comment with an accurate one-liner: memberships are removed via `ON DELETE CASCADE` on `site.service_category_assignments.service_category_id` (added in `20260721180000_service_multi_category.sql`), not a `SET NULL` FK.
    - **Technical:** This comment predates the multi-category migration (`supabase/migrations/20260721180000_service_multi_category.sql`), which replaced the old single `services.category_id` column (which genuinely was `ON DELETE SET NULL`, per that migration's own header) with a `site.service_category_assignments` pivot table whose FK is `service_category_id uuid NOT NULL REFERENCES site.service_categories (id) ON DELETE CASCADE`. The comment's hedge — "(FK ON DELETE SET NULL handles it if in DB)" — is both an unverified-sounding hedge (category 1: "hedging / thinking-out-loud comments left in") and now factually wrong about the mechanism, violating CLAUDE.md's "Comment for WHY... brief docblocks" convention by documenting a WHY that no longer matches the current schema. It doesn't cause a bug (CASCADE still detaches the memberships, so the described outcome still happens) but it will mislead the next engineer who checks the DB expecting a `SET NULL` FK on this table.
    - **Plain English:** A code comment is like a label on a filing cabinet drawer — it should say what's actually inside. This one says "the database sets things to blank when you delete," but a recent database change means the database actually "deletes the related records instead." The end result looks the same today, but the label is wrong, and whoever reads it next might make a decision based on the wrong assumption.
    - **Evidence:**
        ```php
        // Optional: also uncategorise services on hard delete (FK ON DELETE SET NULL handles it if in DB)
        $serviceCategory->forceDelete();
        ```

- [ ] **SLOP-2** · P3 — `indexGlobal`/`indexProfessional` are copy-pasted, differing only by the query filter
    - **Where:** app/Http/Controllers/Api/Staff/StaffSite/StaffNotificationEmailPolicyController.php:23-39, 63-79
    - **Affects:** Developer maintaining notification email policy reads; a future change to the categories-to-policy mapping shape risks being applied to one method and missed on the other.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Extract a private `resolvePolicies(?string $userId): array` helper that runs the `DB::table(...)->when($userId, fn ($q) => $q->where('user_id', $userId), fn ($q) => $q->whereNull('user_id'))->get(...)->keyBy(...)` + `array_map` shaping once.
        - Call it from both `indexGlobal()` (`resolvePolicies(null)`) and `indexProfessional()` (`resolvePolicies($professional->id)`).
    - **Technical:** `indexGlobal()` and `indexProfessional()` are 17-line methods that are identical except for one `whereNull('user_id')` vs `where('user_id', $professional->id)` line — this is category 6 copy-paste duplication ("two or more near-identical blocks that differ only by a constant or a single token"), not the "three similar lines" CLAUDE.md explicitly tolerates. Collapsing to one parameterised helper removes the risk that a future change to `NotificationPublisher::categories()` shaping or the `?->mode ?? 'default'` fallback gets updated in one method and forgotten in the other.
    - **Plain English:** Two nearly-identical recipes exist for "look up someone's email notification settings" — one for the whole platform, one for a single professional. They're copied word-for-word except for one line. If someone later needs to tweak how the recipe works, they'd have to remember to update both copies — and it's easy to forget the second one.
    - **Evidence:**
        ```php
        public function indexGlobal(Request $request): JsonResponse
        {
            $staff = $request->attributes->get('partna_staff');
            $this->authorizeForUser($staff, 'staffView', Notification::class);

            $policies = DB::table('notifications.notification_email_policies')
                ->whereNull('user_id')
                ->get(['category_key', 'mode'])
                ->keyBy('category_key');

            $result = array_map(fn (string $cat): array => [
                'category' => $cat,
                'mode' => $policies->get($cat)?->mode ?? 'default',
            ], NotificationPublisher::categories());

            return $this->success(['policies' => array_values($result)]);
        }
        ```
