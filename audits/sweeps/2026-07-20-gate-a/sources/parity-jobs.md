## P2 — Should fix

- [ ] **#PARITY-1** · P2 — `pre_account_builds.user_id` is `NOT NULL` in prod but nullable in the SQLite test seed, and the factory never sets it
    - **Where:** database/factories/Core/User/PreAccountBuildFactory.php:1; tests/Pest.php:359-374
    - **Affects:** The test suite's ability to catch a regression in the site-first signup path (`GeneratePreAccountSiteJob`, `builds:prune-expired`, `PreAccountBuildService`) that drops the required user association before persisting a `core.pre_account_builds` row. Today every test call site correctly calls `->user()->associate($user)` before `->save()`, so nothing currently 500s — but the gap means a future test (or a future factory `->create()` call, the idiomatic Eloquent shorthand) would pass CI green while writing a row Postgres rejects outright.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - In `tests/Pest.php`'s `setupPreAccountBuildsTable()`, change `user_id TEXT NULL` to `user_id TEXT NOT NULL` so the SQLite stub actually mirrors the migration's constraint — a test that forgets `->user()->associate($user)` then fails fast in CI instead of silently writing NULL.
        - Leave `PreAccountBuildFactory::definition()` as-is: `user_id` is deliberately excluded from `$fillable` ("set via associate() only" — see the model's own comment), so the factory correctly declines to set it directly; the seed table is what needs to catch the omission, not the factory.
    - **Technical:** `supabase/migrations/20260718200000_pre_account_sites.sql` declares `user_id uuid NOT NULL UNIQUE REFERENCES core.users(id) ON DELETE CASCADE` with no DB-level default. `PreAccountBuildFactory::definition()` never populates `user_id` (by design — the model marks it non-fillable), so every caller is required to remember `->user()->associate($user)` before `->save()`/`->create()`. `tests/Pest.php`'s hand-rolled SQLite stand-in declares the same column as `user_id TEXT NULL` — its own comment claims to "mirror migration 20260718200000_pre_account_sites.sql" but does not mirror this constraint. Category 1 (NOT NULL violation the SQLite seed can never catch) — the current test suite happens to comply by convention, but nothing in the harness enforces it, so a regression here is a silent green-CI-then-Postgres-500 waiting to happen rather than a currently-shipping bug.
    - **Plain English:** Every "pre-account" site build in the real database MUST be linked to an owner — the database itself refuses to save one without an owner attached. The practice-database used for automated tests doesn't have that same rule switched on, so if a future test (or a future code change) ever forgets to attach the owner, the tests would still pass — and only the real database would catch the mistake, in production. Turning the same rule on in the test database means a slip-up gets caught immediately during testing instead of during a real signup.
    - **Evidence:**
