All three DeepSeek drafts were checked against the actual migration DDL and dropped — each rested on a premise the schema directly contradicts:

- **PARITY-1** (`notifications.notifications`/`notifications.email_subscriptions` NOT NULL claims): the baseline DDL (`supabase/migrations/20260526000000_baseline_standalone_user.sql:1001-1113`) shows `cta_url`, `ends_at`, and `user_id` (renamed from `professional_id` by `20260527050000_rename_professional_constraints_indexes.sql`) are all **nullable** — none carry `NOT NULL`. The `user_id => null` write in `EmailSubscription::insertOrIgnore()` is the documented "global list, no owner" pattern, not a bug. No violation exists on Postgres.
- **PARITY-2** (`site.platform_connections` "unverifiable from repo"): false on its face — `supabase/migrations/20260602150238_create_platform_connections.sql` exists precisely to reconcile this table into git ("Adopted into the repo to reconcile migration history"). Reading it through the follow-on migrations shows `payload jsonb NOT NULL DEFAULT '{}'::jsonb` (satisfied by `payload => []`), the `platform` CHECK dropped entirely by `20260629120000_drop_platform_connections_check.sql`, `last_refresh_status` CHECK widened to include `'pending'` by `20260616000000_allow_pending_refresh_status.sql`, and `apify_status` CHECK explicitly allowing `NULL`/`'pending'` by `20260701220000_promote_gb_apify_status_placeid.sql`. Every write cited in the finding is safe.
- **PARITY-3** (`audit.user_deletion_audit.metadata`): the baseline DDL (`supabase/migrations/20260526000000_baseline_standalone_user.sql:497`) declares `metadata jsonb` with no `NOT NULL` — the finding's own premise ("if metadata is NOT NULL...") is conditional on something the schema doesn't do.

Spot checks beyond the three drafts (per the exhaustiveness directive) covered `core.users` (including the `auth_user_id`/`primary_email` nullability widening and `status`/`account_type` CHECK widenings for pre-account signup — all correctly landed in `20260718200000_pre_account_sites.sql`, `20260612120000_account_type_partna_business.sql`, `20260712000000_retire_staff_account_type.sql`), `site.content_selection`'s `content_selection_ref_shape` CHECK against `ContentSelectionService`, `core.pre_account_builds`' `source_type` CHECK against `config('partna.pre_account.*')`, `core.data_export_audit`'s NOT NULL `recipient_email` against `DataExportService`'s pre-write guard, and the `HasUuids`-backed alias models (`SiteSubdomainAlias`, `UserHandleAlias`) against their DB-default-less `id` columns. No new PARITY findings surfaced.
