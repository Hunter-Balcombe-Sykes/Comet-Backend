## P0 — Must fix before any real user touches the system

- [ ] **#MIG-1** · P0 — `DROP INDEX` without `CONCURRENTLY` on hot table `site.site_media`
    - **Where:** supabase/migrations/20260527000000_fix_sort_order_unique_constraints.sql:11-12
    - **Affects:** All writes to `site.site_media` during the eventual prod push — gallery uploads, content images, design-kit logo/cover uploads, media-variant processing callbacks.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Change both statements to `DROP INDEX CONCURRENTLY IF EXISTS ...`.
        - No file split is needed: this file already has **no `BEGIN`/`COMMIT` wrapper** (required below it for the two `CREATE UNIQUE INDEX CONCURRENTLY` statements), so `CONCURRENTLY` is immediately usable in place — just add the keyword.
    - **Technical:** `DROP INDEX` without `CONCURRENTLY` acquires `ACCESS EXCLUSIVE` on the target table for the (brief but real) duration of the catalog drop, blocking every `INSERT`/`UPDATE`/`DELETE` on `site.site_media` until it completes. The file's own top-of-file comment correctly reasons about `CONCURRENTLY` for the two `CREATE INDEX` statements ("site.site_media already has rows on dev… will be larger by prod-promotion time") but the two preceding `DROP INDEX` statements were missed from that same reasoning. Since none of the ~90 post-baseline migrations have reached prod yet (prod is still on the pre-standalone schema), this ships as part of the gated re-baseline — a deploy-risk finding, elevated a tier per the lens's prod-is-behind rule, since it will hit whatever row count `site.site_media` carries at cutover.
    - **Plain English:** Imagine a busy photo-lab counter where two old ID tags need pulling off a filing cabinet before new ones go on. The current plan is to lock the entire cabinet — no photo can be filed or retrieved — while both old tags are removed. The fix is a single extra word that tells Postgres to pull each tag quietly without freezing the cabinet, and the file is already built to support it.
    - **Evidence:**
        ```sql
        DROP INDEX IF EXISTS site.site_images_site_sort_active_unique;
        DROP INDEX IF EXISTS site.site_images_site_sort_order_active_uq;

        CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS site_images_site_sort_active_unique
            ON site.site_media (site_id, pool, sort_order)
            WHERE (deleted_at IS NULL);
        ```

- [ ] **#MIG-4** · P2 — Unqualified `DROP FUNCTION` leaves an orphaned trigger referencing a dropped column
    - **Where:** supabase/migrations/20260527070000_skeleton_system_cleanup.sql:39-47 (bug) and supabase/migrations/20260527070001_drop_orphaned_theme_trigger.sql (fix, in a separate file/transaction)
    - **Affects:** Any `INSERT INTO site.sites` executed between `20260527070000`'s `COMMIT` and `20260527070001`'s `COMMIT` during the prod re-baseline push.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Edit `20260527070000` directly (safe per the same "Editing already-applied migrations" rule cited in #MIG-3 — dev already has this applied, so the edit no-ops there; prod hasn't, so the fresh apply gets the corrected version): move a schema-qualified `DROP TRIGGER IF EXISTS set_default_theme_on_sites ON site.sites;` and `DROP FUNCTION IF EXISTS core.set_default_theme_for_site() CASCADE;` to *before* the `DROP COLUMN theme_id` step, inside the same transaction.
        - Leave `20260527070001` in place — its `IF EXISTS` guards make it a harmless no-op once the trigger/function are already gone, and it costs nothing to keep as a belt-and-suspenders safety net.
    - **Technical:** `20260527070000` runs `DROP FUNCTION IF EXISTS set_default_theme_for_site CASCADE;` unqualified. PostgreSQL resolves this against the session `search_path`, finds no match (the function actually lives in `core`), and — because of `IF EXISTS` — silently does nothing. The trigger `set_default_theme_on_sites` (`BEFORE INSERT` on `site.sites`) survives, still bound to `core.set_default_theme_for_site()`, whose body reads `NEW.theme_id` and queries `site.themes` — both of which this same migration goes on to drop. Because the whole file is one `BEGIN`/`COMMIT`, this doesn't corrupt anything mid-transaction (Postgres DDL is transactional; concurrent sessions just block on the lock until commit) — but the moment this file *commits*, the broken trigger and function are both live, and the very next `INSERT` into `site.sites` fires it and 500s on the missing column. `20260527070001` (the very next migration, correctly schema-qualified and correctly ordered) closes the gap — but only once it, too, has committed. `docs/migration-guidelines.md`'s "Editing already-applied migrations" section is the reason this can be fixed at the source rather than left as a two-file race: content edits to an already-applied migration are a no-op wherever it already ran, and only change behavior on a target that hasn't applied it yet — which describes prod exactly.
    - **Plain English:** Think of renaming a room in a building. The work order says "take down the old room number" and "cancel the lighting schedule for that room" — but the cancel instruction has a typo and points at the wrong room, so it silently does nothing. The room number comes down, the wiring for the old schedule is still live, and the very next time someone flips that light switch, the breaker trips because the wiring points at a room that no longer exists. A follow-up work order (already written) fixes the typo — but anyone who flips the switch between the two work orders still gets a power failure. Since the confirmed-safe way to fix an old work order without breaking anywhere it's already been used is to just correct it at the source, that's the cleaner fix here: cancel the schedule *before* removing the room number, in the same work order.
    - **Evidence:**
        ```sql
        -- 20260527070000 (bug): DROP FUNCTION unqualified, before DROP COLUMN theme_id
        DROP FUNCTION IF EXISTS set_default_theme_for_site CASCADE;
        ```
        ```sql
        -- 20260527070001 (correct, but a separate commit — this is the gap):
        DROP TRIGGER IF EXISTS set_default_theme_on_sites ON site.sites;
        DROP FUNCTION IF EXISTS core.set_default_theme_for_site() CASCADE;
        ```

- [ ] **#MIG-6** · P2 — `NOT VALID` + `VALIDATE CONSTRAINT` bundled into one long transaction spanning six unrelated fixes, including hot table `site.site_media`
    - **Where:** supabase/migrations/20260624010000_schema_hardening_constraints.sql:11-74 (site_media block: 54-58)
    - **Affects:** Reads/writes to `site.site_media`, plus `notifications.broadcast_email_receipts`, `audit.auth_factor_events`, `site.platform_connections`, and `site.site_subdomain_aliases` — all for the full duration of this single transaction.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Split the `site.site_media` `DROP CONSTRAINT` / `ADD CONSTRAINT ... NOT VALID` / `VALIDATE CONSTRAINT` block into its own migration file, with `VALIDATE CONSTRAINT` in a separate transaction — per `CONVENTIONS.md` §2's own two-transaction convention, which this file's *comment* correctly names but doesn't actually apply to the constraint step.
        - Don't bundle unrelated fixes across five different tables/schemas into one `BEGIN`/`COMMIT` when one of them touches a table on the lens's explicit hot-table list.
    - **Technical:** `NOT VALID`'s entire benefit is that its `ACCESS EXCLUSIVE` lock is metadata-only and released immediately — but that only holds if `VALIDATE CONSTRAINT` runs in a *separate* transaction afterward, so the weaker `SHARE UPDATE EXCLUSIVE` scan isn't stacked on top of any lock from the constraint-add step. Here, both run inside the same `BEGIN`/`COMMIT` as four other unrelated DDL fixes (DINT-2, DINT-3, DINT-10, SCHEMA-2, SCHEMA-7) touching four other tables — so every lock acquired anywhere in the file is held for the full transaction lifetime, and the `site.site_media` `VALIDATE CONSTRAINT` scan runs while the transaction is *also* holding whatever locks the preceding unrelated statements acquired. The `SET LOCAL lock_timeout = '3s'; SET LOCAL statement_timeout = '30s';` guard at the top of this file (a genuinely good practice — see #MIG-7) is the main reason this doesn't rise to P1: worst case, the transaction aborts cleanly at 30s rather than hanging indefinitely.
    - **Plain English:** Six small, unrelated home repairs get bundled into one work order that keeps the whole house's power off until every single repair — including the one on the kitchen circuit everyone uses constantly (site_media) — is finished, instead of doing each repair as its own quick job with the power back on in between.
    - **Evidence:**
        ```sql
        BEGIN;

        SET LOCAL lock_timeout = '3s';
        SET LOCAL statement_timeout = '30s';
        ...
        ALTER TABLE site.site_media DROP CONSTRAINT site_media_pool_check;
        ALTER TABLE site.site_media
            ADD CONSTRAINT site_media_pool_check
            CHECK (pool IN ('gallery', 'content', 'design', 'product', 'documents')) NOT VALID;
        ALTER TABLE site.site_media VALIDATE CONSTRAINT site_media_pool_check;
        ...
        COMMIT;
        ```

## P3 — Nice to have

- [ ] **#MIG-7** · P3 — Missing `SET LOCAL lock_timeout` / `statement_timeout` guards on DDL touching live-traffic tables
    - **Where:** supabase/migrations/ — most DDL migrations against `site.design_kits`, `site.sites`, `site.blocks`, or `core.users` predating 2026-06-24 lack the guard documented in `docs/migration-guidelines.md` §"Lock and statement timeouts (#SCALE-3)".
    - **Affects:** Deploy reliability — a stuck lock-wait during a DDL migration on a live-traffic table has no timeout backstop and could queue indefinitely rather than failing fast.
    - **Effort:** M (~2–4h) to retroactively add guards to the highest-risk remaining files, or S to formalize "forward-only, no retrofit" as the policy.
    - **What to do:**
        - Per `docs/migration-guidelines.md` §SCALE-3: add `SET LOCAL lock_timeout = '2s'; SET LOCAL statement_timeout = '10s';` at the top of every *new* migration running DDL against a live-traffic table.
        - No blanket retrofit needed: the highest-actual-risk historical files (the CHECK/FK/backfill-touching ones) are already covered individually by #MIG-3, #MIG-5, and #MIG-6. The ~50 `site.design_kits` `ADD COLUMN ... NULL` migrations without the guard are metadata-only regardless (nullable, no default, no rewrite), so the missing guard there is genuinely low-stakes hygiene, not latent risk.
    - **Technical:** `docs/migration-guidelines.md` §SCALE-3 documents this exact convention — "Add at the top of every migration that runs DDL on a live-traffic table: `SET LOCAL lock_timeout = '2s'; SET LOCAL statement_timeout = '10s';`" — with `20260624010000_schema_hardening_constraints.sql` as the first migration to apply it (using `3s`/`30s`). A repo-wide grep shows this is **not** an isolated instance: six further migrations dated 2026-07-01 through 2026-07-18 (`20260701220000`, `20260703000000`, `20260705120000`, `20260705120001`, `20260705120002`, `20260718010000` — all outside this audit's migration-file scope) also carry the guard, meaning the team has been organically adopting the practice for new work since it was introduced, rather than leaving it as a one-off. The residual gap is purely the ~50 files that predate the convention's introduction.
    - **Plain English:** Deploying a database change with no timeout guard is like pulling into a car wash with no emergency-stop button — if the car ahead stalls, everyone behind is stuck. A two-second timeout says "if I can't start within two seconds, back out and flag the problem" instead of silently queuing forever. The team has already started fitting the newer parts of the car wash with this button; the remaining work is fitting the rest.
    - **Evidence:**
        ```sql
        -- docs/migration-guidelines.md §"Lock and statement timeouts (#SCALE-3)":
        SET LOCAL lock_timeout    = '2s';
        SET LOCAL statement_timeout = '10s';
        ```
        ```sql
        -- 20260624010000_schema_hardening_constraints.sql — the first migration to apply it:
        SET LOCAL lock_timeout = '3s';
        SET LOCAL statement_timeout = '30s';
        ```
