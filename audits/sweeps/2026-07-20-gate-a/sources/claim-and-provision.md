## P3 — Nice to have

- [ ] **#CCH-1** · P3 — Idempotency purge index key duplicated as a hardcoded string instead of a shared helper
    - **Where:** app/Services/User/AccountDeletionService.php:356 (`purgeIdempotencyCache()`); counterpart at app/Http/Middleware/IdempotencyKey.php:224-227 (`userIndexKey()`)
    - **Affects:** GDPR erasure path during account-deletion confirmation. If the two hand-written key formats ever drift, `purgeIdempotencyCache()` silently stops finding entries to purge.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add `CacheKeyGenerator::idempotencyIndexKey(string $userId): string` returning `"idempotency:index:{$userId}"`.
        - Replace the inline string in `AccountDeletionService::purgeIdempotencyCache()` and the private `userIndexKey()` method in `IdempotencyKey` middleware with calls to the new helper.
    - **Technical:** Verified: `IdempotencyKey::userIndexKey()` (line 224) and `AccountDeletionService::purgeIdempotencyCache()` (line 356) each independently hardcode the literal pattern `"idempotency:index:{$id}"` — one is the writer (the middleware indexes every cached response under this SET key), the other is the reader/purger. `CacheKeyGenerator` is the codebase's established single-source-of-truth for cache key naming (confirmed: it owns 20+ other key builders) but does not yet cover idempotency keys at all — both the response-cache key and this index key live as private methods inside the middleware. The risk is bounded today: the entries carry a 24h TTL and PII is already pseudonymised by the time this purge runs, so a missed purge leaks only opaque response bodies for the remainder of the TTL window, not live PII. Still, this is exactly the "two teams hand-label the same drawer" pattern the centralized-key convention exists to prevent, and it's a five-line fix.
    - **Plain English:** Two different parts of the system — one that saves a "receipt" every time it caches a response, and one that later throws those receipts away during account deletion — each write out the same filing label by hand instead of using one shared label-maker. Today the two labels happen to match, so cleanup works. If anyone changes one without noticing the other, deleted accounts will leave stray cached data sitting around slightly longer than intended.
    - **Evidence:**
        ```php
        $connection = Redis::connection('cache');
        $indexKey = "idempotency:index:{$authUserId}";

        $cacheKeys = $connection->smembers($indexKey);
        foreach ($cacheKeys as $cacheKey) {
            if (is_string($cacheKey) && $cacheKey !== '') {
                Cache::forget($cacheKey);
            }
        }

        $connection->del($indexKey);
        ```

- [ ] **#TXN-1** · P3 — Bare `DB::transaction()` without explicit connection pinning
    - **Where:** app/Services/User/ConfirmationPreferenceService.php:58-70
    - **Affects:** Professionals updating "skip confirmation" preferences. Production's default connection is pgsql (confirmed by parallel comments throughout this codebase), so there is no functional impact today — this is a convention gap, not a live bug.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Change `DB::transaction(function () use (...)` to `DB::connection('pgsql')->transaction(function () use (...)`.
    - **Technical:** `UserConfirmationPreference` extends `BaseModel`, which forces the `pgsql` connection for all Eloquent operations regardless of what connection wraps them. A bare `DB::transaction()` opens its transaction on the app's *default* connection — pgsql in production, but a separately-configured connection in the Pest test environment (confirmed elsewhere in this same codebase: `SectionVisibilityService::buildContext()` explicitly comments "even in test environments where the default connection differs (SectionVisibilityTestCase sets default = 'sqlite')"). When default ≠ pgsql, this wrapper transaction never actually covers the `UserConfirmationPreference::updateOrCreate()` writes inside it — they execute directly against pgsql, outside any transaction boundary the test can observe or roll back. Every other transactional service already reviewed in this bundle (`AccountDeletionService`, `UserBootstrapService`, `ClaimSiteService`, `UpdateSiteAction`, `DataExportService`) explicitly pins `DB::connection('pgsql')->transaction(...)` for exactly this reason; this call site is the outlier.
    - **Plain English:** Most rooms in this building have a sign saying "this door leads to the main hallway," so a fire-drill test walks the correct path. This one door has no sign. In the real building (production) it happens to connect to the main hallway anyway, so nothing breaks — but during a drill (a test) someone could walk through it and never actually test what the drill was meant to test.
    - **Evidence:**
        ```php
        DB::transaction(function () use ($userId, $normalizedUpdates): void {
            foreach ($normalizedUpdates as $actionKey => $skipConfirmation) {
                UserConfirmationPreference::query()->updateOrCreate(
                    [
                        'user_id' => $userId,
                        'action_key' => $actionKey,
                    ],
                    [
                        'skip_confirmation' => $skipConfirmation,
                    ]
                );
            }
        });
        ```

- [ ] **#TXN-2** · P3 — Bare `DB::transaction()` around an advisory-lock insert, no explicit connection pinning
    - **Where:** app/Services/Site/InsertWithSortOrder.php:21-31
    - **Affects:** Every caller that inserts a row with a computed `sort_order` under an advisory lock (services, links, etc.). Same "no functional prod impact, real convention gap" profile as TXN-1.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Change `DB::transaction(function () use ...` to `DB::connection('pgsql')->transaction(function () use ...`.
    - **Technical:** `DB::select('select pg_advisory_xact_lock(hashtext(?))', ...)` and `DB::transaction()` here both resolve the *default* connection, same gap as TXN-1. This one is Postgres-specific in a second way too: `pg_advisory_xact_lock` doesn't exist on SQLite, so any test exercising this path already has to run against a real pgsql connection one way or another — but the call site still doesn't declare that dependency explicitly, leaving the pgsql assumption implicit rather than pinned. Inconsistent with `SiteProvisioningService::tryCreateSite()`, `UpdateSiteAction::execute()`, and `ContentSelectionService::persist()` in this same bundle, which all pin explicitly.
    - **Plain English:** Same missing sign as the previous finding, but on a door that also has a special keycard lock (the database's advisory lock) that only exists in the "real building." Nothing is broken today, but the door should still carry the sign that says which building it belongs to.
    - **Evidence:**
        ```php
        public static function run(Builder $maxQuery, string $lockKey, Closure $create): Model
        {
            return DB::transaction(function () use ($maxQuery, $lockKey, $create) {
                DB::select('select pg_advisory_xact_lock(hashtext(?))', [$lockKey]);

                $max = (clone $maxQuery)->max('sort_order');
                $next = is_null($max) ? 0 : ((int) $max + 1);

                return $create($next);
            });
        }
        ```

- [ ] **#TXN-4** · P3 — LIFE-5's concurrent-rename row lock reads the default connection, not the pinned pgsql connection its own contract requires
    - **Where:** app/Services/Site/RenameSubdomainAction.php:41-49
    - **Affects:** Every subdomain rename (self-service and staff reclaim). This is the linchpin read for the documented LIFE-5 fix that prevents two concurrent renames from both passing the 30-day cooldown check.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Change the three bare `DB::table(...)` calls in this method (the `lockForUpdate()` re-read at line 45, plus the sites/aliases conflict checks at lines 63 and 78) to `DB::table(...)` on an explicitly pinned `DB::connection('pgsql')`, matching the class's own documented contract.
    - **Technical:** This class's own docblock states the CONTRACT explicitly: "must be called INSIDE an open pgsql transaction (the caller owns the transaction)." `UpdateSiteAction::execute()` (the sole caller) honors that by wrapping the call in `DB::connection('pgsql')->transaction(...)`. But the LIFE-5 fix inside this method — re-reading `subdomain_changed_at` under `lockForUpdate()` to close a race where two concurrent renames could both pass the cooldown check — issues that read via the bare `DB::table('site.sites')` facade, which resolves the *default* connection, not necessarily the caller's pinned pgsql connection. The method's own comment even acknowledges the SQLite fallback case explicitly ("lockForUpdate is a no-op on SQLite — fine for the test suite") without pinning the connection to guarantee the lock actually serializes against the same connection the writer transaction uses. In production this coincides with pgsql by virtue of the app's default connection config, so the fix works as documented today — but its correctness rests on an implicit assumption rather than an explicit pin, which is the exact convention this bundle's other four findings (TXN-1 through TXN-3, CCH-1) all trace back to. This is the most consequential of the four `DB::transaction`/`DB::table` connection-pinning gaps in this bundle because it underpins a named concurrency fix (LIFE-5) rather than a plain write.
    - **Plain English:** This is the same unlabeled-door problem as the three findings above it, but on the door that a previous fix specifically installed to stop two people from renaming to the same address at the same time. The lock only works because, by coincidence of how the building is currently wired, this door already happens to connect to the right hallway — but nothing forces that to stay true, and the class's own paperwork says it's supposed to be guaranteed, not coincidental.
    - **Evidence:**
        ```php
        // LIFE-5: re-read subdomain_changed_at under a row lock INSIDE the tx. Reading the
        // pre-transaction snapshot let two concurrent renames both pass the 30-day cooldown;
        // the FOR UPDATE makes the second rename block until the first commits, then see the
        // updated timestamp. (lockForUpdate is a no-op on SQLite — fine for the test suite.)
        $lockedChangedAt = DB::table('site.sites')
            ->where('id', $site->id)
            ->lockForUpdate()
            ->value('subdomain_changed_at');
        $site->subdomain_changed_at = $lockedChangedAt !== null ? Carbon::parse($lockedChangedAt) : null;
        ```
