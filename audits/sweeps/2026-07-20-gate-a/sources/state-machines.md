## P2 — Should fix

- [ ] **#LIFE-1** · P2 — `AccountDeletionService::request()` swallows a transaction failure without `report()`, leaving Nightwatch blind
    - **Where:** app/Services/User/AccountDeletionService.php:119-130
    - **Affects:** Users initiating account deletion during an infra blip (DB/Redis hiccup). They see a friendly 503; on-call has no real-time signal unless the user complains.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add `report($e)` immediately before returning the 503 array.
        - Keep the existing `Log::error` call for post-mortem context — `report()` is additive, not a replacement.
    - **Technical:** Category (10) observability. Pattern: Log-with-context. Nightwatch alerts on exceptions that escape to the framework's exception handler; `report()` forwards a caught exception there without rethrowing, so the caller still gets the friendly response while Nightwatch still gets the stack trace. This catch only calls `Log::error`, so any DB/Redis failure during a deletion request is invisible to real-time alerting today. The two sibling "must not silently fail" catches in the same class — the Supabase-deletion failure (line 581) and the `forceDelete` failure (line 654) inside `purge()` — both already call `report()`; `request()` is the outlier. Stays P2 (not P1) because this only fires on infra faults, not a routine user-facing scenario — matches the P2 observability anchor (a missed alert during an incident) rather than "ships bad behavior in a known scenario."
    - **Plain English:** When the "start deleting my account" flow breaks because of a database hiccup, we write a note in the server journal and tell the user "try again later." But nobody is watching that journal in real time — our alerting system only hears about crashes it catches directly. This one gets swallowed before it reaches the alarm, so a string of failed deletion requests could go unnoticed. The fix is a one-line addition that hands the same crash to the alarm system too.
    - **Evidence:**
        ```php
        } catch (\Throwable $e) {
            Log::error('Account deletion request failed', [
                'user_id' => $professional->id,
                'error' => $e->getMessage(),
            ]);

            return [
                'success' => false,
                'code' => 503,
                'error' => 'Failed to initiate deletion request. Please try again.',
            ];
        }
        ```

- [ ] **#LIFE-2** · P2 — Pre-account build IP abuse-cap is a check-then-act race with no lock
    - **Where:** app/Services/PreAccount/PreAccountBuildService.php:81-90
    - **Affects:** The public pre-account build endpoint (signup-path Instagram/Google-Business site generation). A burst of concurrent requests from one IP can create more provisional builds than `max_unclaimed_per_ip` (default 3), each kicking off a real, billed scrape (Apify / Google Places) before any of them commits.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Wrap the count-check-and-create sequence in a Postgres advisory lock keyed on the IP hash, mirroring the pattern `App\Services\Site\InsertWithSortOrder::run()` and `ReorderService` already use for the same "count-then-write" shape: `pg_advisory_xact_lock(hashtext($ipHash))` inside the same `DB::connection('pgsql')->transaction()` that creates the build, so concurrent requests from one IP serialize instead of racing the count.
    - **Technical:** Category (2) race-safety on read-modify-write. Pattern: race-safe read-modify-write (advisory lock, since there's no natural row to `lockForUpdate` for an IP-scoped count). The cap check (`PreAccountBuild::live()->where('created_ip_hash', $ipHash)->count()` vs `$cap`) runs entirely outside the transaction that later creates the User/Site/PreAccountBuild rows, with no lock scoping it to the IP — N concurrent requests from the same IP within the check-to-insert window all observe the same count and all pass. This codebase already has an established fix for exactly this shape (`InsertWithSortOrder::run()`, `ReorderService` both wrap read-then-write in `pg_advisory_xact_lock`); this call site is the one place that pattern wasn't applied. At current traffic this is unlikely to bite by accident, but a scripted signup-abuse burst against one IP can deliberately exploit it to fan out more scrape jobs (and Apify/Places billing) than the cap allows — worth closing now, before it's a cost incident during a viral spike.
    - **Plain English:** Before letting someone build a preview site from an Instagram or Google Business profile, we check "has this internet address already made too many of these?" But the check and the "make one more" step aren't glued together — if several requests from the same address arrive at the exact same instant, they can all see "you're under the limit" and all get through, even though the limit is 3. Nothing breaks, but the hard "3 max" rule becomes more of a suggestion under a burst, and each extra one spins up a real, paid-for scrape of the source profile.
    - **Evidence:**
        ```php
        // Signup-path abuse cap: outstanding unclaimed builds per IP (F2).
        if ($staff === null && $ipHash !== null) {
            $cap = (int) config('partna.pre_account.max_unclaimed_per_ip', 3);
        ```

- [ ] **#LIFE-3** · P2 — `HandleAllocator::allocate()` has a check-then-insert race on `handle_lc`, and the caller's `UniqueConstraintViolationException` catch can't tell that apart from a source-dedupe collision
    - **Where:** app/Services/User/HandleAllocator.php:22-29; app/Services/PreAccount/PreAccountBuildService.php:98-113, 143-154
    - **Affects:** Pre-account build creation (Instagram/Google-Business signup-path site generation). Two builds started at the same instant from source names that slug identically both see the candidate handle as free; the loser gets a confusing "Could not create the build. Try again." error instead of a transparent retry.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - In `requestBuild()`'s `catch (UniqueConstraintViolationException)`, don't assume every violation is the `pre_account_builds_live_source_unique` collision. Re-check `User::where('handle_lc', ...)->exists()` first; if that's the actual cause, retry `HandleAllocator::allocate()` with the next suffix and re-attempt the save.
        - Wrap that retried `$user->save()` in its own nested `DB::connection('pgsql')->transaction()` (a SAVEPOINT), mirroring the exact pattern `SiteProvisioningService::tryCreateSite()` and `UserBootstrapService`'s documented LIFE-101 fix already use — Postgres aborts the *whole* transaction on an unhandled 23505 unless the failing statement is inside its own savepoint, so a naive try/catch without this nesting would poison the outer build transaction.
    - **Technical:** Category (1)/(2) — idempotency + race-safety on read-modify-write. Pattern: `UniqueConstraintViolationException` (typed catch exists but doesn't disambiguate two possible constraints) + `lockForUpdate + UNIQUE`. `HandleAllocator::allocate()` does a plain `EXISTS` check with no lock — a classic TOCTOU: two concurrent `requestBuild()` calls with identically-slugging seeds can both see the base handle as free. The DB does catch the eventual collision on `core_users_handle_lc_unique` (referenced in `UserBootstrapService`'s own comments), but `requestBuild()`'s single catch block assumes the violation is always the `pre_account_builds_live_source_unique` dedupe key and calls `findLive($sourceType, $refLc)` to re-serve "the winner's build." For a pure handle collision no such build exists under that source/ref, so `findLive()` returns null and the request fails outright instead of retrying with the next handle suffix. Also note: unlike `SiteProvisioningService::tryCreateSite()`, `$user->save()` here isn't wrapped in its own nested transaction, so a correct fix needs the savepoint discipline in addition to the disambiguating re-check, not just a retry loop.
    - **Plain English:** When we create a new provisional account, we pick a username by slugging the business name and checking if it's taken. Two requests arriving at the same moment can both check, both see "available," and both try to grab it. The database catches the second one's collision, but our code assumes that collision always means "this source already has a build" rather than "someone else grabbed that username" — so the user sees a generic, confusing error instead of us quietly trying the next available username variant.
    - **Evidence:**
        ```php
        $handle = $base;
        $attempt = 1;
        while (User::query()->where('handle_lc', strtolower($handle))->exists()) {
            $handle = $base.$attempt;
            $attempt++;
        }

        return ['handle' => $handle, 'handle_lc' => strtolower($handle)];
        ```
        ```php

            // Lost the race on pre_account_builds_live_source_unique — the other
            // request's build is the canonical one; re-serve it (spec §4.1).
            $existing = $this->findLive($sourceType, $refLc);
            if ($existing) {
                return ['build' => $this->reserve($existing), 'reused' => true];
            }
            throw new PreAccountBuildException(
                PreAccountBuildException::SOURCE_REF_INVALID,
                'Could not create the build. Try again.'
            );
        }
        ```

- [ ] **#LIFE-4** · P2 — `PreAccountBuild` has no reconcile path for a build stuck in `pending`/`building` — only a `failed` state or 30-day expiry ever get swept
    - **Where:** app/Services/PreAccount/PreAccountBuildService.php:156, 169-178; app/Console/Commands/PruneExpiredPreAccountBuilds.php:43-47
    - **Affects:** Any pre-account build whose `GeneratePreAccountSiteJob` dispatch is lost (queue backend hiccup at the exact moment of dispatch) — the user's signup site never finishes generating, and nothing brings it back until the 30-day expiry prune deletes the row outright.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Extend `builds:prune-expired` (or add a sibling scheduled command) to detect builds stuck in `pending`/`building` past a short SLA (e.g. > 30–60 minutes) and re-dispatch `GeneratePreAccountSiteJob` for them, logging a discriminating warning (`pre_account.build_stuck_requeued`) each time — mirroring `gdpr:sweep-stale-exports`, which already does this for the analogous "stuck in processing" `DataExportAudit` state.
        - Fix `reserve()` so a retried request for a source ref whose build is stuck in `pending`/`building` (not just `failed`) triggers the same re-dispatch, instead of silently handing back the stuck row unchanged.
    - **Technical:** Category (4) reconcile/repair jobs for external-state dependence. Pattern: daily reconcile job. `GeneratePreAccountSiteJob::dispatch()` (line 156) runs after the row-creating transaction has already committed; if the queue push itself throws (a transient Redis blip), the exception propagates to the caller and the `PreAccountBuild` row is left committed with `build_state='pending'` and no job ever enqueued. `reserve()` (lines 169-178) — the only re-dispatch path a retried request goes through — only re-fires when `build_state === STATE_FAILED`; a build stuck in `pending`/`building` is returned unchanged, so even the *same* user retrying gets served the permanently-stuck row. `PruneExpiredPreAccountBuilds` only selects candidates where `expires_at < now()` OR (`build_state = failed` AND `updated_at < failedCutoff`) (lines 43-47) — a stuck pending/building build satisfies neither until the full 30-day window elapses. This is a completely silent, permanently broken signup for that one user, invisible to Nightwatch (nothing throws at read time — the state simply never advances) until the row disappears a month later. `DataExportAudit` already has the equivalent protection (`gdpr:sweep-stale-exports`, whose own comment reads "between markProcessing() and completion leaves the audit row stuck forever") — `PreAccountBuild` has no counterpart.
    - **Plain English:** When someone starts building a preview site from their Instagram, we kick off a background job to go fetch and build it. If the hand-off to that background job fails at exactly the wrong moment (a brief hiccup in our job queue), the build record is left saying "in progress" forever — but nothing is actually running. If the same person tries again, our code sees the stuck record and just hands it back unchanged instead of starting fresh. Nobody notices until, a month later, a cleanup job quietly deletes the abandoned record. We already have this exact safety net for GDPR data exports; the signup path is missing the equivalent one.

        ```php
                GeneratePreAccountSiteJob::dispatch($build->id, false)->afterCommit();
            }
        ```

- [ ] **#LIFE-5** · P2 — Seven PII-erasure sub-methods in `AccountDeletionService::purge()` log failures but never `report()` them, so a silent GDPR erasure gap is invisible to Nightwatch
    - **Where:** app/Services/User/AccountDeletionService.php — `purgeExportZips()` 724-728, `purgeEarlyAccessSignup()` 748-751, `purgeFeedbackRows()` 768-771, `purgeCaseSignalPii()` 798-801, `purgeReportedUserEvidencePii()` 851-854, `purgeGlobalEmailSubscriptions()` 878-881, `purgeCrossTenantSubscriptions()` 915-918
    - **Affects:** GDPR compliance observability during the daily hard-delete purge. If any PII-erasure step fails (transient DB fault), the professional row still gets `forceDelete`d and the deletion "succeeds" — but the failure is logged, not alerted, so the surviving PII in these email/handle-keyed auxiliary tables (which the DB cascade never reaches) can sit indefinitely with no one aware.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add `report($e)` alongside each `Log::error` call in all seven purge sub-methods, matching the precedent `purge()`'s own top-level steps already set.
    - **Technical:** Category (10) observability. Pattern: Log-with-context. Nightwatch alerts on exceptions/`report()`, not on log queries. `purge()`'s own top-level "this must not silently fail" steps — the Supabase auth-deletion failure (line 581: `report(new \RuntimeException(...))`) and the `forceDelete` failure (line 654: `report($e)`) — both already call `report()`. The seven PII sub-methods, each individually fault-tolerant by design ("a storage outage must not block account erasure"), are the outliers: they log with full context (`user_id` present, so this isn't a correlation-context gap the way the P2 anchor's bare-`Log::warning` example is) but never alert.     - **Plain English:** During the nightly cleanup of deleted accounts, we scrub personal data out of seven different side-tables (feedback, moderation evidence, email lists, exported files, etc.). If any one scrub step fails — say the database is briefly overloaded — we write a note in the journal and keep going, and the account still gets deleted. But no alarm rings for that specific scrub step. Months later, a supposedly-deleted user's personal data could still be sitting in one of those tables because nobody knew that one step missed. The fix adds a one-line alarm trigger to each of the seven steps.
