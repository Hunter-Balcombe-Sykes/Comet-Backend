## P2 — Should fix

- [ ] **#PRIV-1** · P2 — Original image/video uploads stored verbatim without EXIF/GPS metadata stripping
    - **Where:** app/Services/Media/ImageVariantService.php:141-163 (`storeOriginal`); app/Services/Media/MediaUploadService.php (private `storeOriginal`, video branch)
    - **Affects:** Every image and video uploaded by professionals — gallery photos, logos, design singletons. Originals retain embedded EXIF/container metadata (GPS coordinates, camera/device model, capture timestamp) from phone/camera media indefinitely, on a `private`-ACL disk path kept for re-processing.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - For images: re-encode the original through GD (`imagecreatefromjpeg`/`imagecreatefrompng`/`imagecreatefromwebp` → re-save) before it's streamed to disk in `ImageVariantService::storeOriginal()`, so pixel data survives for re-processing but EXIF does not.
        - For video: `MediaUploadService`'s private `storeOriginal()` currently `fopen`-streams the raw video bytes straight to disk — GD doesn't apply here. Strip container metadata via an `ffmpeg -map_metadata -1 -c copy` remux pass (no re-encode needed) before upload, reusing the `ffmpeg_binary` config already used by `VideoVariantService`.
        - Keep the stripped file as the disaster-recovery/re-processing source — the fix removes metadata, not pixel/audio fidelity.
    - **Technical:** `ImageVariantService::storeOriginal()` opens the uploaded file via `fopen($realPath, 'rb')` and streams the raw bytes directly to the media disk (R2/S3) with zero transformation. GD-based variant generation in `processVariants()` inherently strips EXIF (GD's `imagecreatefromjpeg`/`imagecreatefrompng` don't carry EXIF through to `imagewebp`), so the *variant* artifacts are clean — but the original remains a carrier for every byte the camera embedded, including GPS lat/lon, device serial, and capture timestamp. The video path in `MediaUploadService` has the identical raw-stream pattern for video originals. Under Australian Privacy Act APP 3 (collection minimisation), retaining precise location data that serves no platform purpose is a compliance gap, even though the file is `private`-ACL and not directly user-facing.
    - **Plain English:** When someone uploads a photo or video from their phone, that file contains hidden data — where and when it was taken, what device was used. The platform strips this from the versions shown to the public (good), but keeps the raw original file as a backup with all that hidden data intact. That's like keeping a photocopy of a customer's ID "just in case" when you only needed the picture. The fix cleans the backup copy too — keep the image/video, drop the embedded location and device info before it's stored. That way there's no forgotten location trail if a deletion or data-access request ever needs answering.
    - **Evidence:**
        ```php
        // ImageVariantService::storeOriginal — raw file streamed verbatim, no EXIF strip
        $stream = fopen($realPath, 'rb');
        if ($stream === false) {
            throw new \RuntimeException('Failed to open uploaded file for streaming.');
        }
        try {
            $this->disk()->put($path, $stream, 'private');
        } finally {
            if (is_resource($stream)) {
                fclose($stream);
            }
        }
        ```

- [ ] **#EDGE-1** · P2 — Outbound Cloudflare and streaming-API calls have no explicit HTTP timeout
    - **Where:** app/Services/Cloudflare/CloudflarePurgeService.php:84-87 (`purgeUrls`); app/Services/Cloudflare/CloudflareKvService.php:89-93 (`put`), :124 (`delete`), :142-143 (`bulkPut`); app/Services/Streaming/StreamingTokenManager.php:62-66 (`refreshToken`); app/Services/Streaming/TwitchApiClient.php:41-44 (`getLiveHandles`); app/Services/Streaming/KickApiClient.php:34-37 (`getLiveHandles`)
    - **Affects:** Horizon queue workers (every content mutation dispatches a Cloudflare purge) and the streaming live-status poller/token refresher — a hung third-party API pins a worker slot for up to Laravel's HTTP client default (30s connect+read per call), and `purgeHandle()` can generate 50+ chunks for a profile with many products/menu-items/events.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Add `.timeout(10)` (or a project-standard constant) to every `Http::` call in `CloudflarePurgeService::purgeUrls()` and `CloudflareKvService::{put,delete,bulkPut}()`, matching the pattern already established by `CloudflareCustomHostnameService`.
        - Add the same explicit timeout to `StreamingTokenManager::refreshToken()`, `TwitchApiClient::getLiveHandles()`, and `KickApiClient::getLiveHandles()` — none of the three currently sets one either.
    - **Technical:** Laravel's HTTP client (`Illuminate\Http\Client\PendingRequest`) defaults `connect_timeout` to 10s and `timeout` to 30s when neither is set explicitly — not "indefinite," but still a real per-call ceiling that every one of these six call sites is silently relying on rather than declaring. `CloudflareCustomHostnameService` already sets explicit timeouts (`.timeout(10)`/`.timeout(5)`) on every call in the same namespace, so the gap is inconsistency, not a missing capability. `purgeHandle()` chunks purge targets 30 URLs per POST and can emit many chunks for a profile with a large catalog — at the 30s default, a degraded (not down) Cloudflare API can hold a Horizon worker for minutes per purge run. The streaming clients have the same exposure on a schedule that runs continuously. A 10s explicit timeout surfaces the failure sooner and frees the worker without materially risking a false-timeout against normally-fast APIs.
    - **Plain English:** When the system tells Cloudflare to clear its cached pages, or checks Twitch/Kick for who's live, it makes a phone call and waits for an answer. Right now several of these calls don't have a hang-up timer set explicitly, so they lean on a generic 30-second default instead of a deliberate, short one. One part of the same codebase already sets a shorter, explicit 10-second deadline for similar calls. Matching that everywhere means one slow API response can't tie up a worker for as long, keeping the system responsive when a partner API has a bad day.
    - **Evidence:**
        ```php
        // CloudflarePurgeService::purgeUrls() — no timeout set:
        Http::withToken($this->apiToken)
            ->asJson()
            ->acceptJson()
            ->post($this->url(), ['files' => $chunk])
            ->throw();

        // CloudflareKvService::put() — no timeout set:
        Http::withToken($this->apiToken)
            ->withBody((string) json_encode($value), 'text/plain')
            ->put($url)
            ->throw();

        // StreamingTokenManager::refreshToken() — no timeout set:
        $response = Http::asForm()->post($cfg['token_url'], [
            'client_id' => $clientId,
            'client_secret' => $clientSecret,
            'grant_type' => 'client_credentials',
        ]);

        // TwitchApiClient::getLiveHandles() — no timeout set:
        $response = Http::withHeaders([
            'Authorization' => "Bearer {$token}",
            'Client-ID' => (string) config('services.twitch.client_id'),
        ])->get($streamsUrl.'?'.$query);

        // Contrast — CloudflareCustomHostnameService::create() DOES set a timeout:
        $result = Http::withToken($this->apiToken)
            ->timeout(10)
            ->asJson()
            ->post($this->base(), [
                'hostname' => $hostname,
                'ssl' => [
                    'method' => 'http',
                    'type' => 'dv',
                    'settings' => ['min_tls_version' => '1.2'],
                ],
            ])
            ->throw()
            ->json('result', []);
        ```

- [ ] **#CFG-2** · P3 — SafeUrlFetcher User-Agent strings hardcoded with no config override path
    - **Where:** app/Services/Http/SafeUrlFetcher.php:48-51, 57
    - **Affects:** Ops tuning the outbound UA string (e.g. to work around a target host's WAF); non-prod deployments that send a UA claiming to be `partna.au`.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add `partna.http_fetch.user_agent` / `partna.http_fetch.fallback_user_agent` config keys to `config/partna.php`, defaulting to the current constant values.
        - Read them via `config()` in `fetch()`/`fetchMany()` instead of `self::USER_AGENT`/`self::FALLBACK_USER_AGENT`.
        - Build the default UA string from `config('partna.public_domain')` (already used elsewhere, e.g. `CloudflarePurgeService`) so non-prod environments don't claim to be `partna.au`.
    - **Technical:** The class already reads `maxRedirects`, `timeoutSeconds`, and `maxBytes` from `config('partna.http_fetch.*')` with documented fallback constants — that's the established pattern in this exact file. The two UA strings break it: `self::USER_AGENT`/`self::FALLBACK_USER_AGENT` are referenced directly with no `config()` indirection, so a WAF rule change on a scraped target host requires a code deploy instead of a config push.
    - **Plain English:** The outbound web-fetcher has adjustable knobs for timeouts and size limits, but its "caller ID" name tag is written in permanent marker. If a website starts blocking that name, ops can't swap it without a full deploy — and today it's tagged as `partna.au` no matter what environment it's actually running in.
    - **Evidence:**
        ```php
        private const USER_AGENT = 'Mozilla/5.0 (compatible; PartnaBot/1.0; +https://partna.au)';
        public const FALLBACK_USER_AGENT = 'PartnaBot/1.0 (+https://partna.au)';

        // vs the pattern used for the other settings in this same file:
        $this->maxRedirects = (int) config('partna.http_fetch.max_redirects', self::MAX_REDIRECTS);
        $this->timeoutSeconds = (int) config('partna.http_fetch.timeout_seconds', self::TIMEOUT_SECONDS);
        $this->maxBytes = (int) config('partna.http_fetch.max_bytes', self::MAX_BYTES);
        ```

- [ ] **#CFG-3** · P3 — CloudflarePurgeService hardcodes deep-link enumeration caps as literals
    - **Where:** app/Services/Cloudflare/CloudflarePurgeService.php:157, 176, 201, 214
    - **Affects:** Sites with large product catalogs, menus, or event lists — only the first N rows get their edge cache purged after an edit; ops would need a deploy to raise the caps.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add config keys under `partna.cloudflare_purge.*` for the four DB-query caps: `max_product_handles` (default 100), `max_menu_item_ids` (default 150), `max_event_connections` (default 30), `max_event_ids` (default 100).
        - Read them via `config()` with the current values as defaults.
        - Leave the `array_chunk(..., 30)` API-batch size alone — that's Cloudflare's hard `purge_cache` limit ("accepts at most 30 URLs per request on non-Enterprise plans", per the comment already in `purgeUrls()`), not an ops-tunable value; making it configurable would let someone set it above 30 and break every purge call.
    - **Technical:** `purgeHandle()` runs bounded queries to enumerate deep-link URLs (product pages, menu items, event pages) for the purge batch, each capped with a hardcoded `->limit(N)` or `array_slice(..., 0, N)`. For the vast majority of professionals (small catalogs) this never matters; a power user with 200+ products only gets the first 100 purged, leaving the rest edge-stale until natural TTL expiry. Extracting these four caps to config lets ops raise them without a deploy cycle. The Cloudflare API chunk size (30) is a different kind of constant — it's dictated by Cloudflare's API contract, not internal policy — and should stay a literal.
    - **Plain English:** When someone updates their site, the system tells Cloudflare "forget your cached copies of these pages," building the list by asking the database — but it stops counting after a fixed number (100 products, 150 menu items, etc). For almost everyone this is fine, but a power user with a huge catalog could have some pages stay stale. Moving these caps into settings lets ops raise them with a config change instead of a code deployment. (The 30-per-batch number elsewhere in the same file is different — that one's dictated by Cloudflare itself and shouldn't be made adjustable.)
    - **Evidence:**
        ```php
        // Product handles — capped at 100
        ->whereRaw("p.data->>'handle' IS NOT NULL")
        ->selectRaw("DISTINCT p.data->>'handle' AS product_handle")
        ->limit(100)
        ->pluck('product_handle')
        ->all();

        // Menu item IDs — capped at 150
        ->where('u.handle_lc', $h)
        ->limit(150)
        ->pluck('mi.id')
        ->all();

        // Event connections — capped at 30
        ->whereNull('c.deleted_at')
        ->limit(30)
        ->pluck('c.payload')
        ->all();

        // Event IDs after extraction — capped at 100
        $eventIds = array_slice(array_keys($eventIdSet), 0, 100);
        ```

- [ ] **#SEC-1** · P3 — CloudflarePurgeService interpolates handle and product-handle into purge URLs without URL-encoding
    - **Where:** app/Services/Cloudflare/CloudflarePurgeService.php (`purgeHandle`, `$bases` and `$urls` construction)
    - **Affects:** Cloudflare cache-purge API calls for public profiles with scraped shop catalogs.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Apply `urlencode()` to `$h` when constructing `$bases`/`$apiBase` URLs.
        - Apply `urlencode()` to `$productHandle` when building `/products/{$productHandle}` purge URLs.
        - `menuItemId` (a UUID column value) and `eventId` (already regex-validated to `^[A-Za-z0-9_-]{1,64}$` before being added to `$eventIdSet`) don't need this — leave them as-is.
    - **Technical:** `$h` is `strtolower(trim($handle))`, constrained at write time by the `regex:/^[a-z0-9_-]+$/i` rule enforced in `ReclaimHandleRequest`/`BootstrapRequest`, so encoding here is pure defense-in-depth against a future validation regression. `$productHandle` is a different story: it's read straight from JSONB (`p.data->>'handle'`) sourced from scraped third-party shop data, with no app-side format constraint, and interpolated directly into `"{$base}/products/{$productHandle}"`. Worst case if it contains `#`/`?`/`%` isn't an SSRF or auth bypass — these strings only become entries in a `files` array POSTed to Cloudflare's purge API, never fetched or executed server-side — but a malformed segment could cause the purge to silently target the wrong cache key, leaving a product page stale after an edit. Low severity, cheap fix.
    - **Plain English:** The profile username and product names are pasted directly into web addresses sent to Cloudflare to say "forget this page." The username is already restricted to safe characters, so that part is just extra insurance. Product names come from other people's shopping sites though, and aren't restricted the same way — if one ever contained an unusual character, that specific product's cached page might not get cleared. Adding proper encoding is a cheap, low-risk safety net.
    - **Evidence:**
        ```php
        $bases = ["https://{$h}.{$baseDomain}"];
        // ...
        $urls[] = "{$base}/products/{$productHandle}";
        // ...
        $urls[] = "{$apiBase}/api/public/profiles/{$h}";
        ```
