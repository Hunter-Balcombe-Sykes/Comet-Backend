## P2 — Should fix

- [ ] **#PRIV-1** · P2 — CSP report sink logs raw IP/UA/URL content to Nightwatch with no redaction, and the endpoint is unauthenticated and internet-reachable
    - **Where:** app/Http/Controllers/Api/Internal/CspReportController.php:44-50
    - **Affects:** Two real populations, not "sitepage visitors" as originally scoped — (1) staff members using the Horizon queue dashboard whose browsers fire a genuine CSP violation report, and (2) any unauthenticated internet caller, since the route requires no credentials and accepts arbitrary POST bodies up to the truncation limits.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Strip or hash the `document-uri` and `blocked-uri` fields inside `normalise()` before logging — retain only scheme+host+path, drop query strings entirely (query strings are the one place attacker- or staff-supplied PII could realistically land).
        - Hash the caller IP (truncated SHA-256) rather than logging it raw.
        - No change needed to the auth/throttle posture — `throttle:120,1` plus the CSP-report use case already justify staying credential-less; this is a minimization fix at the logging boundary, not an access-control fix.
    - **Technical:** DeepSeek's draft claimed this endpoint receives reports from "visitors to any Partna sitepage." That's not what the code does: `app/Http/Middleware/SecureHeaders.php` sets `report-uri` **only** on the `horizon`/`horizon/*` branch, with an explicit comment that "Horizon is the ONLY rendered-HTML surface in this app, so it is the only place CSP actually evaluates and the only place report-uri can ever produce traffic" — the public API branch (which is what public sitepage JSON responses get) omits `report-uri` entirely because "JSON responses never trigger CSP." Horizon itself is gated by `AppServiceProvider::authorizeHorizonRequest` (staff-only, confirmed via `tests/Feature/Security/HorizonDashboardAuthTest.php`). So genuine CSP reports only ever originate from staff browsers on the internal admin dashboard — not the public. The real residual exposure is narrower but still live: the route (`routes/api.php:190`, `throttle:120,1`) is deliberately unauthenticated (browsers don't send credentials with CSP reports), so anyone on the internet can POST an arbitrary JSON body and have `document-uri`/`blocked-uri`/IP/UA logged into Nightwatch verbatim (only length/depth are capped, not content). That's a minimization gap worth closing, not a visitor-privacy breach.
    - **Plain English:** When a security rule breaks on our internal admin dashboard, the staff member's browser sends us a short report — and right now we save the raw web address (including anything after the question mark, like a token) and their network address without blacking any of it out. Because this inbox has no lock on the door, a stranger on the internet could also mail it fake reports stuffed with whatever text they want, and we'd file that too. It's not visitor data leaking as originally feared — it's an internal mailbox that files everything it receives without checking what's inside first. Filtering out the risky bits before filing closes that gap.
    - **Evidence:**
        ```php
        Log::error('csp.violation', [
            'report' => self::normalise($payload),
            'ip' => $request->ip(),
            'ua' => substr((string) $request->userAgent(), 0, self::MAX_STRING_LEN),
        ]);
        ```
        ```php
        // app/Http/Middleware/SecureHeaders.php — report-uri only ever attaches here:
        if ($request->is('horizon', 'horizon/*')) {
            // Horizon is the ONLY rendered-HTML surface in this app, so it is the
            // only place CSP actually evaluates and the only place report-uri can
            // ever produce traffic. JSON API responses do not trigger CSP at all.
        ```

## P3 — Nice to have

- [ ] **#CFG-1** · P3 — Coupled hardcoded webhook timestamp tolerance not sourced from shared config
    - **Where:** app/Services/Webhooks/StandardWebhookVerifier.php:19 and app/Http/Controllers/Api/Internal/SupabaseEmailHookController.php:83
    - **Affects:** Webhook idempotency correctness only if someone changes one constant without the other; no current drift exists.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add a key `partna.webhooks.timestamp_tolerance` (seconds, default `300`) to `config/partna.php`, following the existing `env()`-backed default pattern already used for `cache.ttls.*`.
        - Replace `private const TIMESTAMP_TOLERANCE = 300` in `StandardWebhookVerifier` with a read from that config.
        - Replace the literal `300` in `now()->addSeconds(300)` in `SupabaseEmailHookController` with the same config read.
    - **Technical:** The verifier uses a `private const` for the replay-defence window; the email hook controller duplicates `300` as a literal with a comment stating it must match the verifier's tolerance. Both are currently `300` and correct, but they're two independently-editable values expressing one invariant — if the tolerance is ever widened (e.g. to accommodate clock-skewed clients) without touching the controller, the dedup cache would expire before signature-valid replays are rejected, opening a narrow window where a replay is both signature-valid and no longer deduped. No exploit exists today; this is preventative coupling cleanup.
    - **Plain English:** Two parts of the code both say "5 minutes" independently instead of reading it from one shared setting. Today they agree, so nothing is broken. But if someone later changes one "5 minutes" to "10 minutes" without remembering the other exists, the two safety checks would quietly fall out of sync. Writing the number once and having both parts read it removes that risk of forgetting.
    - **Evidence:**
        ```php
        // StandardWebhookVerifier.php:19
        private const TIMESTAMP_TOLERANCE = 300;
        ```
        ```php
        // SupabaseEmailHookController.php
        $dedupKey = 'supabase:email_hook:seen:'.$webhookId;
        if (! Cache::add($dedupKey, 1, now()->addSeconds(300))) {
        ```

- [ ] **#CFG-2** · P3 — Idempotency-cache TTL config read has no inline fallback default (inconsistent with sibling reads in the same controller)
    - **Where:** app/Http/Controllers/Api/Webhooks/SupabaseAuthHookController.php:52
    - **Affects:** MFA brute-force dedup; only if the `partna.cache.ttls.webhook_idempotency` config array entry is itself deleted or renamed independently of this call site.
    - **Effort:** S (~0.5h)
    - **What to do:**
        - Add an explicit fallback for defense-in-depth and consistency: `(int) config('partna.cache.ttls.webhook_idempotency', 300)`, matching the pattern of the other two `config()` calls lower in the same method.
    - **Technical:** Verified `config/partna.php:1583` — this key already resolves via `(int) env('PARTNA_CACHE_TTL_WEBHOOK_IDEMPOTENCY', env('CACHE_TTL_WEBHOOK_IDEMPOTENCY', 86400))`, so under current config the read never returns null; DeepSeek's framing ("config() returns null → TTL 0 → cache self-destructs") overstates the present-day risk, since that requires actively deleting the array entry from `config/partna.php`, not just an unset env var. The residual gap is real but narrow: this is the one `config()` call in the method without an inline default, unlike the two `partna.mfa.*` reads immediately below it — a future refactor that touches the config array without noticing this call site is the only path to the described failure. Worth the one-line consistency fix; not an active vulnerability.
    - **Plain English:** This setting already has a solid backup value written into the settings file itself, so in practice it can't silently go blank today. The only gap is that this one line of code doesn't also carry its own backup number the way its two neighboring lines do — so it's the odd one out. Adding the same safety net here is a five-minute consistency fix, not an urgent problem.
    - **Evidence:**
        ```php
        if (! Cache::add(
            "supabase:auth-hook:{$id}",
            true,
            (int) config('partna.cache.ttls.webhook_idempotency'),
        )) {
        ```
        ```php
        $maxFailures = (int) config('partna.mfa.verify_max_failures', 5);
        ```
