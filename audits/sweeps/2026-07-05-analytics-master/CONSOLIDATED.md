- [ ] **#SCHEMA-1** `[full-sweep]` · P2 — `analytics.site_sessions` has RLS enabled but not forced
    - **Where:** supabase/migrations/20260610000000_analytics_v2_clicks_sessions.sql (site_sessions block)
    - **Affects:** Defense-in-depth for `analytics.site_sessions` against the `postgres`/table-owner role bypassing RLS via the Supabase `authenticated` client path. `app_backend` already has `BYPASSRLS`, so the main application path is unaffected.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add `ALTER TABLE analytics.site_sessions FORCE ROW LEVEL SECURITY;` in a new migration.
        - Add a regression assertion (alongside existing RLS-parity tests) checking `pg_class.relforcerowsecurity` for this table.
    - **Technical:** Every sibling table that enables RLS in this codebase also forces it — confirmed via grep across `site.design_kits` (`20260602000000_design_kits_rls.sql`), all five `moderation.*` tables (`20260606030000_moderation_schema_rls.sql`), `core.feedback`, `core.partna_staff`, `site.platform_connections`/`site.menus`/etc. (`20260702000000_rls_parity_platform_connections_menus.sql`, itself a hardening-parity fix for an identical gap), and `core.supabase_email_events`. `analytics.site_sessions` is the one outlier that only has `ENABLE ROW LEVEL SECURITY` with no `FORCE`. Without `FORCE`, the table owner is exempt from the policy check by Postgres default — a narrow but real consistency gap versus the codebase's own established convention.
    - **Plain English:** Think of Row Level Security as a second lock on a filing cabinet drawer. Every other drawer in the building has both the lock AND a rule that says "even the building manager must use the lock." This one drawer has the lock installed but skipped that second rule, so the manager's master key still bypasses it. The actual app doesn't use the manager's key, so nothing is broken today — but every comparable table already has this second rule, and this one was missed.
    - **Evidence:**
        ```sql
        ALTER TABLE analytics.site_sessions ENABLE ROW LEVEL SECURITY;

        DROP POLICY IF EXISTS site_sessions_owner_select ON analytics.site_sessions;
        CREATE POLICY site_sessions_owner_select ON analytics.site_sessions
            FOR SELECT TO authenticated
            USING (user_id = (SELECT id FROM core.users WHERE auth_user_id = auth.uid() AND deleted_at IS NULL));
        ```

- [ ] **#PARITY-1** `[full-sweep]` · P2 — Analytics event models' `$fillable` lists are missing columns the production writer writes
    - **Where:** app/Models/Analytics/LinkClick.php, app/Models/Analytics/SiteVisit.php, app/Models/Analytics/SectionView.php
    - **Affects:** Any future Eloquent mass-assignment path (`::create()`, `fill()`+`save()`, or a test factory) touching these three tables. The current hot path (`Model::query()->insertOrIgnore($rows)`) bypasses `$fillable` entirely, so production is unaffected today — but `SiteVisit` and `SectionView` both declare `use HasFactory`, inviting exactly the vulnerable call pattern in future tests.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - `LinkClick::$fillable`: add `id, user_id, site_id, link_block_id, created_at, url, platform, product_id, product_title, section_key, label, country_code, region_code, device_type`.
        - `SiteVisit::$fillable`: add `id, user_id, site_id, created_at, region_code`.
        - `SectionView::$fillable`: add `id, user_id, site_id, created_at`.
    - **Technical:** `PostgresEventWriter::clickRow()`/`visitRow()`/`appendSectionRow()` each build a raw array with more keys than the corresponding model's `$fillable`. Because the writer calls `insertOrIgnore()` on the query builder (not `create()`/`fill()`), Eloquent's mass-assignment guard never runs and today's writes succeed regardless. But if a future refactor or test factory calls `LinkClick::create($row)`, the UUID primary key and both tenancy FKs (`user_id`, `site_id`) would be silently dropped — SQLite's lax typing and disabled FK enforcement would let the resulting row through in tests, while real Postgres would reject it (NOT NULL/FK violation), exactly the test/prod schema-drift trap called out in this repo's own engineering notes.
    - **Plain English:** Each of these three database tables has a model class with a list of "fields I'm allowed to accept." The list is missing several fields — including the row's own ID and its links to the user and site it belongs to — that the real save process writes every time. Today that's harmless because the real save process doesn't use that list at all; it writes directly. But it's a hidden trap: if anyone later writes a test or a feature using the normal "create a record" method, those missing fields get silently dropped, and the mistake won't show up until it hits the real production database, which is stricter than the test database.

- [ ] **#DINT-1** `[full-sweep]` · P2 — Session heartbeat upsert silently drops rows on a session-ID collision across two different sites
    - **Where:** app/Services/Analytics/Writers/PostgresEventWriter.php, `upsertSession()`
    - **Affects:** Session/duration/live-visitor tracking for any two sites that happen to receive a ping carrying the same client-minted session UUID (e.g. a bug in the frontend tracker reusing a session ID across subdomains, rather than a realistic UUID-guessing attack).
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Change the primary key to a composite `(id, site_id)` (migration + unique constraint change) so the same client-minted UUID on two different sites is never treated as the same row.
    - **Technical:** `INSERT ... ON CONFLICT (id) DO UPDATE ... WHERE site_sessions.site_id = EXCLUDED.site_id` — in Postgres, when a row conflicts on the PK but the `WHERE` condition evaluates false, **both** the UPDATE and the (already-blocked) INSERT are skipped: the write is a silent no-op. The `WHERE` clause guards against writing into a different site's session row, but its side effect is that the second site's ping is dropped entirely rather than being recorded under its own identity. This requires a session-UUID collision across two different sites, which is astronomically unlikely for a properly-random client-generated UUID and not currently an attacker-controlled input — hence P2 rather than P0/P1 — but a composite key removes the possibility entirely rather than relying on UUID randomness.
    - **Plain English:** Each visitor session gets a unique ticket number generated by their browser. The database's "update this session" logic assumes ticket numbers are only ever reused by the SAME site. If two different sites' visitors ever ended up with the same ticket number, the second one's ping would be silently thrown away instead of recorded, with no error anywhere. This isn't something an attacker can easily trigger today, but it's a real gap in an assumption the code is making.
    - **Evidence:**
        ```php
        DB::connection('pgsql')->statement(
            "INSERT INTO analytics.site_sessions
                (id, user_id, site_id, visitor_id, started_at, last_seen_at, duration_seconds,
        ```
