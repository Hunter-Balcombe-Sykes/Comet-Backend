## P3 — Nice to have

- [ ] **#XDEAD-1** · P3 — Orphaned pre-Astro-split "public sitepage" BFF/query surface, half of it pointing at backend routes that no longer exist
    - **Where:**
        - `$PARTNA_FRONTEND_PATH/app/api/public/booking/{_shared,availability,checkout,config,services}/route.ts`
        - `$PARTNA_FRONTEND_PATH/app/api/public/waitlist/route.ts`
        - `$PARTNA_FRONTEND_PATH/lib/queries/public.ts`, `$PARTNA_FRONTEND_PATH/lib/queries/fetchers/public.ts`
    - **Affects:** No real user path today — every entry point is unreferenced. Risk is to future developers: this code presents as a working "public sitepage" data layer (its own header calls it the "Public sitepage rendering query factory") and would silently fail or mislead someone into rebuilding removed booking-checkout machinery if wired up. Also unnecessary live public HTTP surface — `/api/public/waitlist` and the four `/api/public/booking/*` routes are still deployed, unauthenticated POST/GET endpoints that always dead-end in a 502.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Confirm via Cloud access logs that nothing external hits `/api/public/booking/*` or `/api/public/waitlist` (belt-and-suspenders — static analysis here is already conclusive).
        - Delete `app/api/public/booking/` (all 5 files) and `app/api/public/waitlist/route.ts`.
        - Delete `lib/queries/public.ts` and `lib/queries/fetchers/public.ts`; trim the corresponding cases out of `lib/queries/public.test.ts` (currently the *only* caller of any of these 7 query factories).
        - If a future feature needs public-sitepage data inside the dashboard app, build it fresh against the current backend contract (`GET /public/profiles/{handle}`, `GET /public/site-by-slug`) rather than resurrecting this file — 3 of its 7 targets (`booking/*-by-slug`, `config/integrations`) no longer exist on the backend.
    - **Technical:** Two independent dead layers share one root cause: leftover scaffolding from before the public sitepage renderer moved to the separate `@partnaau/design-system`/Astro stack, never swept during the 2026-05-22 standalone strip-down or since. (1) The Next.js Route Handlers under `app/api/public/booking/*` proxy to `/public/booking/{services,availability,checkout}-by-slug` on the Laravel backend — none of these paths exist anywhere in `routes/` (confirmed by grep across the full `routes/` tree). (2) `app/api/public/waitlist/route.ts` proxies to `${apiBaseUrl}/public/waitlist` and its own docblock names the handler `PublicWaitlistController::store` — that class no longer exists in `app/Http/Controllers/` (only a stale docblock reference survives in `DataExportPayloadBuilder.php`: "Mirrors PublicWaitlistController..."); the waitlist→early-access rename shipped 2026-07-19, and the live landing page (`app/(marketing)/page.tsx`, `app/(marketing)/waitlist/page.tsx`) already correctly posts through `EarlyAccessForm` to `/api/public/early-access`, which forwards to the real, existing `POST /public/early-access` route. (3) `lib/queries/public.ts` + `lib/queries/fetchers/public.ts` — a 7-member React Query factory whose own header calls it the "Public sitepage rendering query factory" — is referenced *only* by `lib/queries/public.test.ts`; no page or component calls `publicQueries.profile`, `.siteBySlug`, `.bookingConfig`, `.bookingServices`, `.joinByHandle`, `.configIntegrations`, or `.configSocialPlatforms`. Three of those targets are additionally stale: `bookingConfig`/`bookingServices` hit the same nonexistent `*-by-slug` routes as (1), and `configIntegrations` hits `/public/config/integrations`, which `routes/api.php` documents as intentionally moved behind auth ("public-surface/SEC-1: GET /public/config/integrations (Google Maps key) moved behind auth ... no product reason for it to be reachable pre-auth"). None of this is reachable today (confirmed: even the frontend team's own `docs/superpowers/plans/2026-07-22-file-audit-checklist.md` still lists these files as unchecked), so it's dead-code hygiene, not a live regression — but it's the kind of trap that costs real hours if a future engineer assumes it's load-bearing.
    - **Plain English:** There's a chunk of code in the dashboard app that was built to let a website visitor book an appointment or join a waitlist directly through this app. Nothing in the app actually uses it anymore — it's like a phone extension still wired into the switchboard that nobody dials. Worse, if anyone tried to use it, the call wouldn't go through: the phone number on the other end (the backend feature it was built to reach) was renamed or disconnected months ago. It's not hurting anyone sitting there, but it's confusing clutter that could waste a future developer's afternoon, or worse, trick someone into rebuilding a "book an appointment" feature that was deliberately retired.
    - **Evidence:**
