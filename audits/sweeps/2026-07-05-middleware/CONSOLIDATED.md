- [ ] **#PRIV-1** · P1 — Idempotency-key response cache survives account deletion, leaving PII in Redis for up to 24 hours
    - **Where:** app/Http/Middleware/IdempotencyKey.php (`Cache::put` in `handle()`; no invalidation hook anywhere in the account-deletion/purge flow)
    - **Affects:** Any user who deletes their account after making a mutating request with an `Idempotency-Key` header in the prior 24h — their cached response body (profile data, site data, email, handle) remains in Redis until natural TTL expiry, past the point the platform tells them their data is gone.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Add a cache-invalidation step to `AccountDeletionService` (the hard-purge path, alongside the existing Supabase Admin API delete + `core.users` row deletion) that scans and deletes Redis keys matching `idempotency:resp:*:<user_id>:*`.
        - Given Redis doesn't support pattern-delete atomically at scale, either maintain a small per-user index of active idempotency cache keys (set on write, consulted + cleared on purge) or accept the 24h residual window explicitly and document it in the data-retention policy.
    - **Technical:** The middleware caches full HTTP response bodies (status, body, headers) in Redis under `idempotency:resp:{version}:{userId}:{route}:{key}` with a ±20%-jittered 24h TTL. `shouldCache()` only excludes 5xx, streamed, and >256KB responses — any successful mutating request that echoes back the updated resource (site update, profile update, etc.) embeds PII in the cached payload. After purge, the `userId` UUID is gone from `core.users` but the cache entry is still keyed by it and readable by anything with Redis access until natural expiry.
    - **Plain English:** Think of idempotency like a receipt printer at a shop — when you submit a change, it keeps a copy of the response for 24 hours so an accidental double-submit shows the same result instead of doing the action twice. When someone closes their account, the system erases their main record but never empties this receipt printer's memory. Their profile data, site content, or email can sit in that memory for up to a day after they've deleted their account — a real gap for a "delete my data" promise.
    - **Evidence:**

    - **Plain English:** A counter that's supposed to reset every hour gets its "reset timer" attached one step after it starts counting.
