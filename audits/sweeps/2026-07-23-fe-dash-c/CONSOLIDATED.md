## P2 — Should fix

- [ ] **#XREPO-1** · P2 — Four booking BFF proxy routes are dead plumbing pointing at nonexistent backend endpoints
    - **Where:** `$PARTNA_FRONTEND_PATH/app/api/public/booking/availability/route.ts:20`, `checkout/route.ts:20`, `config/route.ts:14`, `services/route.ts:14` (+ shared helper `_shared.ts`)
    - **Affects:** No current user — zero live callers found. Risk is latent: if a future page ever wires up a "book now" widget by calling these BFF paths, it will 502 immediately because the backend paths they forward to don't exist.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Delete the four route files (`availability`, `checkout`, `config`, `services`) and `_shared.ts` if nothing else imports `buildBookingUpstreamTargets`/`proxyUpstreamGet`/`proxyUpstreamPost`.
        - Also delete `publicQueries.bookingConfig`/`bookingServices` in `lib/queries/public.ts` and their fetchers in `lib/queries/fetchers/public.ts` — these bypass the BFF and call the backend directly at `/public/booking/config-by-slug` / `services-by-slug`, which also don't exist; their only reference in the whole repo is an assertion in `lib/queries/public.test.ts` (staleTime only, not a real render path).
        - Do **not** touch `app/(app)/account/(dashboard)/booking/*` or `routes/api/platforms.php`'s `{base}/booking` prefix / `PATCH api/booking/settings` — that's a live, correctly-wired feature (connecting a *third-party* booking provider like Fresha/OpenTable for the dashboard), a completely separate concept from the dead first-party public-checkout widget these BFF routes were built for.
    - **Technical:** Each route builds an upstream target via `buildBookingUpstreamTargets(slug, "/public/booking/{availability,checkout,config,services}-by-slug")` and proxies GET/POST to the Laravel backend. Grepping this repo's `routes/api/publicSite.php`, `routes/api/user.php`, and `routes/api/platforms.php` for `booking/availability-by-slug|booking/checkout-by-slug|booking/config-by-slug|booking/services-by-slug` returns zero matches — no such backend route was ever registered (the platform-level `booking` routes in `platforms.php:175` and `user.php:143`'s `/booking/settings` are the *provider-integration* dashboard feature, an unrelated subsystem). Grepping the frontend tree for any caller of these four BFF paths (`/api/public/booking/*`) turns up only the route files themselves and a stale planning doc — no `.tsx` page or component ever calls them. Separately, `lib/queries/fetchers/public.ts` defines `fetchPublicBookingConfigBySlug`/`fetchPublicBookingServicesBySlug`, which call the backend directly at the same nonexistent paths; their only consumer, `publicQueries.bookingConfig`/`bookingServices`, is exercised solely by `lib/queries/public.test.ts` asserting `staleTime` — not a real render path. This is category (3) from the XREPO lens — vestigial BFF plumbing for a subsystem the backend never shipped (public first-party booking checkout), not a live 404.
    - **Plain English:** These are four mailboxes bolted onto the front porch that connect to nothing inside the house. The public "book an appointment directly through Partna" feature never made it into the backend, but the wiring for it is still sitting in the frontend, unused. Nobody's mail is getting lost today because nobody's using these mailboxes — but if a future feature accidentally wires up a "Book now" button to point at them, visitors would get a silent failure. Best to remove the dead wiring now, before it looks like a working feature to a future developer.
    - **Evidence:**
        ```ts
        // frontend: app/api/public/booking/availability/route.ts:20
        const targets = buildBookingUpstreamTargets(slug, "/public/booking/availability-by-slug");
        return proxyUpstreamPost(targets, payload);
        ```
        ```ts

        expect(publicQueries.bookingConfig("alice").staleTime).toBe(STALE_TIME.SLOW)
        expect(publicQueries.bookingServices("alice").staleTime).toBe(STALE_TIME.SLOW)
        ```
        ```
        # backend: grep -r "booking/availability-by-slug\|booking/checkout-by-slug\|booking/config-by-slug\|booking/services-by-slug" routes/ → zero matches
        ```

- [ ] **#XREPO-2** · P2 — Waitlist BFF route proxies to a backend endpoint that was superseded by early-access, and nothing calls it anymore
    - **Where:** `$PARTNA_FRONTEND_PATH/app/api/public/waitlist/route.ts:47-61` (BFF) → backend `POST /public/waitlist` (does not exist)
    - **Affects:** No current user — the live `/waitlist` marketing page's form does not call this route (see evidence below), so nobody actually hits the dead proxy today. Risk is latent: any future code that resurrects a call to `/api/public/waitlist` (e.g. copy-pasting this route as a template) inherits a silent 502.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Delete `app/api/public/waitlist/route.ts` — the `/waitlist` marketing page already uses `EarlyAccessForm`, which correctly posts to `/api/public/early-access` (a MATCHED, live backend route).
        - Grep the frontend one more time for `/api/public/waitlist` immediately before deleting, in case a branch in flight reintroduces a caller.
    - **Technical:** The route does `fetchWithHardTimeout(`${apiBaseUrl}/public/waitlist`, ...)` and returns a 502 fallback on any non-2xx/failure. Grepping this repo's `routes/` for `waitlist` returns zero matches anywhere (`routes/api.php`, `routes/api/publicSite.php`, `routes/api/user.php` all clean) — the backend has no `PublicWaitlistController` or `waitlist_signups` table; the actual signup path is `PublicEarlyAccessController::store` writing to `core.early_access_signups` (confirmed live via `app/Http/Controllers/Api/PublicSite/PublicEarlyAccessController.php` and `app/Http/Requests/Api/PublicSite/PublicEarlyAccessSignupRequest.php`), matching the CONTRACT-INVENTORY's MATCHED entry for `api/public/early-access`. Crucially, the frontend's own `/waitlist` page (`app/(marketing)/waitlist/page.tsx`) renders `<EarlyAccessForm variant="full" ... />`, and `early-access-form.tsx:55` hardcodes `const EARLY_ACCESS_ENDPOINT = "/api/public/early-access"` — the visible waitlist form already posts to the correct, working endpoint. The `app/api/public/waitlist/route.ts` BFF file is therefore orphaned: a leftover from before the early-access rename, with the old name and the old (now-removed) backend path, and zero live callers.
    - **Plain English:** There's old wiring left over from before this feature was renamed. The visible "join the waitlist" form on the website already uses the correct, working address — but there's a second, forgotten address on file that points to a mailbox that no longer exists. Nobody's using the old address today, so no signups are actually being lost, but it's confusing dead weight that should be cleaned up so a future developer doesn't accidentally wire something back up to it.
    - **Evidence:**
        ```ts

        const response = await fetchWithHardTimeout(
          `${apiBaseUrl}/public/waitlist`,
          {
            method: "POST",
            headers: {
              Accept: "application/json",
              "Content-Type": "application/json",
              ...(forwardedFor ? { "X-Forwarded-For": forwardedFor } : {}),
              ...(userAgent ? { "User-Agent": userAgent } : {}),
            },
            body,
            cache: "no-store",
          },
          UPSTREAM_TIMEOUT_MS,
        )
        ```
        ```ts
        // frontend: app/(marketing)/_components/early-access-form.tsx:55 — the LIVE waitlist page's actual form target

        ```
