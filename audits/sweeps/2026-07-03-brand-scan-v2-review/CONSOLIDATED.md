**#SEC-3 (SSRF) — DECISION: BOTH, staged.**
- *This pass (in-repo):* add a pre-check in `BrandScanClient::snapshot()` — call
  `SafeUrlFetcher::assertPublicUrl($url)` (scheme ∈ http(s); host resolves to a
  public IP only) BEFORE the Worker POST. Purpose is cost/junk-rejection (don't
  spend a paid Browser Run on a bad URL) + consistency with the direct-fetch
  path. Frame it as that — NOT as the SSRF boundary.
- *Separate task (cannot land from this backend repo):* the AUTHORITATIVE SSRF
  guard belongs at the fetch point inside the `partna-brand-scan` Worker. The
  backend check is TOCTOU/DNS-rebind-advisory only and never sees redirects.
  Track as a follow-up in that repo — or first verify whether CF Browser
  Rendering's sandbox already blocks the threat model and downgrade to
  "verified, no action." → SEC-3 moved to Standalone.

**#LIFE-1 + outside-link overflow — DECISION: crash-safety + self-continue (paced).**
- *Crash-safety (LIFE-1):* checkpoint each shop-brand analysis with its own
  `update()` as it completes. (Custom links already checkpoint per-connection;
  shop connections currently batch all brands into one save, so a mid-loop crash
  re-pays for completed Browser Runs on retry.)
- *Overflow (Agent B Finding 5 — not a lens finding):* when
  `MAX_ANALYSES_PER_RUN` budget is exhausted AND stragglers remain, re-dispatch
  `AnalyzeConnectionWebsitesJob` with a delay to process the next batch until
  done. The idempotent `entryNeedsAnalysis()` check terminates it naturally.
  KEEP the 15-cap for per-run bounding — this does NOT raise total Browser Runs,
  it just guarantees + paces them. (Lives in Bundle 1.)

**#TXN-1 — annotation (Agent A / F8): asymmetric error isolation is the real defect.**
- Not just the missing transaction: `DesignPresetResolver::resolveForUser()`
  wraps SITE-level factors (previous-website/outside-websites) in try/catch, but
  the PER-CONNECTION loop (Google Business / Instagram) has NO try/catch. One
  throwing connection factor aborts the whole resolve — including the healthy
  isolated site factors — and, with no transaction, can leave
  `design_kit_contributions` partially synced until the job retries. Fix should
  give BOTH loops the same isolation (or wrap the method in a transaction) so the
  docblock's "a factor that throws degrades to empty, never a failed job" is
  actually true system-wide. Related: #OBS-7 (duplicate dead try/catch around
  `presetLayer()`) is the same area — clean up together (Bundle 1 + Bundle 10).

**#LIFE-3 — annotation (Agent B / Finding 3): uncaught analyzer throw strands the row.**
- Only `BrandScanException` / `SafeUrlException` are caught inside
  `WebsiteStyleAnalyzer::analyze()` (those write a valid `ok:false` doc —
  loop-safe). ANY other throw (a bug in `EvidenceConclusions` /
  `ScreenshotSampler`) propagates out of `AnalyzePreviousWebsiteJob::handle()`
  with NO write-back, so `previous_website_analysis` stays out of sync and
  `WorkplaceObserver::reconcile()` re-dispatches the job on EVERY future
  unrelated Workplace edit (bio, address…) — hammering the Worker with no
  negative-result caching. Fix: top-level try/catch in the job that persists a
  failure doc, matching the pattern already used for the two caught exceptions.
  (Moved into Bundle 1.)
