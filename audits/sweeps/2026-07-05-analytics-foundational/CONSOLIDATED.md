## P1 — Fix before pilot launch

- [x] **#FOUND-1** · P1 — Staff analytics `top_links` silently excludes every v2 (skeleton-era) click, duplicating queries that already exist in `AnalyticsQueryService`
    - **Where:** app/Http/Controllers/Api/Staff/StaffSite/StaffAnalyticsController.php:98-135
    - **Affects:** Staff support view of a professional's top links (`GET /api/staff/professionals/{professional}/analytics`) — already returns an incomplete/wrong list for any professional using skeleton-era (url-based) link clicks.
    - **Effort:** M (~2–4h)
    - **What to do:**
        - Replace the inline `visits_by_day` / `clicks_by_day` `DB::table()` queries with `AnalyticsQueryService::visitsByBucket()` / `clicksByBucket()` — same tables, same aggregation, one fewer place to keep in sync.
        - Replace the `join('site.blocks as b', ...)` top-links query with `AnalyticsQueryService::topLinks()`, which already reads `WHERE url IS NOT NULL` (no block join) and covers both legacy block-clicks and v2 self-describing clicks.
        - Since the staff view wants a narrower payload than the professional's own dashboard, add a `staffSummary()` method (or an `$includeSections` flag) to `AnalyticsCacheService` rather than re-deriving composition logic in the controller — `config/partna.php` already uses this "derive from one source" pattern for `section_block_types` (line 799), so there's local precedent.
    - **Technical:** This is not a future-deprecation risk — it is a live data gap today. Migration `20260610000000_analytics_v2_clicks_sessions.sql` (landed ~3 weeks ago) made `link_clicks.link_block_id` nullable and added `url`/`platform`/`product_id`/`section_key` so v2 clicks self-describe without a `site.blocks` row. `AnalyticsQueryService::topLinks()` was updated accordingly to `whereNotNull('url')` with no join. `StaffAnalyticsController::summary()` was never updated: its `top_links` query does an **inner join** on `site.blocks`, so any click row with `link_block_id IS NULL` (every v2 click) is silently excluded from the staff view — while the professional's own dashboard, reading the same click table through `AnalyticsQueryService`, shows the complete picture. Note `site.blocks` itself is not going away — migration `20260705120000_drop_dead_profile_features.sql` (today, part of commit `31115f15`) just narrowed its `block_type` CHECK to 10 surviving section types (`gallery`, `services`, `booking`, `contacts_collection`, `barbershop_info`, `documents`, `newsletter`, `contact`, `public_contact`, `workplace`) — the table is actively maintained, not deprecated. The bug is purely that one read path (staff) missed the v2 migration that the other read path (professional) already absorbed.
    - **Plain English:** The professional's own dashboard and the staff support dashboard both show "your most-clicked links," but they ask the database two different questions. Three weeks ago the main dashboard was updated to understand a new kind of click that doesn't have an old-style "block" attached to it — new-format sitepages generate these by default. The staff screen was never updated, so today it just doesn't show those clicks at all — support staff looking at a professional's account see fewer (or zero) top links than the professional sees on their own screen. Fixing it means pointing the staff screen at the same up-to-date question the main dashboard already asks.
    - **Evidence:**
        ```php
        // Daily charts
        $visitsByDay = DB::table('analytics.site_visits')
            ->where('user_id', $professional->id)
            ->whereBetween('occurred_at', [$from, $to])
            ->selectRaw('DATE(occurred_at) as day, COUNT(*) as count')
            ->groupByRaw('DATE(occurred_at)')
            ->orderBy('day')
            ->get();
        ```
        ```php
        try {
            // Top links
            $topLinks = DB::table('analytics.link_clicks as lc')
                ->join('site.blocks as b', 'b.id', '=', 'lc.link_block_id')
                ->where('lc.user_id', $professional->id)
                ->whereBetween('lc.occurred_at', [$from, $to])
                ->whereRaw("LOWER(COALESCE(b.block_group, '')) = 'links'")
                ->whereRaw("LOWER(COALESCE(b.block_type, '')) = 'link'")
                ->selectRaw('b.id as block_id, b.title, b.url, COUNT(*) as clicks')
                ->groupBy('b.id', 'b.title', 'b.url')
                ->orderByDesc('clicks')
                ->limit(10)
                ->get();
        } catch (Throwable $e) {
            Log::warning('staff.analytics.click_query_failed', ['professional_id' => $professional->id, 'error' => $e->getMessage()]);
            $topLinks = collect();
        }
        ```

## P2 — Should fix

- [ ] **#FOUND-2** · P2 — `sectionTitle()` is a hand-maintained match expression that a new skeleton section requires a code deploy to update
    - **Where:** app/Services/Analytics/AnalyticsQueryService.php:442-469
    - **Affects:** The "top sections" chart on the professional analytics dashboard — labels for skeleton sitepage sections.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Move the section-key → title map into `config/partna.php` (e.g. `analytics.section_titles`), following the same "single source" pattern already used for `section_block_types` in the same config file.
        - Keep the `default` fallback (`ucfirst(str_replace('_', ' ', $sectionKey))`) so unrecognized keys still render.
    - **Technical:** The method hardcodes a ~20-arm `match()` mixing legacy block-era keys (`gallery`, `services`, `booking`) with skeleton-era keys (`shop`, `music`, `podcast`, `book`, `events`). Adding a new skeleton section (e.g. a future "courses" section) requires a backend deploy to this one method. It's P2 rather than P1 because it's already centralized in one place and the `default` arm handles unrecognized keys gracefully — nothing breaks today, but every new section type re-couples a product/config change to a code release.
    - **Plain English:** Every section on a professional's page has a short code name like "shop" or "music," and the analytics dashboard needs to turn that into a friendly label like "Shop." That translation list currently lives inside a code file, so adding a new section type means an engineer has to edit and redeploy code. Moving it into a settings file lets that translation be added without a backend release.
    - **Evidence:**

- [ ] **#FOUND-3** · P2 — `SOURCE_CASE` and `REFERRER_LABELS` are two hand-synced constants that will silently drift
    - **Where:** app/Services/Analytics/AnalyticsQueryService.php:41-59 (`SOURCE_CASE`), :62-66 (`REFERRER_LABELS`)
    - **Affects:** The referrer breakdown chart on the professional analytics dashboard.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Extract the referrer source definitions into a single data structure (e.g. an array of `label => match patterns`) and derive both the SQL `CASE` string and the `REFERRER_LABELS` order from it at construction time.
        - No urgency signal today — the two lists are currently in sync (verified label-for-label) — but the fix removes the need to keep them that way by hand going forward.
    - **Technical:** `SOURCE_CASE` is a ~19-line SQL `CASE` mapping utm_source/referrer patterns to labels; `REFERRER_LABELS` is a separately maintained PHP array of the same labels in display order, consumed by `referrers()`'s `keyBy('source')` lookup. Today the two are in sync, so this isn't an active bug — but adding a new platform (Threads, Bluesky) requires a coordinated edit to both, and if the spelling in the `CASE`'s `THEN` clause ever diverges from the array entry, `$raw->get($label)` silently returns null and the array_map zero-fills that label with no error. This is the textbook P2 "hardening" case — the failure requires a future edit mistake that hasn't happened yet.
    - **Plain English:** Imagine a restaurant where the kitchen writes dish names in one notebook and the waitstaff writes the same names in a separate notepad. Every time a new dish is added, both lists must be updated with matching spelling, or the waitstaff won't recognize an order the kitchen sends out. Today both lists match perfectly, but the design requires a human to keep them in sync forever — one future typo silently makes a traffic source disappear from the charts with no error.
    - **Evidence:**
        ```php
        private const SOURCE_CASE = "
            CASE
                WHEN COALESCE(utm_source,'') ILIKE 'instagram%' OR COALESCE(referrer,'') ILIKE '%instagram.com%' OR COALESCE(referrer,'') ILIKE '%l.instagram.com%' THEN 'Instagram'
                WHEN COALESCE(utm_source,'') ILIKE 'facebook%'  OR COALESCE(referrer,'') ILIKE '%facebook.com%'  OR COALESCE(referrer,'') ILIKE '%lm.facebook.com%'  OR COALESCE(referrer,'') ILIKE '%l.facebook.com%' THEN 'Facebook'
                WHEN COALESCE(utm_source,'') ILIKE 'tiktok%'    OR COALESCE(referrer,'') ILIKE '%tiktok.com%'    THEN 'TikTok'
                ...
                WHEN referrer IS NULL OR referrer = '' THEN 'Direct Link'
                ELSE 'Other'
            END
        ";

        private const REFERRER_LABELS = [
            'Organic (Google)', 'Organic (Bing)', 'Organic (DuckDuckGo)', 'Organic (Yahoo)',
            'Instagram', 'Facebook', 'TikTok', 'YouTube', 'X (Twitter)', 'LinkedIn',
            'Snapchat', 'Pinterest', 'Reddit', 'Direct Link', 'Other',
        ];
        ```

- [ ] **#FOUND-4** · P2 — Analytics write models omit v2 columns from `$fillable`, a silent-write trap for the next developer who uses `::create()`
    - **Where:** app/Models/Analytics/LinkClick.php:26-36, app/Models/Analytics/SiteVisit.php:26-38
    - **Affects:** Any future code that writes via `LinkClick::create()` / `SiteVisit::create()` / mass-assignment instead of the query-builder `insertOrIgnore()` path the current writer uses.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add `url`, `platform`, `product_id`, `product_title`, `section_key`, `label`, `country_code`, `region_code`, `device_type` to `LinkClick::$fillable`.
        - Add `region_code` to `SiteVisit::$fillable` (the column exists per migration `20260610000000` but isn't listed; `country_code`/`device_type` are already present).
    - **Technical:** `PostgresEventWriter` writes via `LinkClick::query()->insertOrIgnore($rows)` / `SiteVisit::query()->insertOrIgnore($rows)` — the query builder, which bypasses Eloquent's mass-assignment guard entirely, so today nothing is broken. Confirmed via repo-wide search: no call site currently uses `LinkClick::create()`, `SiteVisit::create()`, or `SectionView::create()`. But migration `20260610000000_analytics_v2_clicks_sessions.sql` added 8 columns to `link_clicks` and `region_code` to `site_visits` without a matching model update — the next developer who reaches for the normal Eloquent API (`LinkClick::create([...])`) will have every v2 column silently dropped to null with no exception, no log. This is a foot-gun waiting for its first victim, not a live bug.
    - **Plain English:** The database table has extra columns that the model's "official column list" doesn't know about. The current code works because it uses a back door that skips that list. But if a future feature uses the normal front door, those extra columns get silently emptied instead of erroring — like a room in a house that isn't on the floor plan; it's fine until someone tries to furnish it using the plan.

- [ ] **#FOUND-5** · P2 — `RecordAnalyticsEventJob::failed()` logs a payload key that doesn't exist, so every permanently-dropped analytics event logs `event_type: unknown`
    - **Where:** app/Jobs/Analytics/RecordAnalyticsEventJob.php:54-62
    - **Affects:** Nightwatch/log-based diagnosis of permanently-failed analytics ingest jobs (pageview/click/section_view/session_ping) — every occurrence loses the one field that would say which kind of event was dropped.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Change `$this->payload['event_type']` to `$this->payload['type']` — the actual key `AnalyticsEvent::toArray()` emits.
        - Consider also logging `site_id`/`user_id` from the payload (both present in `toArray()`) so a real incident can be traced back to the affected professional, matching the `Log::warning` + `user_id` correlation pattern used elsewhere in this codebase.
    - **Technical:** `AnalyticsEvent::toArray()` serializes the event with key `'type'` (`'type' => $this->type`), never `'event_type'`. `RecordAnalyticsEventJob::$payload` is exactly that array (constructor docblock: `AnalyticsEvent::toArray()`). The `failed()` handler reads `$this->payload['event_type'] ?? 'unknown'`, which is always the `'unknown'` fallback — a real key-name bug, not a hypothetical. This job's own docblock notes it's "at-least-once" with `insertOrIgnore` neutralising duplicate retries, meaning a genuine permanent failure (3 tries exhausted) is meant to be diagnosable from this log line; today it silently loses the one piece of information (which event type: pageview/click/section_view/session_ping) needed to triage it.
    - **Plain English:** When an analytics event (a page visit, a click, etc.) fails to save three times in a row, the system logs an error so engineers can investigate. That log message tries to say what kind of event failed, but it's looking for the wrong label internally — so it always prints "unknown" instead of "click" or "pageview." It's a one-line typo, but it means today, if something goes wrong with analytics recording, the error log can't tell you what broke.
    - **Evidence:**
        ```php
        public function failed(Throwable $e): void
        {
            report($e);
            Log::error('Analytics event permanently dropped', [
                'job' => static::class,
                'event_type' => $this->payload['event_type'] ?? 'unknown',
                'error' => $e->getMessage(),
            ]);
        }
        ```
