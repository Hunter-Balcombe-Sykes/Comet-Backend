- [x] **#SCHEMA-1** · P2 — `site.platform_connections` has RLS `ENABLE`d but not `FORCE`d, unlike every comparable table
    - **Where:** supabase/migrations/20260609000000_harden_platform_connections.sql:30-35
    - **Affects:** Defence-in-depth against a future PostgREST/Studio/raw-query exposure of tenant platform-connection data.
    - **Effort:** S (~0.5–1h) — pair with #SCHEMA-2 in one migration.
    - **What to do:**
        - Add `ALTER TABLE site.platform_connections FORCE ROW LEVEL SECURITY;` in a follow-up migration.
        - Add a `tests/Feature/Security/` regression (none exists for this table today — the exemplars are `DesignKitsRlsTest` and `ModerationSchemaRlsTest`).
    - **Technical:** The hardening migration runs `ENABLE ROW LEVEL SECURITY` but omits `FORCE`. Verified live on dev (`glncumufgaqcmqhzwrxm`): `pg_class.relrowsecurity = true`, `relforcerowsecurity = false`; and `information_schema.role_table_grants` shows **only `app_backend`** holds table privileges (no `anon`/`authenticated`/`PUBLIC`). `app_backend` carries `BYPASSRLS` (baseline `ALTER ROLE app_backend BYPASSRLS`), so the app path is unaffected either way and there is no live exposure. But `20260602000000_design_kits_rls.sql` and `20260606030000_moderation_schema_rls.sql` both pair `ENABLE` with `FORCE`; `platform_connections` is the one hardened table inconsistent with that pattern, with no regression test pinning it.
    - **Plain English:** We put a lock on this table's door (RLS on) but left the frame loose — the account that owns the table can still walk through without a key. Every other similarly-hardened table in this codebase bolts the frame shut (`FORCE`); this one was missed. The app's own account bypasses the lock by design today, so nothing breaks — this closes the gap before someone changes the door.
    - **Evidence:**
        ```sql
        ALTER TABLE site.platform_connections ENABLE ROW LEVEL SECURITY;   -- no matching FORCE ROW LEVEL SECURITY
        CREATE POLICY platform_connections_app_backend_all
            ON site.platform_connections
            FOR ALL TO app_backend
            USING (true) WITH CHECK (true);
        ```
        ```text
        live dev DB: site.platform_connections rls_enabled=true, rls_forced=false; table grants = app_backend only
        ```

- [x] **#SEC-3** · P2 — Dropped `platform` DB CHECK left the app guard as the sole gate: it is unreported *and* bypassable
    - **Where:** app/Models/Core/Site/IntegrationConnection.php:71-86 (`saving()` guard) · supabase/migrations/20260629120000_drop_platform_connections_check.sql (CHECK removed, no DB backstop)
    - **Affects:** Integrity + failure-visibility of the `platform` column on `site.platform_connections`.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Keep the guard's blocking behavior, but make failures observable: `report()` a dedicated non-suppressed exception (or `Log::error()` + `report()`) instead of relying on `ValidationException` alone — `ValidationException` is in Laravel's `Illuminate\Foundation\Exceptions\Handler::$internalDontReport`, so it is **never** passed to `report()` (an unregistered-platform write in a queued job fails the job with no Nightwatch signal beyond the generic job-failure).
        - Close the bypass: the `static::saving()` closure does **not** fire on `saveQuietly()`, Query-Builder `->insert()`, or `->upsert()`. Since the DB CHECK is gone there's no backstop, so make the platform-validity invariant hold on all write paths (a lightweight DB trigger/CHECK against the registry-known set, or a single guarded write method) — or add a regression asserting it.
    - **Technical:** `20260629120000` dropped `platform_connections_platform_check`, so the model's `saving` closure (validates `platform` against `PlatformRegistry` when dirty) is the only thing preventing an arbitrary `platform` string from being stored. Two gaps: (1) it throws `ValidationException`, which Laravel never reports, so a guard trip in a background context is invisible; (2) it is an Eloquent *event*, skipped by `saveQuietly()`/`insert()`/`upsert()`. Verified no current path exploits (2): all `saveQuietly()` calls on this model (`InstagramConnectJob:310`, `GoogleBusinessController:164`, `GoogleBusinessEnrichJob:105/149`) touch status/payload on an existing row and never set `platform`; no raw `DB::table('site.platform_connections')` write exists. Impact even if bypassed is low — an unknown `platform` is inert (`PublicIntegrationConnectionResource` fail-closes it to `{}`, no controller `platform()` matches, the refresher skips it) — so this is hardening, not an open hole, but it is exactly the single-gate-with-holes shape the CHECK removal traded away.
    - **Plain English:** There used to be two guards checking a connection's "platform" name is real — a database rule and an app rule. The database rule was removed on purpose, leaving only the app rule, which (a) raises an alarm the monitoring system is wired to ignore, and (b) has side doors (certain fast/bulk saves skip it). No code walks through those doors today and a bad value would just sit there inert — so it's safe — but restoring a backstop and a real alarm means the check can't be quietly skipped or silently failed later.
    - **Evidence:**
        ```php
        static::saving(function (self $connection) {
            if (! $connection->isDirty('platform')) {
                return;               // status-only updates skip; saveQuietly()/insert()/upsert() skip the event entirely
            }
            $platform = $connection->platform;
            if (! is_string($platform) || ! app(PlatformRegistry::class)->has($platform)) {
                throw ValidationException::withMessages([   // in $internalDontReport → never report()ed
                    'platform' => 'The selected platform is not a supported platform.',
                ]);
            }
        });
        ```

- [x] **#SEC-2** · P2 — Instagram media mirror uses a host-string allowlist, not `SafeUrlFetcher` IP-resolution
    - **Where:** app/Jobs/Platforms/InstagramConnectJob.php:196-227 (`mirrorOne`), 229-286 (`mirrorVideo`), 288-302 (`isAllowedHost`)
    - **Affects:** The Instagram auto-connect pipeline — media fetched from a scraper-supplied CDN URL and `Storage::put()` to R2. Risk class: SSRF (the exact area that was previously a CRITICAL SSRF in the old `InstagramController::mirror()`).
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Route `mirrorOne()`/`mirrorVideo()` through `SafeUrlFetcher` (or run its `assertSafe()` IP-resolution check before the fetch), so the host is *resolved* and private/reserved/loopback/link-local IPs are rejected — not just string-matched against `cdninstagram.com`/`fbcdn.net`. Keep the content-type + no-redirect + size checks (they're stricter than `SafeUrlFetcher` for this fixed-host case and worth retaining).
        - Add a byte cap to `mirrorOne()` — it buffers the full body via `$response->body()` with no size limit, unlike `mirrorVideo()` which streams to a temp file and enforces `MAX_VIDEO_BYTES`.
    - **Technical:** Unlike every other outbound fetch in the subsystem (all 24 scrapers verified to route through `SafeUrlFetcher`), the IG mirror uses a bespoke, weaker guard: `isAllowedHost()` does a host-**string** allowlist (`$host === $allowed || str_ends_with($host, '.'.$allowed)`) plus `withoutRedirecting()` + a content-type check + (video only) a 50 MB cap. It never resolves the host to an IP, so it does not reject an allowlisted host that resolves to an internal/reserved address. Not exploitable by a normal user today: URLs come from the Apify scrape of the user's own IG profile, so the host is always Meta's CDN — a user cannot make Instagram serve media from an arbitrary host. Reaching an internal IP would require a compromised/malicious Apify response or DNS control over a `cdninstagram.com`/`fbcdn.net` subdomain. Per the audit's own calibration ("host-string allowlist weaker than IP-resolution but not currently exploitable" → P1/P2) this is **P2**, graded seriously because it is the previously-CRITICAL class and the codebase doctrine is "all outbound fetches go through `SafeUrlFetcher`."
    - **Plain English:** When someone connects Instagram, the system downloads their latest photo/reel to store a copy. It checks the address is one of Instagram's known domains and refuses redirects — a real safeguard. But the official tool for this (`SafeUrlFetcher`, used everywhere else) also looks up the real server address and refuses anything pointing at our own internal network; the current check trusts the domain name without that lookup. Because those addresses come from Instagram, not the user, it's safe today — but this is exactly the kind of download that caused a serious hole here once before, so it belongs under the same roof as everything else.
    - **Evidence:**
        ```php
        // mirrorOne — bespoke host-string guard, no IP resolution, no byte cap
        if (! $this->isAllowedHost($url)) { return null; }
        $response = Http::timeout(self::IMAGE_TIMEOUT_SECONDS)
            ->withoutRedirecting()
            ->withHeaders(['Accept' => 'image/*'])
            ->get($url);
        // ...
        Storage::disk('media')->put($path, $response->body());   // full body buffered; no MAX_IMAGE_BYTES

        private function isAllowedHost(string $url): bool
        {
            $host = strtolower((string) parse_url($url, PHP_URL_HOST));
            foreach (self::ALLOWED_HOSTS as $allowed) {           // ['cdninstagram.com', 'fbcdn.net']
                if ($host === $allowed || str_ends_with($host, '.'.$allowed)) {
                    return true;                                  // host STRING match — no IP resolution
                }
            }
            return false;
        }
        ```

## P3 — Nice to have (defense-in-depth)

- [x] **#SEC-1** · P3 — `IntegrationConnection` declares tenant anchor `user_id` in `$fillable` with no post-create immutability guard
    - **Where:** app/Models/Core/Site/IntegrationConnection.php:36-48
    - **Affects:** Any future code path that hydrates this model from unvalidated input — not exploitable today.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - **Do not** simply remove `user_id` from `$fillable`. `tests/Feature/Platforms/PlatformConnectionModelTest.php` and every write path (`ManagesIntegrationConnection::writeConnection`, `EventsCatalog::writeRow`, `GoogleBusinessAutoSync::write`, `InstagramController::connect`) rely on `IntegrationConnection::updateOrCreate(['user_id' => $user->id, ...], [...])`; `updateOrCreate()` mass-assigns the *matching* array (incl. `user_id`) on the create path, so removing it from `$fillable` would break the upsert idiom the whole feature is built on.
        - If a guardrail is wanted, add a narrow `static::saving` check (mirroring the `platform` guard) that rejects a *change* to `user_id` on an already-persisted row — that doesn't conflict with create-time mass assignment.
    - **Technical:** `$fillable` includes `user_id` (the tenant anchor `IntegrationConnectionPolicy::ownerMatches` compares against). Every current write sets it from the resolved authenticated user, never from `$request->validated()` (no Form Request in `app/Http/Requests/Platforms/**` carries a `user_id` rule), and the `create` policy re-checks `skeleton.user_id === actor.id` — so there is no live exploit. The naive "remove from `$fillable`" fix is wrong (breaks tested `updateOrCreate` upserts); any remediation is optional hardening as a change-guard.
    - **Plain English:** In theory, having "who owns this" on the list of fields a form may set sounds risky. In practice every path sets the owner from the logged-in session, never from user input — and the exact database-update pattern this feature relies on actually *needs* that field on the allowed list (a test proves it). So the obvious fix would break working code for no real gain; if anything is done, it should be a narrow rule that only blocks *changing* the owner after creation.
    - **Evidence:**
        ```php
        protected $fillable = [
            'user_id',
            'platform',
            'resource_id',
            'payload',
            // ...
        ];
        ```
