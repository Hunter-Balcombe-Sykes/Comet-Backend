## P2 — Should fix

- [ ] **#XREPO-1** · P2 — Orphaned public-booking BFF/query scaffolding proxies to backend routes that were never built
    - **Where:** `app/api/public/booking/{availability,checkout,config,services}/route.ts`, `app/api/public/booking/_shared.ts`, `lib/queries/fetchers/public.ts:33-38`, `lib/queries/public.ts:25-37`
    - **Affects:** No live user path today — a repo-wide grep of the frontend tree turns up zero callers of any of this code. The risk is latent: it currently misrepresents a public booking-checkout flow as implemented, and a future "book now" widget wired to it would silently hit a 404 instead of a booking confirmation.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Delete `app/api/public/booking/` (the 4 `route.ts` files + `_shared.ts`) — no caller reaches any of it anywhere in the frontend.
        - Delete `fetchPublicBookingConfigBySlug`/`fetchPublicBookingServicesBySlug` from `lib/queries/fetchers/public.ts` and the `bookingConfig`/`bookingServices` entries from `lib/queries/public.ts`; drop the matching assertions in `lib/queries/public.test.ts`.
        - Leave `app/(app)/account/(dashboard)/booking/*` and `BookingDashboardSection` untouched — that page tree is the live, actively-maintained booking-provider-connect feature (Fresha/Square), not related to this dead code.
    - **Technical:** DeepSeek's draft (XREPO-1) claimed the `/account/booking` dashboard page triggers these BFF calls and 404s. That's false on both sides. Backend: grepping `routes/` for `by-slug` and reading `routes/api/publicSite.php` in full confirms no `/public/booking/{availability,checkout,config,services}-by-slug` route was ever registered — no such endpoints exist anywhere in this repo. Frontend: the dashboard's `/account/booking` page mounts `BookingDashboardSection`, which calls the genuinely live `/platforms/{base}/booking`, `/platforms/{base}/fresha`, `/platforms/{base}/square` routes (`routes/api/platforms.php:51-73,175-182` — the "graduated out of Integrations, 2026-07-18" booking-provider-connect feature is current and capability-gated, not dead). Separately, `lib/queries/fetchers/public.ts`'s `fetchPublicBookingConfigBySlug`/`fetchPublicBookingServicesBySlug` fetch the *same* nonexistent backend paths directly (bypassing the BFF entirely) — but `publicQueries.bookingConfig`/`bookingServices` are referenced only from their own test file (`lib/queries/public.test.ts:24-25`), confirming zero production callers. This is dead scaffolding for a public booking-checkout flow that was started on both sides and never finished/wired — not a live 404.
    - **Plain English:** Someone laid the pipework for a "book an appointment right on your Partna page" feature on both ends — the website's side and the matching connection at the office — but the office end was never actually built, and nothing in the app currently turns the tap. Nobody is hurt by it today. But it's still lying there unlabeled, and if a future developer assumes it's connected and builds a button onto it, customers would get an error where they expected a booking confirmation.
    - **Evidence:**
        ```ts

        // POST /api/public/booking/availability — returns available booking slots for a given sitepage slug.
        // Proxies to POST /public/booking/availability-by-slug on the Laravel backend.
        ```
