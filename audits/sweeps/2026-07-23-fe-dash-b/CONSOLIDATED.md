## P3 — Nice to have

- [ ] **#XDEAD-1** · P3 — Orphaned public-booking dead code, duplicated across two frontend surfaces, both targeting a backend API deleted in the 2026-05-22 commerce strip-down
    - **Where:** *(partna-frontend)* `app/api/public/booking/_shared.ts`, `app/api/public/booking/availability/route.ts`, `app/api/public/booking/checkout/route.ts`, `app/api/public/booking/config/route.ts`, `app/api/public/booking/services/route.ts`, `lib/queries/fetchers/public.ts:33-38`, `lib/queries/public.ts:25-37`
    - **Affects:** no live users today (zero callers) — but a future engineer grepping the frontend for "how does public booking work" will find two fully-wired, plausible-looking call paths for an endpoint that has been gone for two months, and waste time chasing it.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - In `partna-frontend`, delete the 5 `app/api/public/booking/**` BFF proxy files (they proxy to `/public/booking/{availability,checkout,config,services}-by-slug`, none of which are registered in this repo's `routes/`).
        - Delete `fetchPublicBookingConfigBySlug` / `fetchPublicBookingServicesBySlug` from `lib/queries/fetchers/public.ts` and the `bookingConfig` / `bookingServices` entries (+ their `public.test.ts` assertions) from `lib/queries/public.ts` — these hit the same dead backend paths directly, bypassing the BFF layer entirely, and have zero importers outside their own test file.
        - Do **not** propose restoring the backend booking API — public booking was removed on purpose in the 2026-05-22 standalone strip-down (commerce/marketplace features are out of scope pre-pilot); this is cleanup only.
    - **Technical:** `routes/` has no `public/booking/*` group — only `App\Http\Controllers\Api\Platforms\BookingController` survives, which is the unrelated platform-*detection* controller (`routes/api/platforms.php:175-181`, `/detect`, `/status`), not a public-facing booking flow. The frontend nonetheless carries two independent, fully-implemented client paths for the deleted public booking API: a Next.js BFF proxy layer (`app/api/public/booking/*/route.ts`, each proxying to `/public/booking/*-by-slug` via `buildBookingUpstreamTargets`) and a direct-fetch TanStack Query layer (`lib/queries/fetchers/public.ts` + `lib/queries/public.ts`). Neither has a live caller anywhere else in the frontend repo (`grep -r "/api/public/booking"` and `grep -r "bookingConfig|bookingServices"` return only the definitions and their own tests), so nothing in production currently reaches either path — this is dead code, not a live 404, which is why it sits at P3 rather than P1.
    - **Plain English:** Two different leftover pieces of the website's code still know how to ask the server for booking information — but the server stopped offering that feature back in May, and nothing on the actual site button-clicks its way to either piece anymore. It's like keeping two different phone numbers on a business card for a service you stopped offering last season — harmless until someone actually dials one and gets confused, or a new hire assumes it still works and builds on top of it. No customer is affected today; it's just clutter worth sweeping out.
    - **Evidence:**
        ```ts
        // POST /api/public/booking/availability — returns available booking slots for a given sitepage slug.
        // Proxies to POST /public/booking/availability-by-slug on the Laravel backend.
        ```
        ```ts
        export async function fetchPublicBookingConfigBySlug(slug: string) {
          return publicFetch(`/public/booking/config-by-slug?slug=${encodeURIComponent(slug)}`)
        }
        export async function fetchPublicBookingServicesBySlug(slug: string) {
          return publicFetch(`/public/booking/services-by-slug?slug=${encodeURIComponent(slug)}`)
        }
        ```
