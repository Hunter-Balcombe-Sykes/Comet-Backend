- [ ] **#SCALE-2** · P2 — `PurgeRawAnalyticsEvents` sequentially scans all five analytics tables on every run; none has a timestamp-leading index
    - **Where:** app/Console/Commands/PurgeRawAnalyticsEvents.php:95-115
    - **Affects:** The daily scheduled purge (`Schedule::command('partna:analytics:purge-raw-events')->dailyAt('03:00')->withoutOverlapping(30)` in routes/console.php) as well as manual `--dry-run` invocations. At 10k users generating 100k-1M page views/day, `analytics.site_visits`/`link_clicks`/`lead_submissions`/`section_views`/`site_sessions` will each hold tens of millions of rows within the 90-day retention window.
    - **Effort:** M (~2-4h)
    - **What to do:**
        - Add a standalone (or timestamp-leading) index per table: `site_visits(occurred_at)`, `link_clicks(occurred_at)`, `lead_submissions(occurred_at)`, `section_views(occurred_at)`, and `site_sessions(last_seen_at)` — all via `CREATE INDEX CONCURRENTLY` in a two-file migration pair (per the repo's own CONCURRENTLY convention, as used in `20260610000001_analytics_v2_click_indexes.sql`).
        - Keep the `countEligible`/`purgeBatched` query shape as-is; the fix is purely the missing index.
    - **Technical:** Every index on these five tables leads with `professional_id`/`site_id`/`ip_hash` (site_visits/link_clicks/lead_submissions/section_views, per `supabase/migrations/20260526000000_baseline_standalone_user.sql:1154-1242`) or `user_id` (site_sessions, per `20260610000000_analytics_v2_clicks_sessions.sql`). `countEligible()` and `purgeBatched()` both filter with `WHERE <tsColumn> < cutoff` and nothing else, so none of these indexes can be seeked into — every run of every table falls back to a sequential scan. To find what to sweep, it has to check every single row's date because none of the filing cabinets are organized by date — they're organized by which professional the row belongs to. As the platform grows to thousands of active professionals with millions of visits a day, this nightly sweep gets slower and slower because it's checking every folder in every drawer instead of jumping straight to "everything before this date."
    - **Evidence:**

- [ ] **#OBS-2** · P2 — `QueuedIngestor`'s per-event fail-open has no aggregate signal for a sustained beacon-dispatch outage
    - **Where:** app/Services/Analytics/Ingestors/QueuedIngestor.php:21-32
    - **Affects:** Every public analytics beacon (pageview/click/section-seen/ping) fleet-wide during any Redis/queue-driver disruption — the client always receives a 2xx response regardless of whether the event was actually queued.
    - **Effort:** S (~0.5-1h)

        - Add a rolling failure counter (e.g. `Cache::increment` on a per-minute bucket) and call `report($e)` once the count crosses a threshold in a short window, so a *sustained* outage becomes Nightwatch-visible without changing the per-event contract.

    - **Plain English:** The system is deliberately built so a single dropped visit-counter never crashes the visitor's experience — that's a sound design choice, like a shop not stopping business because one receipt printer jammed.
