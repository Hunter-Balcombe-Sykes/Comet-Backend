## P2 — Should fix

- [ ] **#XREPO-1** · P2 — Charlie's font-change tool schema advertises 8 font slugs the handler rejects
    - **Where:** `lib/chat-engine/registry.ts:433` (`design_set_font` tool description) vs `lib/chat-engine/action-design-handlers.ts:34-42` (`FONT_SLUGS` allowlist)
    - **Affects:** Any Charlie AI Copilot user who asks to change their sitepage font by name — 8 of the 9 slugs the AI is told are valid (`origin, melodrama, parceh, humane, reglo, oswald, ostrich-sans, young-serif`) are rejected by the handler; only `geist` (of the advertised set) actually works.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Update the `design_set_font` tool description in `registry.ts` to list the real 7-font roster: `geist, inter, general-sans, monument-grotesk, forma-djr, helvetica-neue, helvetica-now`.
        - Fix the handler's own error message in `action-design-handlers.ts` (`` `${DESIGN_SET_FONT_TOOL} requires a valid font_slug from the roster (for example geist, oswald, young-serif).` ``) — it currently suggests `oswald` and `young-serif` as examples, both of which are themselves invalid, so a failed call can lead the model straight into a second failed call.
        - Ideally derive the tool description from `FONT_SLUGS` (or the shared `FONT_OPTIONS` in `use-individual-typography.ts`) at build/definition time so the two can't drift again.
    - **Technical:** `FONT_SLUGS` in `action-design-handlers.ts` was locked to a 7-font roster on 2026-07-12 (per the file's own comment, mirroring `FONT_OPTIONS` in `use-individual-typography.ts`) and explicitly calls out `melodrama`/`origin` as removed. `registry.ts`'s `design_set_font` tool description was never updated to match — it still lists the old 9-slug set, of which only `geist` overlaps the current roster. Any tool call the model makes for one of the 8 stale slugs hits `executeDesignSetFont`'s `throw new Error(...)` guard. Compounding this, that same error message's "for example" hint (`oswald, young-serif`) names two more invalid slugs, so a naive retry loop can fail twice before landing on a real one. This is confined to the frontend chat-engine layer — no backend route or contract is involved.
    - **Plain English:** The AI assistant's internal instructions still list an old menu of 9 font names, but the kitchen only stocks 7 of them today — and only 1 of the old menu's names happens to still be on today's list. If someone asks the assistant to switch to "Oswald" or "Young Serif," it will try, fail, and then (because even its own fallback suggestion still names foods the kitchen doesn't have) may try again and fail a second time. Nobody loses data and the feature isn't broken outright, but a normal request to change the site's font can bounce a couple of times before it works. Fixing the menu to match what's actually in stock — and fixing the "try this instead" note too — makes it work on the first try.
    - **Evidence:**
        ```ts
        // registry.ts:433 — tool description advertises stale slugs:
        description:
          "Set the sitepage font by slug. Valid slugs: geist, origin, melodrama, parceh, humane, reglo, oswald, ostrich-sans, young-serif.",
        ```
        ```ts
        // action-design-handlers.ts:34-42 — handler only allows 7:
        const FONT_SLUGS: ReadonlySet<string> = new Set([
          "geist",
          "inter",
          "general-sans",
          "monument-grotesk",
          "forma-djr",
          "helvetica-neue",
          "helvetica-now",
        ])
        ```
        ```ts
        // action-design-handlers.ts:64-69 — the fallback message itself names invalid slugs:
        const fontSlug = readString(input.font_slug)?.toLowerCase()
        if (!fontSlug || !FONT_SLUGS.has(fontSlug)) {
          throw new Error(
            `${DESIGN_SET_FONT_TOOL} requires a valid font_slug from the roster (for example geist, oswald, young-serif).`,
          )
        }
        ```
