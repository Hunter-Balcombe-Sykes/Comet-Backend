- [ ] **#SEC-1** · P0 — StaffEmailSubscriberController has no authorization gate — any staff member can access any brand's full email subscriber list with PII
    - **Where:** app/Http/Controllers/Api/Staff/StaffSite/StaffEmailSubscriberController.php:36-73 (index) and 80-109 (export)
    - **Affects:** Every brand on the platform — their entire marketing email subscriber list (emails, full names, status, timestamps) is readable and exportable by any authenticated staff member.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Add a Policy (e.g., `ProfessionalDataPolicy`) with a `viewSubscribers` ability scoped to the staff actor's permitted professional set.
        - Call `$this->authorizeForUser($staffUser, 'viewSubscribers', $professional)` at the top of `index()` and `export()`.
        - Consider an access-audit log row when staff views/export subscriber lists for GDPR accountability.
    - **Technical:** The controller receives `Professional $professional` via route-model binding and passes it directly into `EmailSubscription::query()->where('professional_id', $professional->id)` with zero authorization check. Per Partna doctrine, every tenant-owned resource lookup must pass through a Policy registered in `AppServiceProvider::boot()` and called via `authorizeForUser`. The `Api\Staff` namespace implies staff-only middleware, but that only gates the entire staff surface — it does not scope which professionals a staff member can inspect. Absent a tenant-scoping policy, a single compromised staff session yields every brand's subscriber PII.
    - **Plain English:** Imagine every support agent at a bank can pull up any customer's full transaction history just by typing their account number in the URL. That's what's happening here — any staff member can look at (and download as CSV) the complete email subscriber list of any brand on the platform, no questions asked. The fix is to add a lock that says "this staff member is allowed to see data from these specific brands" before the door opens.

- [ ] **#SEC-2** · P0 — DataExportPayloadBuilder::emailSubscriptions() leaks unsubscribe tokens and consent metadata by bypassing Eloquent's `$hidden`
    - **Where:** app/Services/Professional/DataExport/DataExportPayloadBuilder.php:158-163
    - **Affects:** Every professional who requests or receives a GDPR data export — the zip file emailed to them contains live `unsubscribe_token` values for every marketing subscriber on their list.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Replace the raw `->get()` with an explicit `->select(...)` that excludes `unsubscribe_token`, `consent_ip_hash`, and `consent_user_agent` (matching the pattern already used in `integrations()` and `enquiries()`).
        - Add a regression test asserting the export JSON does not contain `unsubscribe_token`.
        - Consider rotating unsubscribe tokens for every exported subscription as defense-in-depth (the `markUnsubscribed` path already does this; adopt the same pattern).
    - **Technical:** The `EmailSubscription` model declares `protected $hidden = ['unsubscribe_token', 'consent_ip_hash', 'consent_user_agent']` so that JSON serialization via the Eloquent API resource layer never emits these fields. However, `emailSubscriptions()` uses `DB::connection('pgsql')->table(...)->get()->map(fn ($r) => (array) $r)->all()` — a raw query builder path that never touches the model's `toArray()` or the `$hidden` configuration. Compare with `integrations()` (line 131–137), which explicitly `->select(['id', 'provider', 'shop_domain', ...])` excluding `access_token` and `refresh_token`. The `unsubscribe_token` is a bearer secret: anyone who possesses it can unsubscribe that subscriber via the public `POST /api/public/unsubscribe/{token}` endpoint. Exfiltrating it in an emailed zip file creates a persistent credential-leak surface.
    - **Plain English:** The system keeps a "secret key" for each email subscriber that lets them unsubscribe with one click. Normally, these keys are hidden from view everywhere in the app. But when a brand owner requests a data export (e.g., for GDPR compliance), the export zip file accidentally includes every single one of those secret keys in plain text. Anyone who gets a copy of that export — or intercepts the email — can unsubscribe any subscriber on that brand's list. It's like including the spare key to every apartment in a building inside the fire-safety report.
    - **Evidence:**
        ```php
        // DataExportPayloadBuilder.php:158-163 — exports ALL columns
        private function emailSubscriptions(string $professionalId): array
        {
            return DB::connection('pgsql')
                ->table('notifications.email_subscriptions')
                ->where('professional_id', $professionalId)
                ->get()
                ->map(fn ($r) => (array) $r)
                ->all();
        }
        ```
        ```php
        // EmailSubscription.php:23-27 — these fields are supposed to stay hidden
        protected $hidden = [
            'unsubscribe_token',
            'consent_ip_hash',
            'consent_user_agent',
        ];
        ```
        ```php
        // DataExportPayloadBuilder.php:131-137 — the SAME builder properly strips secrets on integrations
        private function integrations(string $professionalId): array
        {
            return DB::connection('pgsql')
                ->table('core.professional_integrations')
                ->select(['id', 'provider', 'shop_domain', 'last_sync_at', 'created_at', 'updated_at'])
                ->where('professional_id', $professionalId)
                ->get()
                ->map(fn ($r) => (array) $r)
                ->all();
        }
        ```

- [ ] **#SEC-3** · P2 — SendEnquiryNotificationJob::failed() logs the recipient's email address to the error log
    - **Where:** app/Jobs/Notifications/SendEnquiryNotificationJob.php:46-53
    - **Affects:** Any enquiry notification that fails permanently — the brand's notification email address persists in the log aggregator (Nightwatch) indefinitely.
    - **Effort:** S (~0.5–1h)
    - **What to do:**
        - Replace `'notification_email' => $this->notificationEmail` with `'notification_email_hash' => hash('sha256', $this->notificationEmail)` or redact to `'notification_email' => '[redacted]'`.
        - Audit all `Log::error` / `Log::warning` calls across the job layer for other email-in-context patterns.
    - **Technical:** Laravel's log channels (especially when aggregated through Nightwatch or similar observability pipelines) retain log entries long-term. GDPR Article 5(1)(e) storage-limitation and Article 32 security-of-processing requirements apply to logs that contain personal data. A hashed value preserves debuggability (you can still correlate with the same email from other log lines) without storing the raw email in plain text.
    - **Plain English:** When a contact-form notification email fails to send, the system writes the recipient's email address into the permanent error log. Think of it like writing a customer's home address on the wall of the server room — it stays there forever, and anyone with access to the monitoring dashboard can see it. The fix is to use a scrambled version (a "hash") that still lets engineers trace the same address across log entries without revealing the actual email.
    - **Evidence:**
        ```php
        // SendEnquiryNotificationJob.php:46-53
        public function failed(\Throwable $e): void
        {
            report($e);
            Log::error('SendEnquiryNotificationJob failed permanently', [
                'enquiry_id' => $this->enquiryId,
                'notification_email' => $this->notificationEmail,
                'error' => $e->getMessage(),
            ]);
        }
        ```
    - `[DRAFT, confidence: 0.9]`
